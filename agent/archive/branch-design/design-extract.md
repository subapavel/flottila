## B. ARCHITECTURE.md §6 subsection 'User-defined error handling' (branch lines 254-279)

**User-defined error handling** (D-102, D-103): a flow declares named error handlers and attaches one to the whole flow or to a single step, where `recording` is attached — but `onError` is a single name, not a key-by-key merge (D-044), so a step's declaration replaces the flow's outright and `onError: none` takes the built-in path. A step inside a route branch takes its own `onError` or the flow's. A handler is a pipeline of ordinary steps (`transform`, `to`, `call`, anything), so the author can build a SOAP Fault or a partner-specific JSON error, notify, compensate or send the message to another target — none of which the built-in paths of D-045 / D-049 can do.

```yaml
onError: soapFault                   # flow default; a step may name another handler, or `none` for the built-in path
errorHandlers:
  - name: soapFault
    on: [MALFORMED, INVALID]         # the Fault kinds this handler takes; default: every kind
    then: handled                    # handled | rethrow
    reply: { status: 400 }           # sync only; default: the status D-049 maps from the kind
    steps:
      - { type: xslt, name: fault, stylesheet: flows/fault.xsl }
```

The handler is given the failure as explicit arguments, never as a prop (§5: the exception as a property is not carried over from Camel): `ErrorHandler` is `Envelope apply(Envelope in, Failure f)` with `Failure(String step, Fault.Kind kind, String text)` and `in` = the failed step's input envelope, the same envelope a park records (D-045); its fields are readable inside the handler only, through the read-only expression scope `error.step`, `error.kind`, `error.text`. The handler owns the headers, props, keys and body of `in`; `error.*` never becomes one of them.

| Mode | What `then: handled` returns | Durable record | What the sender sees |
| --- | --- | --- | --- |
| Sync | the handler's last envelope is the reply, `reply.status` written to the §5 status prop (default: D-049's status for the kind) | the marker rides the run's trail at `all`, `ends` and `errors`; no step waits for it (D-066) | the handler's reply, instead of the kind's status with the error text |
| At-least-once | nothing to return; the run ends handled, the message is never parked and the worker completes its item | the `HANDLED` marker, awaited before the run ends, at every recording level — it stands where the DLQ row would have stood (F-2, D-049 b) | nothing; the 202 was given at the durable save |
| At-most-once | nothing to return; the handler's result is dropped like any result | the marker on the trail at `all`, `ends` and `errors`, nothing at `off` | nothing; the ACK went before the pipeline ran |

Ordering: the step's own retry runs out first — the handler sees the final failure, never an attempt — and the handler runs before the built-in path, as the wrapper between the step's recorder and its parking, so a handled failure reaches neither the park, nor the sync error reply, nor the at-most-once drop, and the rest of the main pipeline does not run. Handlers never nest and never loop: a handler's steps carry no `onError`, and a failure inside the handler, an unmatched kind, `then: rethrow` and a marker that cannot be written all fall back to the built-in path of D-045 / D-049 with the step's original failure surfaced and the handler's (or the write's) failure suppressed — so every at-least-once failure still ends in exactly one durable record, a DLQ row or a `HANDLED` row, or its item stays to its lease. An interrupt is never handled: it is a shutdown signal, not a failure of the message, and it reaches no handler (D-103).

In the timeline the handler's steps are rows of their own, named `<handler>:<step>` — the form §6 reserves for a nested pipeline, as a route branch is `route:<branch>` — numbered in a range reserved per handler after the main pipeline's steps in declaration order (range length = the handler's steps + 1); the run ends with one marker row beside the failed step's `FAILED` row: step = the last number of that range, step name `onError:<handler>`, outcome `HANDLED`, `error` = `<failed step name>: <failure text>`, the envelope the handler ended with (headers, props, keys, body hash + size), always metadata-only. A run that ends `HANDLED` is a **successful run** of the flow (D-105): it is not in the flow's error rate, not in error alerting and not in the SLA's failure count — the outcome of a handled failure is success, and an operator who sees permanent red for something the flow handled stops trusting the colour. What carries it instead is a number of its own, `handled`, per flow, per step and per handler, shown beside the error rate on the per-flow screen; it rises on every handled failure, so a handler cannot turn a failure into silence. Nothing leaves the history: the failed step keeps its `FAILED` row and its error text, the handler's steps keep their rows, and an error is present on a row iff its outcome is `FAILED` or `HANDLED` (D-102, amending D-044). Replay and DLQ retry: the marker is never a replay input (`Replay.from` matches the `OK` row of step N−1, `Replay.java:101`) and a step number inside a handler range is refused; a replay restarts the main pipeline from a recorded main step under its own new id and runs the handler again if it fails again; a handled failure leaves no DLQ row, so there is nothing to retry — an operator who wants that choice writes `then: rethrow`.

Migration: a CPI Exception Subprocess becomes a flow-level handler, its End Message `then: handled`, its Escalation End `then: rethrow`, `${exception.message}` the scope's `error.text`; Camel's `onException(X.class).handled(true)` becomes an `onError` whose `on:` names the `Fault` kind the exception class stood for (there is no exception-class matching: `api` has the four kinds `MALFORMED`, `INVALID`, `DOWNSTREAM`, `INTERNAL`, not a type hierarchy), and `.maximumRedeliveries` stays the step's `retry`, which runs before the handler. Not carried over from Camel: `.continued(true)` (a handled failure ends the run, it never resumes at the next step), a context-wide `onException` (a handler belongs to a flow; a package is not a Camel context), `onWhen` predicates, and a handler for a handler.
