   Times are from the start of the `FlowWorker.failed()` call; "failed()" is how long the call lasted, "defer" is
   `InMemoryWorkQueue.defer`, which reads the clock. "Clock found quiet": `rail8-clock` reads `InMemoryWorkQueue.size` and
   then `VirtualTime.flowTime` (the time given), which `VirtualTime.drive` does after a quiet sample only, and then calls
   `FakeClock.advance`. In b4 the defer ran while that advance was still firing its timers. d13 is the invoice-async flow:
   the fault is not the sftp flow's own.

   The chain, as the recordings show it:
   a. The node. On the retry path `FlowWorker.failed()` (FlowWorker.java:681-704) logs a WARNING with the failure through
      `System.Logger`. java.util.logging's ConsoleHandler formats it and writes it (4337 bytes; 4735 in d13) to `System.err`,
      all on the flow's own virtual thread. No window holds a contended monitor enter, a GC pause, a safepoint or a pinned
      thread; none of the four whose settings trace parking (b4, b17, d13, c0) holds a park. Classes load inside the call in
      d13 only (38: the first log call of that JVM).
   b. The JDK (Temurin 25, read from `lib/src.zip`). `System.out` and `System.err` write through `java.lang.System$Out`
      (System.java:1882-1916), which wraps each write in `jdk.internal.misc.Blocker.begin()` / `end()`. On a virtual thread
      that is `CarrierThread.beginBlocking()` -> `ForkJoinPool.beginCompensatedBlock()` (`tryCompensate`, ForkJoinPool.java
      :2186): the scheduler's pool gives the carrier's place to a spare worker until the block ends.
      `VirtualThreadSchedulerMXBean.getMountedVirtualThreadCount()` is that pool's active count
      (`ForkJoinPool.getActiveThreadCount()`), and for the length of the block the count leaves this carrier out.
      c0: `beginCompensatedBlock` at +988 us, the counter agent reads mounted=0 queued=0 at +1008, the write at +1044,
      mounted=1 again at +1081, `endCompensatedBlock` at +1094. The thread was mounted and writing while the count read 0.
   c. The runner. `Quiescence` (Quiescence.java:64-68, :87-90) calls a sample idle when that count and the queued count are
      0, and answers quiet after 1 ms of idle samples with one fingerprint (`STEADY`, FlowTests.java:89). In c0 the block
      lasted 106 us and the clock thread took no quiet sample inside it. In d13 `beginCompensatedBlock` itself lasted
      3919 us: the count read 0 from +27137, the clock thread read the queue's size at +28206 - 1069 us later - and
      advanced the clock; it did so again at +29704; the thread's write came at +31032, the block ended at +31095, and `InMemoryWorkQueue.defer`
      (InMemoryWorkQueue.java:113-117) computed the retry's due time from the clock as it then stood.
   d. The report. Both flows have a mock with a poll round pending (MockComponent, 1 s), so the clock had a timer to step to:
      700 -> 1000 -> 2000 ms. A defer of 1 s from 1000 gives tries at 2000, 2100, 2300, 2700; from 2000 it gives 3700. The
      expected line is 2400 (the defer computed at 700).

   What the counter agent is: `method-trace/CountAgent.java`, a `-javaagent` whose platform thread polls the two counts and
   keeps every change with its time.

3. The same without Rail8 (`carrier/CarrierProbe.java`, a standalone program; `carrier-probe.txt` on CPUs 1-3,
   `carrier-probe-1cpu.txt` on one CPU; 200 000 samples per line)

   | the one virtual thread is            | samples the scheduler's two counts call idle | samples with no carrier thread RUNNABLE |
   | parked                               | 200 000                                      | 200 000                                 |
   | spinning                             | 0                                            | 0 (one CPU: 1981, see below)            |
   | blocked in a Process pipe read       | 200 000                                      | 0                                       |
   | writing 4337 bytes to System.err     | 55 654 (one CPU: 77 653)                     | 0                                       |
   | parked again, three carriers idle    | 200 000                                      | 200 000                                 |

   A carrier thread is a platform thread of class `jdk.internal.misc.CarrierThread`; its `Thread.getState()` stays RUNNABLE
   while it runs a virtual thread, compensated block or not, and is WAITING when it is parked for work. Reading the states
   of all carriers costs about 470 ns (three carriers). No sample of any line was called idle by both readings while the
   thread ran. On one CPU the spinner's carrier was seen not yet RUNNABLE in 1981 samples at the start: it had been
   signalled and had not run yet; the scheduler's counts were not idle in those samples. Neither reading is enough alone.
