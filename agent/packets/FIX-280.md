# FIX-280 - testkit's coverage figure is the same in every run (class B)

Row: `grep -n "^| FIX-280 " agent/BACKLOG.md`. The map: `agent/work/FIX-280-scout.md`, Part 1. The measurement, the
row's "before": `agent/work/FIX-280-before.txt` - two testkit-only runs on unchanged code read 400 and 402 of 417
branches, the whole difference in `ComponentContract.java` :393 and :550; four whole-reactor runs read 401, 400,
398, 397, there also :279 and :510.

## What is wrong

Each of the contract's twelve polls is `soon(() -> <a comparison>)`. The comparison is a branch of that call
site's own lambda, and its false outcome is taken only when the first poll comes before the delivery. Nothing can
order a component's delivery against the first poll, so whether a call site's lambda sees "not yet" differs from run
to run - and with it the module's branch figure, which every later row compares.

## The change

The comparison leaves the call sites. `ComponentContract` gains three helpers beside `soon` (:109), each one line
over it, `protected final` like it:

- `soonEquals(IntSupplier actual, int expected)` - `soon(() -> actual.getAsInt() == expected)`;
- `soonAtLeast(IntSupplier actual, int least)` - `soon(() -> actual.getAsInt() >= least)`;
- `soonPresent(Supplier<?> value)` - `soon(() -> value.get() != null)`.

The twelve call sites (:204 to :594, listed in the map) use them with a method reference (`seen::size`,
`invoked::get`, `pending::get`): no call site keeps a comparison in a lambda. What the contract asks of a component
does not change: the same condition, the same patience, the same message on failure. `PollingConsumerContract` is
not touched (its polls did not move in any run measured). `ComponentContract`:515 is no poll and stays.

`requireNoEarlierDirFailure(long gen)` (`platform/runtime/src/main/java/dev/rail8/runtime/journal/Journal.java`

construction (`JournalDirForceOrderTest` :52-116: two persists whose directory forces are held, B released first -

covered in three whole runs and missed in one. The mirror case takes it in every run: both forces held as in
`JournalDirForceOrderTest`'s `Two`, A released first, and A's persist completes while B's force is still held -
an earlier persist never waits for a later force. The seams exist: `HeldFiles` (:235, :245), `OwnDirForce`.
