# FIX-175 — each attempt of a same-id rerun keeps its own snapshots (class B)

Row: agent/BACKLOG.md FIX-175. Monitoring is the product: a D-135 worker rerun or a same-id DLQ `/retry` (D-136) shows no timeline of
its own attempt today, because `messages` PK (id, step) `on conflict do nothing` (PgMessageStore:51-55) keeps run 1's rows.

Facts (scout): messages PK (id, step) V1:13-25, cols V2/V11, index V10 (created_at, id, step); no attempt column outside `work`;
latest migration V18. Snapshot (core record/Snapshot.java:36) has no attempt; its props carry ATTEMPT (Envelope:46) when >= 2
(FlowWorker:646, /retry → work.restart attempts k, max k+1). A rerun's body key has the "~N" part suffix (Envelope:101), so bodies
do not collide; only the row is dropped. Readers: timeline AdminServer:608-615 (order by step), body route :617-644 (first row with
step n), search by key (message ids only), Retention :156-162 (whole message by id), FlowWorker:640 (ingress from the timeline),
Replay (step n-1 row). Pins: PgMessageStoreIT:129-137 first-wins, InMemoryMessageStoreTest:153, NodeIT:720/1517, AdminServerTest:235-332.

## Decision
P1 V19: `messages.attempt int not null default 1`; PK (id, step, attempt). Existing rows are attempt 1. No other table changes.
P2 Snapshot gains `attempt` (int, >= 1): ATTEMPT from the envelope's props, absent → 1. Insert carries it; `on conflict (id, step,
   attempt) do nothing` (a resent row of the same attempt still first-wins). The in-memory store does the same.
P3 Timeline: rows ordered by (attempt, step); each step object gains `"attempt"` (additive; the shape stays a flat `steps` list).
P4 Body route `/admin/messages/{id}/steps/{n}/body`: the latest attempt's row for step n by default; `?attempt=k` selects attempt k;
   a k with no row → 404 with the usual body; a k not a positive int → 400.
P5 Readers that pick one row per step: FlowWorker's ingress lookup takes attempt 1 (the arrived body); a message replay from step n
   and a DLQ replay take the latest attempt's step n-1 row. Search by key and retention are unchanged (they key on the message id).
P6 Docs (architect): §8 Snapshot key (id, step, attempt), §6 Recording sentence (each attempt recorded), changelog row, D-140
   (reversible), BACKLOG FIX-138b's "V18" → the next free migration. Version pins 18 → 19 in the tests that pin it.

## Acceptance (red first, test-author)
A1 IT: an at-least-once message whose partner fails twice and then succeeds (count 2, fake or short interval) → the timeline holds
   the steps of attempts 1, 2 and 3, each with its `attempt` and its own outcome; attempt 3's final step OK.
A2 IT: a parked message retried by `POST /admin/dlq/{id}/retry` → the retried attempt's rows appear beside the earlier ones.
A3 body route: default = latest attempt's body for step n; `?attempt=1` returns run 1's body (different bytes when the step's
   input differs, or at least run 1's hash); `?attempt=9` → 404; `?attempt=0` / `x` → 400.
A4 PgMessageStoreIT: a duplicate (id, step, attempt) is ignored; the same (id, step) with another attempt is kept. The test-author
   amends :129-137 (its own expectation changes with P2; reason in the commit).
A5 MigrationsIT: V19 PK (id, step, attempt), a pre-V19 row reads as attempt 1; pins 18 → 19.
A6 a message replay from step n after a two-attempt run uses attempt 2's step n-1 body; the worker's rerun reads attempt 1's ingress.
A7 InMemoryMessageStoreTest: the same two cases as A4.
No sleep-based timing (fake clock / scheduled retry interval as in CORE-14a tests).
