## Behaviour (D-095)
- `Deployments.undeploy(String name)` → `UndeployResult(String name, String version, List<String> flowsRemoved)` (flow ids as in
  GET /admin/flows, sorted). Order of checks: name pattern → BAD_REQUEST; deployed env → FORBIDDEN "manual undeploy is
  non-production only (ARCHITECTURE §9)"; lock busy → CONFLICT / STOPPING as deploy; closing → STOPPING; unknown package (no
  record, not listed) → new Kind NOT_FOUND (404) "no package '<name>' is deployed"; pinned by another record (FAILED included) →
  CONFLICT "<name>@<version> is in use by <a>, <b>" (dependents sorted, each once).
- Then, under the lock: delete the record (new `DeploymentStore.delete(String name)`, Pg + Ledger) — the commit point; a delete
  that fails is the node's failure (IOException / 500) and changes nothing else; then stop and close every flow of the package
  (retire's way: a stop that fails is a WARNING and counts as settled); drop it from the listing; prune its unpacked directories
  that no remaining record pins and no remaining flow reads (WARNING on failure, the undeploy stands). Archives in the
  ArchiveStore are kept (rollback = deploy again). A FAILED package undeploys the same way (no flows to stop).
- A restart after an undeploy does not restore the package. Undeploying the last dependent makes the dependency undeployable.
- Admin: `DELETE /admin/packages/:name` beside PUT (same guards) → 200 {name, version, flowsRemoved:[…]}; refusals by the status
  map plus NOT_FOUND → 404; body {error}. GET /admin/packages no longer lists it; its flows answer as an unknown flow.
- Out of scope: CLI `flottila undeploy` (no row asks for it), control-plane undeploy.
