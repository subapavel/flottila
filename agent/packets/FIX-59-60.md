# Packet FIX-59 + FIX-60 (class A, batch)

Two independent small fixes in `flottila-runtime`, one commit. Red tests first.

## FIX-59 — `FLOTTILA_S3_PREFIX` is not validated

Today `NodeConfig.java:491` takes the env value as-is:
`env.getOrDefault("FLOTTILA_S3_PREFIX", "flottila")`. Keys are built as
`<prefix>/archives/<sha256>.zip` (javadoc `NodeConfig.java:178`), so an empty prefix, a
leading `/` or a trailing `/` produces an odd object key (`//archives/…`, `/archives/…`).

### Acceptance 59
`NodeConfigTest` refuses each of these values of `FLOTTILA_S3_PREFIX`, and the refusal
message names the key `FLOTTILA_S3_PREFIX` and shows the offending value:
- `""` (empty)
- `"   "` (blank)
- `"/flottila"` (leading slash)
- `"flottila/"` (trailing slash)
- `"/"`

A prefix with an inner slash (`"a/b"`) is accepted — only the ends are wrong.
The default (variable unset) stays `flottila` and stays accepted.
The refusal is the same mechanism `NodeConfig` already uses for other bad env values —
find it and follow it; do not invent a second refusal style.

## FIX-60 — `ArchiveStore.fetch` has no size bound

`ArchiveStore` (`flottila-runtime/src/main/java/io/flottila/runtime/deploy/ArchiveStore.java:27`)
declares `void fetch(String sha256, Path target) throws IOException` with no bound.
`Deployments.restore()` writes whatever the object holds into the data dir and only then
compares the sha256, so a wrong or hostile object fills the disk before it is rejected.

### Acceptance 60
Both implementations (`DirArchiveStore`, `S3ArchiveStore`) take a maximum size at
construction and refuse a fetch whose source exceeds it.

- The cap is a `long` and is passed in, never defaulted to unlimited (CLAUDE.md:
  "Never default a limit to unlimited"). Its value at the call sites is
  `config.maxPackageBytes()`; the three construction sites are `Node.java:185`,
  `Node.java:190` and `Deployments.java:241`.
- A new case in `ArchiveStoreContract` (the suite both implementations run): an object
  whose bytes exceed the cap is refused with an `IOException`, the message names the cap
  and the actual or allowed size, and **the target file does not exist afterwards** —
  no partial file is left behind.
- An object exactly at the cap is fetched normally. The existing contract cases keep
  passing unchanged.
- The refusal happens while streaming, not after the whole object is on disk: the test
  must be able to tell the difference. Assert on the target's absence, and prefer a
  source comfortably larger than the cap so a whole-then-check implementation would be
  visible in the test's own disk use.
- `ArchiveStoreContract` needs to know the cap. Add one `protected abstract long cap()`
  (or an equivalent single hook) and have each subclass build its store with it. Keep
  the change to the suite as small as that.

## Architect's rulings on the red tests (approved 2026-11-14)

The red is approved. FIX-59's red is an assertion failure
(`agent/work/FIX-59-60-red-2.log`, 102 run / 1 failed); FIX-60's red is a compile
failure (`agent/work/FIX-59-60-red-1.log`), because the constructors do not exist yet.
That is accepted for this task.

Assumed signatures, confirmed:
- `new DirArchiveStore(Path dir, long maxBytes)`
- `new S3ArchiveStore(S3Client s3, String bucket, String prefix, long maxBytes)`

1. **Replace the constructors, do not overload them.** An overload without a cap is a
   limit defaulted to unlimited, which CLAUDE.md forbids; an overload with a built-in
   default cap hides the limit at the call site, which is the same fault one step further
   away. Every construction site states its cap.
2. **The implementer updates the ~20 existing call sites** the test-author listed
   (`S3ArchiveStoreTest:42`, `S3ArchiveStoreIT:121` and `:135`, `Shelf`, the
   `Deployments*Test` classes, the `AdminServer*Test` classes and the rest). This is
   mechanical: add the cap argument, change no expectation. It is explicitly authorised
   here, so it is not a breach of "the implementer may not change a test it did not
   write" — if any of those call sites needs more than a new argument, stop and say so in
   the hand-back instead of reinterpreting the test.
3. **Refuse while streaming.** The test can only prove the target is absent afterwards,
   so the obligation is on the implementation: count bytes as they are copied and fail as
   soon as the count passes the cap. Do not write the whole object and check its size.
   Delete any partial or temporary file on the failing path.
4. The `IOException` message names the cap and the offending size, in the voice the
   deploy code already uses for refusals.
