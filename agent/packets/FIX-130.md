# Packet FIX-130 (class A) — the last bare-id log filter in TrailTest

Module: `flottila-core`, test-only. Row: `agent/BACKLOG.md`, FIX-130 (dep FIX-123 `done`).
Found by the reviewer of FIX-123, non-blocking there, a row of its own here.

## The defect

`TrailTest:359-360`, in `aFailedOrTooLargePersistRecordsTheRowMetadataOnlyAndCountsIt`:

    List<String> warned = logged.stream().filter(r -> r.getLevel() == Level.WARNING)
            .map(r -> r.getMessage() + " " + r.getThrown())
            .filter(m -> m.contains("m-f")).toList();
    assertFalse(warned.isEmpty(), "a WARNING names the message whose rows were recorded metadata-only");

Two things are wrong with that filter and neither is visible while the test is green:

1. `contains("m-f")` is a bare id substring. This is the trap FIX-54 hit once and FIX-121 hit
   twice: `"m-w"` is a prefix of `"m-wait"`. It is safe here only by accident — `m-f` happens to
   prefix no other fixture id in this case. A fixture renamed `m-f2` in some future case, or a
   second message in this one, and the assertion starts passing on the wrong record.
2. The filter runs over `getMessage() + " " + getThrown()`, so the **exception text** can satisfy
   it. Today the thrown is `IllegalStateException("pg down")` so it cannot, but the assertion does
   not say what it means: a WARNING whose message names nothing and whose cause happens to mention
   `m-f` would pass.

`assertFalse(warned.isEmpty())` is also the weakest available shape: it cannot tell one matching
record from five.

## Acceptance

1. The filter selects by the case's own `BlobKey` — the same shape the two persist cases use after
   FIX-123 (`TrailTest:386`, `:409`: `m.contains(<key>.toString())`) — not by a bare id substring,
   and not over a string that includes `getThrown()` unless the assertion genuinely means to
   accept a cause. State which it means in the assertion message.
2. The case still fails if no WARNING names the metadata-only message. Prove it: with the filter
   changed, delete or neutralise the WARNING in `Trail` as a hand mutant and observe the case fail.
   A filter change that makes the assertion unfalsifiable is worse than the bare substring.
3. Count what the case means. If exactly one WARNING is expected for this message, assert the
   count, not non-emptiness. If more than one is legitimately possible here, say so in the
   hand-back with the reason and keep `assertFalse(isEmpty())` — do not guess a number to look
   strict.
4. Nothing else in the case changes: the three `assertEquals` at `:356-358` and the
   `metadataOnly()` count stay exactly as they are. This row narrows one filter.
