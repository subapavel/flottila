# Packet FIX-254 (class B) — a flow time never depends on the machine

Row: `agent/BACKLOG.md` FIX-254, under MAIN-1 since `ci` run 224 failed on it (`agent/work/MAIN-1-ci.md`):
`bin/rail8 test examples/demo` reported `PASS sftp-invoice: partner down (flow time 2700ms)` where
`TestCommandTest.DEMO_REPORT` expects `2400ms`. The other five lines and the totals line were as expected.

The runner's time is virtual. A flow time that differs between two runs of one package is a fault of the runner.

The row's acceptance has two halves, and this packet has two stages for them:

1. **The cause is shown before anything changes** — stage 1, a measurement. Done: `agent/work/FIX-254-evidence.txt`.
2. **Each case reports the same flow time in every run** — stage 2, below. Done: section 5 of the evidence file.

## The cause (measured; the recordings are named in the evidence file)

- The clock thread `rail8-clock` (a platform thread, `VirtualTime.java:58`) steps the virtual clock when
  `Quiescence.quiet()` says so: two samples with no mounted and no queued virtual thread
  (`VirtualThreadSchedulerMXBean`), equal fingerprints, idle for `STEADY` = 1 ms of wall time (`FlowTests.java:89`).
- `getMountedVirtualThreadCount()` is the scheduler pool's active count. The JDK leaves a carrier out of that count
  while its virtual thread is inside a blocking operation the pool compensates for — the code between
  `jdk.internal.misc.Blocker.begin()` and `end()`. A write of `System.out` or `System.err` that reaches the file
  descriptor is one (`java.lang.System$Out`, System.java:1882-1916); so are a read of a `Process` pipe, a
  `RandomAccessFile` call, a DNS lookup. For the length of the block the count reads 0 while the thread is mounted
  and running.
- The node's worker logs a WARNING on the retry path (`FlowWorker.failed()`, FlowWorker.java:681-704), and the console
  handler writes it to `System.err` on the flow's own virtual thread. The block normally lasts about 100 µs. When it
  lasts more than 1 ms — 3.9 ms in one recording — the runner calls the world quiet and steps the clock to the mock's
  next poll round; the worker then computes its retry from the stepped clock (`InMemoryWorkQueue.java:113-117`): 2700 or
  3700 ms where 2400 is right. Recorded in the sftp flow and in the invoice-async flow.
- On this machine 3 of 210 reports were wrong on four idle CPUs, 0 of 300 on one CPU or under load.

What this packet first suspected — a monitor hand-over through the JDK's unblocker thread — is refuted: none of the six
recorded windows holds a contended monitor enter. The world read of a sample takes no monitor (`FlowTests.java:296-300`),
and that stays true.

## Stage 1 — the measurement (done, 2026-11-15)

`agent/work/FIX-254-probe/probe.sh` ran the demo under CPU pins and load (the verifier: five configurations, 510 runs);
the architect recorded method traces with a counter agent (`method-trace/`) and measured the carrier threads' states in
a standalone program (`carrier/`). Nothing under `src/` changed. The numbers are in the evidence file.

## Stage 2 — the remedy

### The decision (D-155)

A sample of `Quiescence.ofJvm` counts, besides the scheduler's two counts and the runner's busy threads, **the carrier
threads whose state is `RUNNABLE`**.

A carrier is a platform thread of class `jdk.internal.misc.CarrierThread`. Measured
(`agent/work/FIX-254-probe/carrier/carrier-probe.txt`): its `Thread.getState()` is `RUNNABLE` while it runs a virtual
thread, inside a compensated block too, and `WAITING` while it is parked for work. Reading the states of all carriers
cost about 0.5 µs there, with three carriers. The scheduler's counts stay in the sample: a carrier that has been
signalled and has not run yet is not `RUNNABLE`, and only the counts see its thread. `STEADY` stays as it is.

Not chosen: a registry of the node's threads through `Runtime` (an `api` change for the test runner's need; threads
start in more than ten places across `api`, `core` and the components); keeping the log write off the flow thread in
the runner (it removes one caller of one blocking operation); a longer `STEADY` (the block has no upper bound).

### Acceptance — red first (test-author; `QuiescenceTest`, the section "the JVM's scheduler")

Write the cases in the style of the cases already there (`until`, a list of the sample indices that answered quiet).

1. **`aVirtualThreadInsideACompensatedBlockIsNeverQuiet`.** Stage: start the child process `cat`
   (`new ProcessBuilder("cat").start()`); a virtual thread sets a flag and then reads one byte of the child's output
   (`process.getInputStream().read()`). That read blocks between `Blocker.begin()` and `end()` (Process.java:964-972 —
   the same pair `System$Out` uses) until the child's input closes; the standalone program held a thread there for
   200 000 samples, all of which the scheduler's two counts called idle. After the flag is set, call `quiet()` on
   `Quiescence.ofJvm(() -> "unchanged")` 20 000 times: no call answers quiet, and the reader is alive after the last
   one. Then close the child's input (`process.getOutputStream().close()`), join the reader, and show with `until` that
   the same probe answers quiet (it is not always false). Destroy the child in `finally`.
   Red today: `quiet()` answers true once the thread is in the block. Observe this red alone, before cases 2 and 3
   exist, in 5 consecutive runs of the case; give the first quiet index of each run. If 20 000 calls do not show the red
   in every run, change the number and say why.
2. **`aSpinningVirtualThreadIsARunningCarrier`.** While a virtual thread spins — wait for the flag the spinner itself
   sets — each of 1 000 calls of `Quiescence.runningCarriers()` answers at least 1. This case is the guard on the JDK's
   class name: if a later JDK renames the carrier class, the count is 0 and this case says so.
3. **`parkedVirtualThreadsLeaveNoCarrierRunning`.** With one virtual thread parked on a Vert.x future (as
   `parkedVirtualThreadIsQuiet` stages it), `until(() -> Quiescence.runningCarriers() == 0, …)` is reached and the
   thread is still `WAITING`.
4. The eleven cases already in the class stay as they are, and green.

Cases 2 and 3 do not compile until the implementer adds the method: that is their red. Add to the class comment's list
of "the type these tests define" what cases 1 to 3 define.

### The contract the cases define (implementer; `Quiescence.java` only)

- `static int runningCarriers()`, package-private: the platform threads of class `jdk.internal.misc.CarrierThread`
  whose `Thread.getState()` is `RUNNABLE`, read now. Find them from the root thread group
  (`ThreadGroup.enumerate(Thread[], true)`). Compare the class by its name; no `--add-exports`, no `--add-opens`, no
  reflection into the JDK. Read the threads anew on every call: carriers come and go (the pool starts spare ones for
  compensated blocks and retires idle ones). No mutable static state.
- Both `ofJvm` overloads: a sample's mounted reading is the scheduler's mounted count plus `runningCarriers()` plus
  `busy`.
- The class comment says what a sample counts and why the scheduler's count is not enough, in two or three sentences,
  with the JDK fact above. Check the fact against the resolved JDK (`javap`, or `lib/src.zip` of the JDK in use) before
  writing it; never from this packet alone.
