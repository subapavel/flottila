# Packet FIX-254 (class B) — a flow time never depends on the machine

Row: `agent/BACKLOG.md` FIX-254, under MAIN-1 since `ci` run 224 failed on it (`agent/work/MAIN-1-ci.md`):
`bin/rail8 test examples/demo` reported `PASS sftp-invoice: partner down (flow time 2700ms)` where
`TestCommandTest.DEMO_REPORT` expects `2400ms`. The other five lines and the totals line were as expected.

The runner's time is virtual. A flow time that differs between two runs of one package is a fault of the runner.

The row's acceptance has two halves, and this packet has two stages for them:

1. **The cause is shown before anything changes** — stage 1, a measurement. No file under `src/` changes.
2. **Each case reports the same flow time in every run** — stage 2, written by the architect from stage 1's
   numbers. Not in this packet yet.

## What is known (read from the code by three scout passes, `agent/work/FIX-254-scout.md`)

- The normal timeline of the failing case: delivery 1 tries at 0, 100, 300, 700; the defer is 1 s; delivery 2
  tries at 1700, 1800, 2000, 2400. If the virtual clock stands at 1000 instead of 700 when the defer's due time
  is computed (`InMemoryWorkQueue.java:113-117`) or when the worker arms its wake (`FlowWorker.java:499-506`),
  delivery 2 tries at 2000, 2100, 2300, 2700 — the sighting. 1000 is the sftp mock's next poll round (its timer
  is pending from t=0, `MockComponent` ROUND = 1 s).
- The clock thread `rail8-clock` (a platform thread, `VirtualTime.java:58`) steps the clock when
  `Quiescence.quiet()` says so: two samples with no mounted and no queued virtual thread
  (`VirtualThreadSchedulerMXBean`), equal fingerprints, idle for `STEADY` = 1 ms of wall time
  (`FlowTests.java:89`).
- A virtual thread blocked on a `synchronized` monitor leaves its carrier (JEP 491). From the monitor's release
  until the JDK's unblocker thread queues it again it is neither mounted nor queued. `Quiescence.java:19-22`
  says the steady time covers that hand-over.
- The sample's own read of the world takes no monitor, by design (`FlowTests.java:296-300`; `FakeClock` is an
  `AtomicReference`, the mock's lists are copy-on-write, `Watched` counts with atomics). The clock thread does take
  monitors elsewhere: in the settled predicate on a quiet sample (`queue.size()`, `door.undelivered`, :271), in
  `FakeTimer` (`pending`, `nextDelay`, :40, :49, :59), and while it runs the due timer tasks inside
  `clock.advance` — `FlowWorker.retriesDue` (:511-524) and what it claims, the mock's `fire` (:324-329).
- Only `Timer.schedule` and `cancel` are counted as busy (`Watched`, `FlowTests.java:341-365`). A flow thread
  blocked on any other monitor is counted nowhere.

## The hypothesis (the architect's; NOT shown)

A flow thread meets a monitor that another thread holds — the clock thread inside a timer task, or a second flow
thread — and leaves its carrier. After the release it waits for the JDK's unblocker and is invisible; the world
does not change, so every sample is idle with an equal fingerprint. Normally that lasts microseconds. When the
unblocker does not get a CPU for 1 ms — a loaded runner, a GC pause that stops it while wall time passes — the
steady wait ends and the clock steps under a thread that is about to run.

What would refute it: deviating runs in which no flow thread has a contended monitor enter near the wrong step.
Then the thread was unseen for another reason (a wait in real time, a hop through a platform thread), and the
next measurement is an instrumented one — the architect writes it; do not start it.

## Stage 1 — the measurement (verifier)

Tree: the scratch worktree named in the call, after its whole-reactor run — the cli jar is in

Run these in this order. Each line is one configuration; write each one's output to
