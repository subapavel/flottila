# P2-01 — Postgres WorkQueue wired to async flows (D-075)

Class C. Designer draft approved by the architect 2026-10-28; decisions marked [A]. Read D-075 first.

## Acceptance
- `partitionBy: <key>` on an at-least-once flow names the key of its one `extractKey` step. `FlowBuilder.delivery` compiles
  that step's expression (`language(step).value(xpath, resources)`) into `Function<Envelope, Optional<String>>`; it builds no
  stage and opens no producer. `partitionBy` on sync / at-most-once flows has no effect [A].
- `Delivery.atLeastOnce(admission, flow, ingress, partitionKey, store, queue, timer, saveTimeout)`; the old 7-arg form passes
  `e -> Optional.empty()`. The key is evaluated on the caller's virtual thread on the envelope as it arrived, inside the
  saveTimeout window, before persist and record start, and goes to `enqueue(id, flow, 1, key)`.
- Key outcomes: value → key; none or "" → null (unordered); > 256 chars (`Delivery.MAX_PARTITION_KEY_CHARS`) → final Nack
  (400), nothing saved; a `Fault` MALFORMED/INVALID → saved unkeyed, 202; any other throwable → retryable Nack, nothing saved.
  The Delivery javadoc's "none has run at the save" is restated (D-075 supersedes D-049 b).
- Build refusals (IAE → existing "does not build" 422 line), at-least-once flows only: no extractKey step for the key; two
  such steps; a WHOLE-body language with maxBodyBytes > treeLimit; [A] a `split` or `to` step before that extractKey.
- `queue` read in the Deployments flow-validation loop: absent/`postgres` = today's PgWorkQueue (Node.java unchanged);
  `kafka` → "flow 'x' sets delivery.queue kafka: the Kafka hand-over is not built yet (Phase 2, later); omit it or use
  postgres"; `queue` on a sync or at-most-once flow → "... only an at-least-once flow has a work queue".
- `WorkerPolicy(lease, maxAttempts, pollInterval, int maxChain)`; 3-arg constructor = maxChain 32; maxChain ≥ 0; 0 = off;
  DEFAULT (30 s, 5, 1 s, 32).
- FlowWorker fast path when verdict COMPLETE, `item.partitionKey() != null`, not stopped, chain < maxChain: settle calls
  `completeAndTakeNext(seq, token, workerId, policy.lease())`. `done(next)`: under the lock `running` swaps seq for next (one
  slot, room unchanged), a new Lease renews, `process(next, chain+1)` runs on a fresh virtual thread. `done(empty)` ends the
  chain; STALE = one WARNING, `staleSettles` +1, nothing taken; a failed future fails the round. Otherwise settle as today.
  A next item past maxAttempts is parked by the existing verdict path. The poll after an item moves to the chain's end;
  `poll()`'s future and `close()` wait for the chains they started.
- [A] A failed keyed item parks and its key continues; XI block-by-default lands with the XI QoS row.
- flow.schema.json: only the descriptions of `partitionBy` and `queue` change. Docs (ARCHITECTURE §7/§14, D-075) are done.
