# FIX-146 — six completed tasks have no entry in the journal

Class **[A]**. Mechanical, but it edits the one file `docs/WORKFLOW.md` calls append-only, so the
care goes into *not* disturbing what is already there.

## The defect

`docs/WORKFLOW.md:48` names **`PROGRESS.md` at the repo root** as the journal: append-only, one
entry per task, newest at the bottom, 1486 lines today.

There is a second file, **`docs/PROGRESS.md`**: 56 lines, written newest-at-the-**top**, last
touched 2026-11-02 and never since. It holds six entries whose ids appear nowhere in the journal:

| id | commit |
| --- | --- |
| FIX-111 | 6f069a4 |
| WF-1 | b86678e |
| P2-08b | ecb721a |
| P2-02L | a326f1b |
| P2-02D | f8a28b9 |
| P2-05 | 84b47f0 |

All six commits are real and land between 2026-10-29 and 2026-11-02, so for four days some session
appended to the wrong path. The descending order is the tell that it never read the journal it was
supposed to be writing to.

Two consequences, and the second is why this is a row rather than a tidy-up: six completed tasks
have no entry in the record that `docs/WORKFLOW.md` §2 and CLAUDE.md both treat as the project's
evidence; and a reader who greps for PROGRESS finds two files, cannot tell from the names which is
current, and the stray one's **top** entry reads as the project's latest state.

## What to do

Fold all six into the journal at their **chronological positions**, delete the stray file.

### Reconstructing an entry

Each entry is rebuilt from its commit — `git show --stat <sha>` and the commit message — and
reformatted to §2's format and the 15-line limit (the limit includes the `##` heading line).

**Read `docs/WORKFLOW.md` §2 for the format, and read the two newest entries in `PROGRESS.md` as
working models.** The stray entries are in a different format and a different order; do not carry
their shape across.

**Invent nothing.** This is the whole risk of the task. The stray entries may claim a check whose
output no longer exists, and a commit message is not an observation. Where an entry would state a
build, test, coverage or benchmark result that cannot be recovered from the commit itself, write
`NOT_RUN` and say the evidence was not recoverable. An entry that reads thinner than its
neighbours is the correct outcome; a fabricated green is not. If the stray entry asserts something
the commit contradicts, keep the commit and note the discrepancy in one line.

### Not disturbing the journal

- **Insertion only.** Do not reword, reorder, reformat or re-wrap a single existing entry. The
  journal is append-only by `docs/WORKFLOW.md:48`; the chronological insert is the one exception
  this row buys, and it buys nothing else.
- Prove it: `git diff PROGRESS.md` must show **only added lines** — no deletions, no modifications.
  Say so with the `--numstat` figures, and if a single line shows as changed, find out why before
  going further.
- The journal's entry count must rise by **exactly six**. Count `^## ` before and after, and report
  both numbers.
- Each new entry **≤15 lines including its heading**. Measure every one with a script that prints
  the count before you write it; do not eyeball it.

### The two questions the row asks

1. Did `agent/NOTES.md`, `agent/HANDOFF.md` or anything else ever point at `docs/PROGRESS.md`?
   `grep -rn 'docs/PROGRESS'` across the repo must end at **0 hits**. If a file does reference it,
   fix that reference rather than leaving a dangling path.
2. **Could `ci/ledger_check.py` have caught this?** Read it. If a one-line check would have — a
   journal at exactly one path, or no `^## ` heading outside the journal — **add it in this task**
   and say what it now rejects. If it would have taken more than a line, do not build it: report
   what the check would need and leave it for a row of its own. Either way, say which.

## Allowed paths

- `PROGRESS.md` (insertions only)
- `docs/PROGRESS.md` (deleted — with `git rm`, so the deletion is in the diff)
- `ci/ledger_check.py` (only if question 2's answer is a one-line check)
- `agent/NOTES.md` or `agent/HANDOFF.md` only if question 1 finds a reference to repair

Nothing under `src/`. No test. No Maven.

## Evidence

No code changes, so the build is **`NOT_RUN` and must be reported that way** — do not invent a
green. The evidence for this task is counts and greps, each quoted as observed output:

- `^## ` headings in `PROGRESS.md` before and after, and the difference
- `git diff --numstat PROGRESS.md` showing insertions only
- the per-entry line counts, all ≤15
- `grep -rn 'docs/PROGRESS'` → 0 hits
- `git status --porcelain -uall` showing the staged deletion and no `??`

## Note for the reviewer

The thing to be sceptical about is **fabrication**, not formatting. Six entries are being written
today for work done two weeks ago by sessions whose context is gone. Pick at least two entries and
check every factual claim in them against the commit they name — particularly any test name, any
count and any assertion of a passing check. A claim that cannot be traced to the commit or to a log
on disk is a defect even if it is probably true.

Second: confirm from `git diff --numstat` that no existing entry moved. The journal's integrity
matters more than whether the six new entries are elegant.
