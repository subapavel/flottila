## FIX-59 — `FLOTTILA_S3_PREFIX` is not validated

`NodeConfig.java:1017` still takes the env value as-is:
`env.getOrDefault("FLOTTILA_S3_PREFIX", "flottila")`. Keys are built as
`<prefix>/archives/<sha256>.zip` (javadoc `NodeConfig.java:553`), so an empty prefix, a leading `/`
or a trailing `/` produces an odd object key (`//archives/…`, `/archives/…`).

### Acceptance 59
`NodeConfigTest` refuses each of these values of `FLOTTILA_S3_PREFIX`, and the refusal message names
the key `FLOTTILA_S3_PREFIX` and shows the offending value:

- `""` (empty), `"   "` (blank), `"/flottila"` (leading slash), `"flottila/"` (trailing slash), `"/"`

A prefix with an inner slash (`"a/b"`) is accepted — only the ends are wrong. The default (variable
unset) stays `flottila` and stays accepted.

The refusal uses the mechanism `NodeConfig` already has: an `IllegalArgumentException` naming the
env key and the value, as at `:120`, `:128`, `:138`, `:149`, `:670`. Do not invent a second style.

## FIX-60 — `ArchiveStore.fetch` has no size bound

`ArchiveStore.java:27` declares `void fetch(String sha256, Path target) throws IOException` with no
bound. `Deployments.restore()` writes whatever the object holds into the data dir and only then
compares the sha256, so a wrong or hostile object fills the disk before it is rejected.

### Acceptance 60
Both implementations take a maximum size at construction and refuse a fetch whose source exceeds it.

- The cap is a `long`, passed in, never defaulted to unlimited. Its value at the call sites is
  `config.maxPackageBytes()` (`NodeConfig.java:44`, `:92`).
- A new case in `ArchiveStoreContract` (`flottila-runtime/src/test/java/io/flottila/runtime/deploy/ArchiveStoreContract.java:31`,
  the suite both implementations run): an object whose bytes exceed the cap is refused with an
  `IOException` whose message names the cap and the actual or allowed size, and **the target file
  does not exist afterwards** — no partial file is left behind.
- An object exactly at the cap is fetched normally. The existing contract cases keep passing
  unchanged.
- The refusal happens while streaming, not after the whole object is on disk. The test can only
  prove the target is absent, so prefer a source comfortably larger than the cap, so a
  whole-then-check implementation would show in the test's own disk use.
- The contract suite needs the cap: add one `protected abstract long cap()` (or an equivalent single
  hook) next to the existing `emptyStore()` (`:39`) and `keyOf()` (`:42`), and have each subclass
  build its store with it. Keep the change to the suite that small.

## Architect's rulings, carried from FIX-59-60.md and still binding

1. **Replace the constructors, do not overload them.** Today they are
   `DirArchiveStore(Path dir)` (`DirArchiveStore.java:20`) and
   `S3ArchiveStore(S3Client client, String bucket, String prefix)` (`S3ArchiveStore.java:34`).
   They become `DirArchiveStore(Path dir, long maxBytes)` and
   `S3ArchiveStore(S3Client client, String bucket, String prefix, long maxBytes)`. An overload
   without a cap is a limit defaulted to unlimited, which CLAUDE.md forbids; an overload with a
   built-in default cap hides the limit at the call site, which is the same fault one step further
   away. Every construction site states its cap.
2. **The implementer updates every existing construction site.** Measured on this tree there are 22:
   3 in `src/main` — `Node.java:296`, `Node.java:301`, `Deployments.java:255` — and 19 in tests:
   `AdminServerTargetsTest:106`, `AdminServerDeployTest:747`, `:955`, `:1041`,
   `DeploymentsListenerTest:111`, `:414`, `:438`, `DeploymentsFenceTest:71`,
   `DeploymentsSecretsTest:516`, `:550`, `S3ArchiveStoreTest:42`, `DeploymentsDedupeTest:80`,
   `DeploymentsPollerLeaseTest:103`, `S3ArchiveStoreIT:74`, `:121`, `:135`,
   `DeploymentsListenerEdgeTest:92`, `Shelf.java:33`, `DeploymentsRestoreGuardTest:57`,
   `DeploymentsTargetsTest:128`, `DirArchiveStoreTest:27`.
   This is mechanical: add the cap argument, change no expectation. It is explicitly authorised
   here, so it is not a breach of "the implementer may not change a test it did not write". **If
   any of those sites needs more than a new argument, stop and say so in the hand-back instead of
   reinterpreting the test.** The count is 22 as measured; if you find more, report the number.
3. **Refuse while streaming.** The test can only prove the target is absent afterwards, so the
   obligation is on the implementation: count bytes as they are copied and fail as soon as the count
   passes the cap. Do not write the whole object and check its size. Delete any partial or temporary
   file on the failing path.
4. The `IOException` message names the cap and the offending size, in the voice the deploy code
   already uses for refusals.

## The trap in this module, paid for once

Do **not** pass `-Dtest=` to `flottila-runtime`. Its pom has a second surefire execution
`heap-bounded` with `<includes>**/*HeapTest.java</includes>` and `-Xmx48m`; `-Dtest=` overrides those
includes and forces big classes into the 48 MB fork, which OOMs and proves nothing. Run the whole
module's test phase instead, and expect it to take several minutes.
