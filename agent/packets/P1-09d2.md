# P1-09d2 — Redeploy (F-5, D-060 c, D-063). Designer draft 2026-10-27, approved by the architect with the decisions below.

## Architect decisions
- Split: **P1-09d2a** (building blocks: StepResources `reads` sink, `FlowBuilder.reads`, `WorkQueue.hasItems`, `FlowHash`, `hash`/`state` in `/admin/flows` on the first deploy); **P1-09d2b** (redeploy happy path: classify, two-phase swap with barrier, added/removed/unchanged, 422 for removed or mode-changed at-least-once flows with items, drain recheck WARNING, dir reuse and pruning, 200 `added/swapped/removed`, NodeIT); **P1-09d2c** (failed start: rollback from the kept dir, FAILED state, 500 `{error, problems}`, the next deploy restarts a FAILED flow, `consumer.start()` bounded by stopDeadline).
- Open (1) a version bump alone does not restamp unchanged flows. (2) yes, in d2c. (3) `/health` for FAILED flows → P1-09c. (4) FIX-32 folded into d2b (the cleanup `finally` keeps the refusal, cleanup failure suppressed). (5) accepted: while v1 drains a swapped flow runs up to 2× its worker max; documented in D-063. (6) P1-09e is covered by d2b's `oldWorkerItemsFinishOnOldProducersThenClose`; P1-09e closes with d2b.
- Conflicts: F-5 amended and §9 changelog line with d2b (window ≤ the slowest stop); D-057 b retention "current + previous + dirs in use" (D-063); XSLT run-time `doc()`/`unparsed-text()` reads are neither confined nor hashed → F-9 (task: a later row; d2a documents the gap); D-059 500 body gains `problems` (d2c).

## Designer draft (verbatim)
P1-09d2 design draft (designer, 2026-10-27). Read: CLAUDE.md, AGENTS.md, BACKLOG rows d1b/d2/09e/c, F-5, D-057/059/060/062, ARCH §9 + changelog, packet d1, deploy/*, AdminServer, FlowBuilder, FlowDefinition, FlowWorker, Delivery, PgWorkQueue, StepResources, xslt CompileConfinement.
1. PROPOSAL
- api `StepResources` gets an 8th component, `java.util.function.Consumer<Path> reads`. The 7-arg constructor delegates with a no-op. `file()` and `resolve()` report each confined path they return. The xslt and xsd steps already read everything through these two methods (D-052), xsl:include and xs:import included.
- core: `FlowBuilder reads(java.util.function.Consumer<Path>)` (replaces the earlier sink). `WorkQueue.Future<Boolean> hasItems(String flow)` is true for any row of the flow: due, backing off, leased or held. Pg: `select exists(select 1 from work where flow=$1)` on the existing index work_flow_seq (completed rows are deleted).
- Effective hash: package-private runtime `FlowHash`, computed in Deployments right after a flow's delivery and worker are built. It is `sha256:<hex>` over these UTF-8 lines:
  - `flottila-flow-hash 1`;
  - `yaml <path> <sha>` (raw bytes);
  - `file <path> <sha>` for each file the build reported (package-relative, sorted);
  - `endpoint <id> <scheme> <options as JSON with sorted keys>` for `from` (including `flow` and `maxBodyBytes`) and every `referencedEndpoints()`, with this env's overlay applied.
  - Left out: package.yaml, version, revision, other environments' overlays, files no build read.
- `DeployedFlow` gains `hash` and `State state {RUNNING, FAILED}`; `/admin/flows` items gain both. `deploy` returns `DeployResult(DeployedPackage pkg, List<String> added, swapped, removed)`, and the 200 body gains `added`, `swapped` and `removed` (sorted, qualified ids).
- Order:
  - The prechecks stay as they are, minus the 409 for a name already deployed.
  - Unpack. A target `<sha>` dir that is a kept dir is reused and the fresh unpack dropped. Today's `deleteTree(dir)` would delete the running version's dir.
  - Load and check. Extra problem: a running at-least-once flow that v2 removes or makes non-at-least-once while its `hasItems` is true. It joins the same 422 and nothing stops.
  - Build delivery and worker for every v2 flow, then hash each.
  - Classify each flow: added (new id, or running FAILED), unchanged (same hash), changed, removed.
  - Unchanged: the new build is stopped with zero deadline and closed, and no consumer is built. The running objects and DeployedFlow stay untouched and keep their build-time `package`/`revision` stamps.
  - Consumers are built only for added and changed flows; a build failure there is 422.
- Swap, under the node-wide lock:
  - Phase A, every changed and removed flow in parallel: `worker.stop()`; `join(delivery.stop(stopDeadline), consumer.stop())`; `delivery.close()` awaited; `worker.close()` called but not awaited (FIX-30).
  - Phase B, only after all of A has settled, every changed and added flow in parallel: `consumer.start()`, then `worker.start()`.
  - A removed at-least-once flow is checked with `hasItems` again once its `worker.close()` completes (drained). Items still there are a WARNING naming the flow; this never delays the answer.
- Success:
  - The package record is replaced (version, revision, sha, files, deployedAt).
  - Pruning keeps the current dir, the previous dir, and any dir a running flow was built from. A failed delete is a WARNING.
- Failure in B:
  - v2 flows that started are stopped with stopDeadline, the rest with zero deadline; all are closed.
  - Changed and removed flows are rebuilt from the running version's kept dir with its version stamps, through the same two phases.
  - A flow whose rebuild or start fails is FAILED (no objects). The package record is unchanged and the new dir is deleted unless kept.
  - 500 `{error, problems}`: "version X did not start; Y runs again", or the same with "flows [..] FAILED".
  - The next deploy treats a FAILED flow as added, so re-PUTting the same archive restarts it: dir reused, nothing stops, only revision and deployedAt change.
- In flight during a swap:
  - Sync requests finish on v1 within stopDeadline, else 503 + Retry-After (D-056). New connections in the window are refused.
  - An at-least-once save in flight gets 202, or a retryable Nack at the deadline.
  - Queued items run on v2 (D-057). Items v1's worker already claimed finish on v1 and its producers, renewing their leases; then those producers close. This covers P1-09e.
  - Per-key order holds: a leased row blocks its key for every worker (ELIGIBLE).
  - Held rows stay held and run on v2 after release (P1-09c).
- Concurrency: one deploy at a time per node (tryLock, else 409). It is not per package because the barrier, the P1-09g cross-package port check and `close()` need one view.

3. REJECTED
- Static reference scan of the yaml: misses includes and imports, so a fix would silently not take effect.
- Hashing the flow's whole dir: flows share `flows/`, so it breaks "only its readers".
- A `StepFactory.files()` SPI: misses transitive files.
- A per-flow parallel swap without the barrier: a renamed flow on the same port is shared by Vert.x (the round-robin F-5 rules out).
- Restamping unchanged flows (needs a swap or a mutable holder).
- A per-package lock.
- A same-sha no-op shortcut: it would skip FAILED flows.
- Awaiting the old worker's drain before answering: minutes with backoff.
4. EXPENSIVE TO REVERSE (draft — review at hand-over)
- The StepResources component (api).
- `WorkQueue.hasItems` (two implementations).
- The hash's lines and `sha256:` format (P1-09c may persist it).
- JSON: `hash`/`state` in `/admin/flows`, `added`/`swapped`/`removed` in 200, `problems` in 500.
- Disk retention rule.
- Unchanged flows keep their build-time message pins.
5. CONFLICTS
- F-5 and changelog 3.4 §9 say "per-flow window": the barrier makes the window as long as the slowest stop (≤ stopDeadline). Needs an F-5 amendment and a changelog line.
- D-057 b says "current + previous kept"; this keeps "+ dirs in use" as well.
- D-060 c vs D-052: XSLT run-time `doc()`/`unparsed-text()` on relative URIs goes to Saxon's own resolver. It reads the build dir unconfined and is not in the hash (CompileConfinement:67), so a changed lookup file never swaps. Needs a new finding.
- §9 "pins the commit on every message": unchanged flows pin the revision they were built from.
- D-059: the 500 body was `{error}`.
- D-058: the recheck happens after the drain, not right after stop.
6. OPEN (recommendation)
- (1) Should a version bump alone change the stamps? Recommend no: the pin is honest, and the flows list shows the build version.
- (2) Bound `consumer.start()` by stopDeadline in d2b? Recommend yes: a timed-out start counts as failed, and a late success is followed by stop. Otherwise a stuck start holds the lock forever (FIX-34).
- (3) `/health` for FAILED flows: P1-09c, same rule as a failed restore.
- (4) Fold FIX-32 into d2b (same cleanup finally)? Recommend yes.
- (5) While v1 drains, the node transiently runs up to 2× the worker max for that flow. Recommend accepting it and documenting it.
- (6) Mark P1-09e covered by d2b?
SPLIT: recommended.
- d2a [C] building blocks: the sink, `hasItems`, the hash, `hash`/`state` on the first deploy. Acceptance: the d2a tests green, and an included XSL changes the hash.
- d2b [C] (depends on d2a): redeploy in Deployments, AdminServer and NodeIT. Acceptance: the row's done-when.
- If d2b's red list goes past about 20 cases, cut rollback/FAILED into d2c.
