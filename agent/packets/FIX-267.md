# FIX-267 - the operator's events on a message: cancel, and the record of a retry (class C)

Row: `grep -n "^| FIX-267 " agent/BACKLOG.md`. Decision D-156, finding `docs/findings/F-55.md`: replay is not part of
Rail8; a message keeps one id; a failed message is retried under that id (`POST /admin/dlq/{id}/retry`) or cancelled.
Cancel does not exist. `/retry` takes no actor and writes no record. There is no message log (OPS-2, pending).
This row is a design: the designer's draft, the advisor's opposition, the architect's decision, a finding with the
ARCHITECTURE change, and the implementation rows. No code in this row.

## The owner's word so far (read first)

- D-156 (`docs/DECISIONS.md`), F-55 - in particular "The operator's hole until cancel exists, stated exactly".
- `issues/ISSUE-10.md` items 2 and 3, not answered; their defaults hold and the design rests on them:
  item 2 - a cancelled message counts as a failure of its flow; item 3 - cancel covers the failed list only, and a

## What the design must answer

1. The route, its inputs (actor, reason - required by item 3's default) and every answer it gives, with status codes:
   the cancel itself; an id that is not in the failed list; an id already cancelled; a second cancel; a `/retry`
   after a cancel (a refusal that names the cancel, not today's 404); a cancel racing a `/retry` (one wins, the other
   gets a plain answer; the lock is the restart statement's row lock).
2. Cancel works for every row `/retry` refuses (F-55 lists them): a flow redeployed in another mode, a flow not
   deployed on the node, a lost body, a park that is not the worker's step-1 park, a keyed row parked without its
   key (before V17, or - found by FIX-263's test-author - a keyed flow's message parked before its key was kept).
   So it needs neither the deployed flow nor the body. Say on which node it may run (any member? the one holding the
   journal copy?) and why.
3. The record's home, one persisted shape for both events - who did what to a message, when, why. Weigh at least:
   (a) one audited delete like the work queue's discard - the state is read from the `audit` row, no new table;
   (b) a marker on the message (its status or a row in the message's history) plus the audit row;
   (c) a lifecycle or events table of its own.
   For each: what the message's timeline and the failed list show afterwards; what `/retry`'s refusal reads; what
   retention does with the message, its bodies and refs after a cancel (today retention never removes what a DLQ row
   names); what it costs in writes (operator path only - nothing per message on the hot path); how it meets OPS-2's
   message log when that exists; what an upgrade of persisted data looks like.
4. The record of a retry: where the actor comes from, what is written, in which transaction with the restart
   statement, and what the timeline shows (the retry's attempt already gets its own row, D-140).
5. What a cancelled message is in the message store's terms (a terminal state? which one - failed, as item 2's
   default says?) and in the counts an operator sees. A sync message has no DLQ row: say what cancel answers for it.
6. Whether `Dlq.remove` stays (its only main caller is `Replay.replayParked`, which FIX-264 removes).
7. What is expensive to reverse (a persisted format, a public route, a status name) - named, to be marked
   `draft - review at hand-over`; and what is the owner's to decide - as questions with defaults, not as blockers.
8. The implementation rows, in order, each with its red test in one sentence and its class.
