# FIX-140 — recording must not replace the throwable it is about to rethrow

Class B. Depends on FIX-133 (done, 9a9c916). Found by the FIX-133 reviewer as non-blocking; the
premise was then verified in the code by the architect, and that verification narrowed the task.

## The defect

`Recorder.java:85-90` catches, records, and only then rethrows:

    } catch (Throwable failure) {
        if (!handedOn[0] && policy.records(step.index(), last, Snapshot.Outcome.FAILED)) {
            record(e, step, Snapshot.Outcome.FAILED, failure.toString(), started, cpu0, policy);
        }
        throw failure;
    }

If `record(...)` throws, the catch block leaves with the RECORDING's failure and the original
throwable is lost. D-111 promises the opposite — "write the `FAILED` row, rethrow unchanged" — and is
now qualified to say that holds only when recording succeeds.

For an `Error` this is worse than a swapped exception. The replacement is an `Exception`, and
`Parking.java:49` catches `Exception`, so it would PARK it: an `Error` would become transient, which
is exactly what D-098 refused and what D-111 explicitly leaves standing. FIX-133 did not create the
risk — it existed for an `Exception` — it changed the consequence, by sending `Error`s through
`record` for the first time.

## What CANNOT reproduce it, so nobody spends a round there

**A throwing `MessageStore` will not do it.** `Trail.flush()` ends with
`.transform(settled -> Future.<Void>succeededFuture())`, and `Trail.close()` states it outright with
the comment "no flush ever fails". A store's own failure never surfaces to the caller. Verified in
the code by the architect, not inferred from the comment.

The two real triggers:

- **(a) `failure.toString()` at `:88` throws.** A `Throwable` subclass whose `toString` throws tests
  this in a few lines and needs nothing else. It is enough to pin the fix, and it is the trigger the
  red test should use.
- **(b) An interrupt while `Trail.add:90` awaits a flush.** That line is `if (full) flush().await()`,
  and `full` means more than `FLUSH_AT` = 256 rows buffered. An `await` on an interrupted virtual
  thread throws `InterruptedException` sneakily (D-056, the stop-deadline cancel). This is the
  realistic production cause but the expensive one to stage. Attempt it only if (a) is already green;
  if it needs more than a simple fixture, say so in the hand-back and leave it — do NOT weaken (a) to
  make room for it.

## The shape (implementer)

Wrap the `record` call in its own try. On a failure, attach it to the original with `addSuppressed`
and rethrow the original unchanged:

- the original throwable is what leaves `wrap`, always, `assertSame`-identical;
- the recording failure is reachable via `getSuppressed()`, never discarded;
- no control flow moves, exactly as in FIX-133: the guards, the row's contents and the rethrow stay.

Watch two JDK details: `addSuppressed` throws if you pass the throwable to itself, and it is a no-op
when suppression was disabled by the two-arg `Throwable` constructor. Neither may turn into a second
failure inside the catch — a failure in the salvage path would reintroduce the very defect.

**One decision, made here so the packet does not ask for it twice.** A `FAILED` row that was never
written is a lost row, and monitoring is the product, so the recording failure is ALSO logged once at
`WARNING` with the message id and the step. Not a counter and not once-per-writer (D-104's shape is
for a shared writer; this is per message). The flood is bounded by the number of in-flight messages,
because trigger (b) arrives with a stop that interrupts each of them once, and a stop that loses rows
for every in-flight message is an incident an operator must see rather than a line to suppress.

## Red tests (test-author, before any production change)

In `flottila-core/src/test/java/io/flottila/core/record/RecorderTest.java`, as NEW methods. Reuse the
existing fixtures and the `CountingStore` from FIX-133 where useful; do not edit
`aCancelledStepRecordsItsFailureSnapshot`, its `Map<String, Exception>`, `sneaky`, or FIX-133's four
cases.

1. `aRecordingThatThrowsStillLetsTheOriginalErrorEscapeUnchanged` — a step throws an `AssertionError`;
   recording fails through trigger (a). The escaping throwable is `assertSame` the `AssertionError`,
   and the recording failure is among its `getSuppressed()`. This is the case that fails today.
2. `aRecordingThatThrowsIsLoggedOnceWithTheMessageAndStep` — the `WARNING` is captured and names both.
   Follow `TrailTest`'s log-capture style; FIX-123 and FIX-130 pinned the sentence shape there.
3. `aFailureWhoseToStringThrowsStillLeavesARowOrNoneButNeverADifferentThrowable` — state and assert
   what the row does in that case. Decide it from the code and say which you chose in the hand-back:
   either no row (the text could not be built) or a row with a placeholder text. Do NOT invent a
   third behaviour in production to make a test pretty — that is the implementer's line to hold.

Report honestly which cases were red. If one is green against today's code, name the assertion that
would fail if the fix were reverted, or replace it — a test that cannot fail is worth nothing, and
FIX-133 lost two rounds to exactly that.
