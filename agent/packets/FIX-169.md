# FIX-169 — Postgres 18 as the test image, one source for the version (owner 2026-11-11) [B]

## Today
98 test classes in flottila-runtime name `postgres:17` (most `postgres:17` bare, some pinned) as a literal; deploy/compose
pins `postgres:17.11`; the root quickstart docker-compose.yml runs `postgres:16`. PG 18 is the current release (2025-09);
PG 19 is RC, GA planned 2026-11-19. Nothing was ever run on 18. D-128: ha needs PG ≥ 17 (4-arg pg_logical_emit_message).

## Decision (architect, D-129 reversible)
- V1 One source: a testkit constant (e.g. `io.flottila.testkit.PostgresImage.NAME`) = `postgres:18.<patch>` pinned to the
  newest 18 patch tag that exists (verified by pulling it, never from memory), overridable by the system property
  `flottila.it.postgres` (a full image name) so CI can run the same suite on another version. Every Testcontainers
  Postgres in every module goes through it; no other `postgres:<digit>` literal in any test or main source.
- V2 Compose: deploy/compose and the root quickstart use the same pinned tag. The PG 18 image keeps its data under
  /var/lib/postgresql/18/docker and expects the volume at /var/lib/postgresql — mount accordingly (verify on the image).
- V3 Supported versions: 17 and 18. CI keeps 17 as the floor with one extra run of the -Pit suite under
  `-Dflottila.it.postgres=postgres:17.11` (or the newest 17 patch). 19 is added after its GA as row FIX-169b (no RC images).
- V4 Production changes only if something fails on 18; a contradiction with ARCHITECTURE → finding first.
- V5 Docs: ARCHITECTURE (where PostgreSQL is introduced / §4 profiles) states supported versions 17–18, tested main 18,
  ha ≥ 17; changelog row; D-129; NOTES/QUICKSTART if they name a version.
