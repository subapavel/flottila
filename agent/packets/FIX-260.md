## The reading (from the code and the two logs; the red confirms it or you hand back)

- The message is the Vert.x SQL pool's: a caller's wait for a pooled connection elapsed. No production source holds the
  text. `RAIL8_PG_POOL_WAIT` becomes `PoolOptions.setConnectionTimeout` on the node's two pools, intake and work
  (`Node.java:233-234`, `:419-422`); the case starts its node under PT0.2S (`NodePoolWaitIT.java:388`). The test's own
  `observer` pool sets no wait and `lock()` is a plain connection.
- Only one call of the case hands a `VertxException` to the test thread as itself: `Node.start`, through
  `OnVirtualThread.call` (`startNode`, :186-195). The deploy is HTTP — a refusal there is a 503 or an `AssertionError`.
- A pool connects on its first statement (`Node.java:227`). The first pooled statement of a start is the durability
  check on the intake pool (`Node.java:263`), before the migration (:264) and before the start's notices.
- The job log agrees. In the class's window the failing run shows 11 node starts that printed their notices and 12
  Flyway runs; the green run here (`agent/work/MAIN-1-run3.log`, the class's section) shows 12 and 13. One Flyway run in
  each is a test's own, on thread `main`. So the failing run lacks one whole node start — no migration, no notice:
  that start failed at or before the durability check, and the case ran its 0.53 s without printing a line.
- The fixture knows the exposure: `warmUp` (:132-136) starts one node per JVM under the default wait because "the first
  node a JVM starts took 140 to 380 ms for its first pooled statement (the wait covers the connect)". Every later node
  still opens new connections under the 0.2 s.

Not shown: what made that connect take longer than 0.2 s on the runner. The product's behaviour is the designed one
(a caller waits at most the wait, the connect included; the default is PT5S); nothing under `src/main` changes.

## What the first attempt measured (test-author, 2026-11-15)

Logs, in the worktree: `agent/work/FIX-260-red.log`, `agent/work/FIX-260-diag.log`.

The reading holds: with the node's first connect held by a `PgWire` relay, the start under PT0.2S is refused after 219 ms
with `io.vertx.core.VertxException: Timeout waiting for connection` — the sighting's text, from
`io.vertx.sqlclient.impl.pool.SqlConnectionPool` (vertx-sql-client 5.1.10, javap).

The staging the packet first asked for cannot be a case: a refused start does not return while its connect is pending.
The failure path of `Node.start` (:351-382) ends in `closeStores`, whose `intake.close().await()` (:599) waits for the
connect in progress; the start throws only once the connect ends. On the runner the connect was slow and then finished.
Releasing the held connect "after the refusal and before the start returns" has no observable trigger — the node logs
nothing on that path and nothing goes over the wire. That is a fault of the product's start, not of this fixture:
row FIX-261 (a refused start says what was refused before it closes anything, and returns within a bound while a
connect is pending); the node-level case moves there, where the start's own report is its trigger.

A refused start leaves nothing that changes a second start: before the durability check (`Node.java:263`) no port is
bound, no component started and no statement has reached Postgres; the data directory is untouched with a key given by
value, as this class gives it (a generated key's file is created by the first load and read back by the second); the
failure path closes both pools. A start refused at a later pooled statement has opened more, and its failure path
closes it; starting again on the same data directory is then the product's ordinary restart.
