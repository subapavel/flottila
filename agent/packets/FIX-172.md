# FIX-172 — finite wait for a pooled Postgres connection (class B)

Row: agent/BACKLOG.md FIX-172. CLAUDE.md: every limit finite, never unlimited. CORE-17 O2 left the client defaults.

Facts (javap vertx-sql-client 5.1.10; scout):
- `PoolOptions.DEFAULT_MAX_WAIT_QUEUE_SIZE = -1` (unbounded), `DEFAULT_CONNECTION_TIMEOUT = 30` s (wait for a pooled connection).
- Node.java:218/:219 sets only `setMaxSize` on the intake and work PoolOptions.
- A pool error today: intake save → 500 (not a Fault, HttpComponent.java:218-234); admin read → 500 (AdminServer.java:476-478);
  claim → WARNING, next poll tick (FlowWorker.java:342-353); sweeper/retention/NOTIFY log and continue.

## Decision
P1 Two keys, read by NodeConfig.from, carried on `NodeConfig.Pg` (last components, in-process ctors take the defaults):
  - `FLOTTILA_PG_POOL_WAIT` — the longest wait for a pooled connection, ISO-8601 duration, PT0.001S..PT1M, default PT5S
    (the save timeout is 5 s, ARCHITECTURE §4 table).
  - `FLOTTILA_PG_POOL_QUEUE` — the most callers waiting per pool, 1..65536, default 1024.
  Refused at start naming the key: not parseable, or outside its range. Both apply to the intake and the work pool.
P2 Node sets `setConnectionTimeout` (+ unit) and `setMaxWaitQueueSize` on both PoolOptions from these values. Membership and
  LISTEN connections are not pooled and are unchanged.
P3 A refused waiter (wait elapsed or queue full) is retryable backpressure (D-082):
  - intake: the POST is answered 503 (retryable), never 500, and nothing is saved; the members of the group all get it.
  - admin read: 503 with the usual error body, never 500.
  - worker claim: the worker keeps running and claims on a later tick once the pool frees (today's behaviour; pinned).
  - park/complete/sweeper/retention/NOTIFY: unchanged (log and continue; the lease/reconcile covers them) — not pinned here.
  How a pool refusal is recognised is the implementer's choice, from the client's exception type checked with javap,
  never from a message string.
P4 Docs: ARCHITECTURE §4 "Postgres pools by role" sentence "stay at the client's defaults (FIX-172)" → the two keys and
  their defaults; DECISIONS row D-132 (reversible); changelog row 3.10.

## Acceptance (red first, test-author)
A1 NodeConfig: defaults PT5S / 1024 when unset; bounds accepted at both ends; each key refused below/above/unparseable,
   the message naming the key; in-process `Pg` ctors carry the defaults.
A2 IT, intake: a node with a short wait (e.g. FLOTTILA_PG_POOL_WAIT PT0.2S) and every intake connection held busy
   → a POST answers 503 well before the 5 s save timeout, the message is not in the store; after release a POST is 202.
A3 IT, admin: work pool held busy, short wait → an admin read answers 503, not 500.
A4 IT, worker: work pool held busy past the wait → the worker survives and completes the queued item after release.
A5 the queue bound is applied: a pool option test or IT showing the (N+1)-th waiter refused at once with a small queue
   (FLOTTILA_PG_POOL_QUEUE 1) — the test-author may pin it through observable behaviour or the built PoolOptions.
No sleep-based timing in assertions; holding connections via locks or open transactions is fine (see NodePoolRolesIT:225).
