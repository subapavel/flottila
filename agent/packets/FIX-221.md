# Packet FIX-221 (class A) — a contract case reads two deliveries in the order of their sends

Rows: `agent/BACKLOG.md` FIX-221 (and FIX-170, the same fault), under MAIN-1. Sightings: once in
four runs here (`agent/work/FIX-213-evidence.txt`, last block), once on a runner — `ci` run 209,

## The fault (the architect's reading of the code — confirm it by the red, or hand back)

`ComponentContractSelfTest.eachBrokenPropertyFailsExactlyItsCases` (:337-339) expects the variant
"acknowledged before the handler answered" (`ackBeforeHandler`) to fail nine named cases. Sometimes
it fails a tenth, `aSendCarriesTheMessageIdToThePartner`.

- The variant's `send` (`ComponentContractSelfTest.java` :238-242) dispatches the handler — on a
  virtual thread of its own (`dispatch`, :193-212) — and returns the envelope at once.
- The contract case (`platform/testkit/src/main/java/dev/rail8/testkit/ComponentContract.java`
  :496-518) sends a plain envelope, then a bounded one, waits for two deliveries and reads
  `seen.get(0)` as the plain one and `seen.get(1)` as the bounded one.
- For a component that answers after its handler the order holds: the first send completes after
  the first delivery. For this variant the two handler threads race; when the second delivery is
  recorded first, the case compares the bounded envelope with the plain id and fails.

The case states what crosses with a send (D-101 (3): the sender's message id, once, a forwarded one
replaced). The order of two deliveries is not its subject, and its verdict for a variant that
carries the ids correctly must not depend on which handler thread ran first.

## Acceptance

1. Red first, deterministic, in `ComponentContractSelfTest`: a variant that carries the ids as the
   correct one does and acknowledges before the handler answered, with the two handler runs of
   this case forced into the opposite order of the sends — the first delivery's handler run is
   held until the second delivery has been recorded (a gate in the variant's handler executor or
   dispatch; no sleep, a bounded wait on a state). Against it the contract case
   `aSendCarriesTheMessageIdToThePartner` fails today. The new self-test case asserts that this
   variant does NOT fail that contract case (it may fail the nine cases the ack-first variant
   fails; assert the exact set). Observed red before the contract case changes.
2. The fix is in the contract case, `ComponentContract.aSendCarriesTheMessageIdToThePartner`: each
   delivery is identified by what it is (its body: `id-plain`, `id-bounded`), not by its position
   in `seen`. Its strength for a correct component is unchanged: exactly two deliveries; the plain
   one carries exactly `contract-plain-1` (the forwarded id replaced); the bounded one carries
   exactly `contract-bounded-2`. A component that drops the id, keeps the forwarded one, or
   carries the other send's id still fails it — the existing self-test expectations that name
   `MESSAGE_ID` (:538 and its uses) stay as they are and stay green.
3. `eachBrokenPropertyFailsExactlyItsCases` keeps every expected set unchanged.
4. Survey, in the hand-back: every other case of `ComponentContract` and of
   `PollingConsumerContract` that reads deliveries by position across more than one send or more
   than one handler run (grep `.get(0)`, `.get(1)`, `getFirst`, `getLast`, and assertions on a
   whole list of deliveries), each with one sentence: why the order is guaranteed for every variant
   the self-tests expect to pass it, or that it has the same fault. A case with the same fault is
   fixed the same way, with its own forced-order red; if there are more than two, fix none beyond
   this one and list them — the architect opens rows.
5. No sleep, no wall-clock assertion, nothing removed or disabled. No change outside
   `platform/testkit/` — `ComponentContract.java` (the one case, and a private helper if needed)
   and `ComponentContractSelfTest.java`. The contract suite's public surface does not change: every
   component's contract test compiles and runs unchanged.

Contract cases and their self-tests are the test-author's; there is no implementer step.
