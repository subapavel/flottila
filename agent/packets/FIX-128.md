# Packet FIX-128 (class A) — a non-zero `warmupFailed` is never exercised

Module: `flottila-bench`, test only. Row: `agent/BACKLOG.md`, FIX-128. Residual of FIX-63, whose
production half is done.

## The defect

`NodeBenchMainIT.java:72` asserts `warmupFailed` is 0. Nothing anywhere drives it non-zero, so the
field could be hard-wired to 0 and the suite would not notice. The value under test is the harness's
`load(...).failed()` at `NodeBenchMain.java:313`, and the record also carries `warmedUp`, which is
meant to be `warmup - warmupFailed`.

Read those two places before writing anything; the line numbers are from an audit on 2026-11-14 and
may have drifted by a line or two, so confirm them rather than trusting them.

## Acceptance

1. A warm-up in which some requests are refused reports that count in the record: the test drives a
   known number of refusals during the warm-up and asserts `warmupFailed` equals exactly that
   number, not merely that it is greater than zero.
2. The arithmetic is asserted in the same case: `warmedUp` equals `warmup - warmupFailed`, with
   `warmupFailed` non-zero, so a mutant that drops the subtraction or returns `warmup` fails.
3. The existing `NodeBenchMainIT.java:72` zero-case keeps passing unchanged. You may not weaken,
   re-expect or delete it — it is the all-succeed case and it stays. If it has to move for the new
   case to exist, stop and hand back why instead of editing it.
4. A mutant that hard-wires `warmupFailed` to 0 fails the new case. Say in the hand-back which
   assertion catches it; run the mutant if you can do so inside the allowed paths, and report
   NOT_RUN with the reason if the only way to try it is to edit production code.

## Red first

The red is the new case against today's code only if the production half really does count
refusals. FIX-63's production half is done, so expect the new case to pass once written. That makes
it a guard, not a red, and the hand-back must say so plainly rather than describing a red that did
not happen. If instead the new case FAILS on today's code, that is a live defect in the counting:
stop, do not fix production code, and hand back the failure with its output.

## How to refuse warm-up requests

Find the mechanism the suite already has — a component or mock whose responses can be made to fail,
or an existing fixture that refuses on demand. Do not add a production seam, a flag, a system
property or a test-only branch in `NodeBenchMain` to make refusals possible. If no existing
mechanism can refuse during warm-up specifically, stop and hand back what you found; the answer is
then a design question for me, not a workaround for you.
