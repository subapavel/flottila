# P1-09f — deploy validates each step's options against `StepFactory.configSchema` (D-057 amendment)

Class B. Architect spec 2026-10-28.

## Acceptance
- `Deployments.check()` (flottila-runtime deploy), next to the endpoint-config check (Deployments.java:748): for every step of
  every flow whose `type` resolves to a `StepFactory` on the node, the step's options (`StepConfig.config`, i.e. the step map
  without the structural keys type/name/retryable) are checked with `Schemas.check(factory.configSchema(), options)`.
- Each schema problem is one line in the 422 `problems` list, shaped like the endpoint lines:
  `flow '<flowId>' step <n> '<name>' (type '<type>') option at '<path>': <message>` (n is 1-based position in `steps`).
  All problems of all steps are collected; the deploy stays atomic (nothing is swapped, D-057).
- [A, after the implementer's handback] A step's `recording` is the platform's key (FlowBuilder consumes it, FlowDefinition
  javadoc :20-21), not a factory option: it is left out of the options checked, like type/name/retryable. A strict factory
  schema (no additional properties) accepts a step that sets `recording`.
- Built-in step types without a factory (to, route, filter, extractKey, validate, split) are not checked here (flow.schema.json
  already types them); an unknown type stays the existing "does not build" problem — no second line for it.
- A factory whose `configSchema()` is not a valid JSON Schema (or not JSON) is one problem line naming the step type, never a
  500 or an exception out of deploy.
- A valid package (packages/demo; DeploymentsTest's PackageDraft baseline) deploys exactly as before.
- No ARCHITECTURE change (§7 already says configSchema is validated at deploy time); no public-type change in flottila-api.

## Red tests (test-author)
- DeploymentsTest.invalidPackages(): new cases, words asserted as in the existing table —
  "a step option its factory's schema refuses" (an xslt-like test factory requiring `stylesheet`, step given `stylesheet: 7`
  or missing it) → 422 naming flow, step name, type and the option path;
  "two bad steps in two flows are both reported" (both lines present);
  "a step factory whose configSchema is not a schema" → 422 naming the type.
- DeploymentsTest: aStepWhoseOptionsMatchItsSchemaDeploys (positive control: the same factory, valid options → deployed).
- AdminServerDeployTest: one case through HTTP — a step option outside its schema → 422 `{error, problems}` with the line.
- Use the test factories already registered in the runtime tests where possible; add a test factory only in test code.
