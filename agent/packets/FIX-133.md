# FIX-133 — a step that throws an Error leaves no row at all

Class B. Decided by D-111 (2026-11-14) **as amended the same day** — read the amendment, not only the
first half of the row. Depends on FIX-71 (done, e835f43).

## The defect

`Recorder.java:85` catches `Exception`. A stage that throws an `Error` therefore propagates with **no
row written at all**, and the message's timeline shows that step as one that never ran. Measured:
`RedeliveredTimelineTest` case 2 produces steps 0-7 all `OK` for a message whose first run crashed,
indistinguishable from one clean successful run. Monitoring is the product, so a failure the timeline
cannot show is a product defect.

## The change (production)

One line, `flottila-core/src/main/java/io/flottila/core/record/Recorder.java:85`:

    } catch (Exception failure) {            // becomes:
    } catch (Throwable failure) {

Extend the existing comment rather than replacing it: it must still say that a checked exception
arrives here sneakily from an interrupted await (D-056), and add that an `Error` is recorded too and
rethrown unchanged (D-111).

**`Throwable`, not `RuntimeException | Error`.** The BACKLOG row's original text said the latter,
copying D-104's form from `BatchingWriter`. That is a **narrowing** here and D-111's amendment
retracts it: `Exception` deliberately catches the checked `InterruptedException` that D-056's
stop-deadline cancel produces, and `RuntimeException | Error` does not include it, so it would delete
the `FAILED` row for every cancelled delivery in order to add one for an `Error`.
`Exception | Error` would also close the hole, but only for a reader who already knows a direct
`Throwable` subclass cannot reach the line. Completeness is the whole premise, so the catch states it.

Nothing else changes. **No control flow moves**: the row is written under the same
`!handedOn[0] && policy.records(...)` guard as today, with `failure.toString()` as the error text, and
`throw failure;` rethrows the same instance. Precise rethrow (JLS 11.2.2) should let that compile with
no `throws` clause, because the compiler sees only unchecked types leaving the try. **If it does not
compile, stop and hand back — do not wrap, do not add a `throws`, do not call `sneaky`.** That outcome
would mean D-111's "no control flow change" is unachievable in this form and is the architect's to
decide, not the implementer's.

Still standing, do not touch: D-098 and D-049 — an `Error` is not transient and is not retried;
`FlowWorker.java:352` still leaves the item to its lease. D-103 — a user error handler never sees an
interrupt. **`Parking.java:49` must keep catching `Exception` only**; a scout read it as a second
instance of this gap and that reading is wrong, because parking an `Error` would make it transient,
which D-098 refused. `Delivery.java:319-320` is a real second instance but contradicts D-049 (d), not
D-111; it is FIX-136 and not in scope here.

## Red tests (test-author, before any production change)

All in `flottila-core/src/test/java/io/flottila/core/record/RecorderTest.java`, as **new** methods
beside `aCancelledStepRecordsItsFailureSnapshot`, which is the model to follow and must not be edited.
Reuse its `static sneaky(Throwable)` helper and its `factory(type, stage)` / `flow` / `step` fixtures.

1. `aStepThatThrowsAnErrorRecordsItsFailureSnapshot` — parameterised over at least `AssertionError`
   (with a message) and `StackOverflowError` (**without** one, so assert on the class name only;
   `failure.toString()` carries no message there and an assertion demanding one would be wrong).
   For each: the row exists, its outcome is `FAILED`, its `error()` names the throwable's class, the
   rows before it are untouched, and the escaping throwable is `assertSame` the one thrown.
2. `aStepThatThrowsADirectThrowableSubclassIsRecordedToo` — a `Throwable` subclass that is neither
   `Exception` nor `Error`, thrown through `sneaky`. This is the case that distinguishes `Throwable`
   from `Exception | Error`; without it the chosen form is not pinned.
3. `anErrorAfterTheStepHandedOnLeavesNoSecondRow` — the stage hands on (an `OK` row is written) and
   then throws an `Error`. The `handedOn[0]` guard must still suppress a second row. This is the
   assertion that catches a "fix" that moves the guard.
4. `aPolicyThatDoesNotRecordFailuresStillLetsAnErrorEscape` — with a policy whose
   `records(..., FAILED)` is false: no row, and the `Error` propagates unchanged. Pins that recording
   and handling stay independent in both directions.

**Red is not optional and one of these is already green by accident**: case 4 passes against today's
code (no row is written either way). Say so in the hand-back and name which assertion in it would fail
if the guard were dropped, or replace it with one that is genuinely red.
