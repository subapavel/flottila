# FIX-141 — one producer that fails to close must not strand the others

Class A. Small. Found by F-30's sweep and deliberately kept out of FIX-136, because this is a shutdown
path and D-049 (d) does not reach it.

## The defect

`Producers.java:44-55`, the close loop:

```java
for (Producer p : producers) {
    Future<Void> closing;
    try {
        closing = p.close();
    } catch (RuntimeException thrown) {   // :49 — a producer that throws instead of failing its future
        closing = Future.failedFuture(thrown);
    }
    settled.add(closing.recover(failure -> {
        LOG.log(System.Logger.Level.WARNING, "flow " + flow + ": a producer did not close (" + p + "): " + failure, failure);
        return Future.succeededFuture();
    }));
}
```

An `Error` from one producer's `close()` abandons the **loop**, so every producer after it is never asked
to close and never joins `settled`. Sockets, pools and file handles belonging to the untouched producers
leak, and the close future that the caller waits on either never completes or completes without them.

## The decision, made here so the implementer does not have to

Widen `:49` to **`Throwable`**. Nothing else changes, because the `recover` at `:52-55` **already**
defines the right behaviour for a producer that will not close — log it at WARNING, naming the flow and
the producer, and carry on — and a synchronous throw should reach exactly that handler rather than a
different one. The whole purpose of collecting `settled` is that one bad producer does not decide the
fate of the rest.

That is the decision the row asked for, and it is worth stating rather than assuming: this is a shutdown
path, where finishing the remaining work matters more than propagating the first thing that went wrong.
An `Error` that genuinely must reach the JVM — an OOM — will reach it again on the next allocation; an
`Error` that merely means one producer is broken must not take the others down with it.

## Red

1. three producers, the **middle** one's `close()` throws an `Error`: all three are asked to close
   exactly once, the future still completes successfully, and exactly one WARNING names the failing
   producer. Fails today, because the third producer is never asked.
2. the same with a `RuntimeException` instead — the regression guard proving the catch widened rather
   than shifted. Green today; say so plainly rather than presenting it as evidence of the fix.
3. assert "asked exactly once" by counting calls on the fixture, not by observing a side effect, so a
   producer closed twice is caught as well as one closed never.

Put them where the existing `Producers` tests are; if there is no test class for it, say so and name the
one you created.

## Note for the reviewer

One line of production code, so the question is whether case 1 really fails for the stated reason — that
the loop was abandoned — and not merely because one WARNING is missing. The call count on the third
producer is what separates those two, so check it is asserted.
