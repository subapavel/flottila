# FIX-136 — an Error must not escape Delivery, in any of the three modes

Class B. Depends on FIX-133 (done, 9a9c916) and on **F-30**, which is written and must be read first.

## Read before anything else

`docs/findings/F-30.md`, whole, 167 lines. It settles the question the BACKLOG row left open and it was
**corrected once** — its first draft implied the permit leak followed from `Delivery.apply` for every
mode, which is false. Read the corrected per-mode breakdown, not a summary of it. Nothing in this

The one-line version: D-049 (d)'s "never an escaped exception" means **every throwable**, D-049 needs

## What to change, and the type to use

Four catch sites. Use **`Throwable`**, not D-104's `RuntimeException | Error` multicatch, at all of
them, for one reason: every one of these is a site that **translates a synchronous throw into a failed
future or a logged drop**, and the caller is a future either way. There is no throwable such a caller
handles better by having it propagate, and a sneaky checked throwable — which the multicatch would miss
and which D-056 widened two of these very catches to catch — is exactly what arrives here when a stop
deadline interrupts an `await`. D-104's multicatch is a different situation: there the catch decides
policy, not translation. Say this choice out loud in the commit; do not leave it to be guessed.

1. **`Delivery.java:319-320`** — `catch (RuntimeException failure)` around
   `intake.save(e, ingress.apply(e), flow, key, dedupe, ...)`. The at-least-once ingress save. This is
   the row's headline site.
2. **`SequentialIntake.java:41`** — `catch (RuntimeException failure)` around
   `arrived.body().store().persist(arrived.body().key())`.
3. **`SequentialIntake.java:47`** — `catch (RuntimeException failure)` around `store.record(ingress)`.
   Sites 2 and 3 sit **inside** the `intake.save` that site 1 calls, so widening site 1 alone leaves the
   hole open one frame deeper. All three or none.
4. **`Delivery.java:176` and `:218`** — `catch (Exception thrown)` / `catch (Exception failure)` around
   the sync and at-most-once pipeline runs, **plus their locals**: `Exception failure` at `:172` and
   `Exception dropped` at `:214` widen to `Throwable` with them. `Future.failedFuture` takes a
   `Throwable`, so the sync return path needs no other change.

**Site 4 changes what D-056 settled.** D-056 widened those two catches from `RuntimeException` to
`Exception` deliberately, for the sneaky `InterruptedException` an interrupted `await` throws, and it did
not consider `Error`. So the commit must say that it widens them again and why, and D-056's row gains a
note. This is not a silent fix either.

## The acceptance, per mode — they are three different assertions

The ingress save exists **only in at-least-once**. The row's "all three delivery modes" is right about
the scope and wrong if read as one assertion repeated three times. F-30 has the detail; here is what
each mode must pin.

**at-least-once** — the mode that actually breaks, and the only one where the permit is at risk, because
its path has no `finally` at all and the permit is released only when the answer is decided
(`Flight.land()` at `:109-111`, class javadoc at `:50`):

- an `Error` thrown synchronously by the intake's `save` produces a **retryable NACK**, not a thrown
  throwable out of `apply`
- **the permit returns**: assert it, through `Delivery.admission()` (the package-private accessor at
  `:147`) and `admission.inFlightRequests()` — back to 0, and `inFlightBytes()` with it
- **`stop(Duration)` completes.** Drive it: after the failing delivery, call `stop` and assert its future
  completes. Give the assertion a bound through the fake timer and the test's own deadline, never a sleep.
- **the NACK must name the `Error`, not a timeout that never happened.** Assert the reason text carries
  the throwable's own `toString()` and does **not** contain "durable save timed out". This is the
  sharpest half of the task: see the correction below.
- the same three for an `Error` from each of `SequentialIntake`'s two sites, so sites 2 and 3 are pinned
  separately from site 1 rather than by proxy

**Correction to F-30, third round (2026-11-14) — read this before you judge the severity.** F-30 first
said the permit leaks *permanently* and that `stop()` *can never complete*. Both were wrong and have been
rewritten. `Delivery.java:286` schedules the save timeout **before** the save is asked, and `:281` lands
the flight when the answer completes, so the pending timeout eventually fires, completes the answer and
returns the permit. Today's real behaviour: the permit is held for the remainder of `saveTimeout` (5 s by
default) per `Error`, and `stop()` completes at its deadline instead of at once — bounded and
self-healing. **What is not self-healing is the record.** The answer is completed by
`new Ack.Nack("durable save timed out after " + saveTimeout, true)`, so the sender and the monitoring are
told a save timed out when in truth a step threw an `Error`, which is never recorded at all. Widening the
catch replaces that with `retryable(done.cause())` (`:324`), which carries the real cause. The assertions
above are unchanged and still correct, because they assert the **stronger** form — permit back at once,
with no clock advance — which fails today. Only the reason for caring has changed.

**sync** — the permit already returns here, via the `finally` at `:177-181`. Do not present that as the
fix:

- an `Error` from the pipeline comes back as a **failed future** from `apply`, rather than being thrown
  out of it
- assert the permit **keeps** returning — a regression guard on behaviour that is already right, and say
  in the case's javadoc that this is what it is

**at-most-once** — the permit already returns here too, via the `finally` at `:219-222`:

- an `Error` from the pipeline is **logged and dropped**, as D-049 (b) requires, instead of ending as an
  uncaught throwable on the message's own virtual thread (`:205` starts it with
  `Thread.ofVirtual()...start(() -> run(e, flight))`, so today it reaches the thread's default handler
  and lands on stderr with no message id through `System.Logger` at all)
- capture the log the way `TrailTest` and `RecorderTest` do, and assert exactly one record naming the
  message
- the sender already holds its 202, so nothing is owed to it; what this pins is the log line, which for
  a platform whose product is monitoring is the whole of the damage

## The NACK-text assertion: where its red comes from (added 2026-11-14, after the red addendum)

The `assertFalse(nack.reason().contains("durable save timed out"))` added to
`anErrorFromTheIngressSaveIsARetryableNackNotAnExceptionOutOfApply` is **not observed red today and
cannot be**: the case fails at its first assertion, because the `Error` escapes `apply` — which is the
headline defect. The test-author reported that plainly instead of claiming a red it had not seen, and it
was right to.

Two things follow, and the reviewer must hold the task to both.

1. **The identity half is already asserted, in the only form that survives the fix.**
   `Delivery.retryable` at `:436-437` is
   `new Ack.Nack(Objects.toString(failure.getMessage(), failure.toString()), true)`, so for an `Error`
   with a non-null message the reason **is** that message, with no class name anywhere. The existing
   `assertTrue(nack.reason().contains(LINKAGE))` therefore pins the cause's identity as strongly as the
   reason affords. A `toString()` or class-name assertion would fail *after* a correct fix, or force a
   change to `retryable()` that nobody asked for. None was added, correctly.
2. **The designated mutant for the `assertFalse` is this**: with the fix in place, stop the widened catch
   from deciding the answer — let the `Error` fall through to the pending `:286` save timeout instead.
   The reason then reads `"durable save timed out after PT2S"` and the `assertFalse` is the line that
   kills it, while every other assertion in the case still passes. That mutant is the proof the
   assertion is load-bearing, and the verifier must run it. Until it has been run, the assertion is a
   prediction, not evidence — the test-author said so and the word stands.

`SequentialIntakeTest` deliberately has no such assertion: it calls `save` directly and gets a failed
future, with no NACK and no reason text. Its two sites reach the assertion anyway, because the
`Site`-parameterized `DeliveryTest` case covers `BODY_PERSIST` and `INGRESS_RECORD` with the NACK in
hand. Building a `Delivery` inside `SequentialIntakeTest` to reach a reason string would be a restructure
for nothing.
