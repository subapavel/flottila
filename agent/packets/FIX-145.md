# FIX-145 — a pg_xact_status failure pins only its own save; the sweep goes on (class B; review F7.3, F-29)

Architect 2026-11-10. Base: 69d0d0b.
Problem (verified in code; PG behaviour for a future xid per the review, SQLSTATE 22023): PgIntake.settle (PgIntake.java:215-230)
asks one batched XACT_STATUS (:103) for every in-doubt xid; any error propagates out of openSaves() (:210-212) into
SegmentSweeper.pass (:116), which aborts before rows.sweep (:117). One unresolvable xid (a failover to a standby whose xid counter
is behind, a lost reply) stops all segment collection on the node until restart.

## Decision
- settle(): if the batched query fails, ask each in-doubt xid on its own. An xid whose query fails stays in doubt (its save stays
  open, its segment pinned) — an error is never taken as an abort or a commit. Every other xid settles as today.
- openSaves() never throws because of a status lookup: it returns the saves still open (all of them if even the per-xid queries
  cannot run, e.g. the pool is down). The sweeper then sweeps what is not pinned, as on a normal pass.
- One WARNING per xid the first time its lookup fails (xid, SQLSTATE/message, how long it has been in doubt), not one per pass;
  a later success settles it silently as today. No new config, no metric now (FIX-141 / admin listing may expose it later).
- Batched first stays the normal path (one round trip); the per-xid fallback runs only after a batched error.
