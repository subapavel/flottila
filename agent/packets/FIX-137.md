# FIX-137 — a duplicate-only intake group commits a WAL barrier before its 202 under ha (review F3.2, D-114) [B]

## Today
PgIntake.transaction (:385-396): a group in which no member writes rows (every member a duplicate of an earlier save,
D-084/D-109) rolls back and answers 202 for the earlier message. Under ha that earlier save may be committed locally only:
a SyncRep wait ended by a backend termination or a fast restart (FIX-136 §4 residual) leaves a local-only commit whose
sender got 503; the sender's retry is then answered 202 by the duplicate path, which waits for nothing — a promotion loses
a message the sender holds a 202 for.

## Decision (architect, from the FIX-136 designer's P8; D-128 reversible)
- B1 Under `ha`, a group with no row to write runs `select pg_current_xact_id()` inside its transaction and COMMITs instead
  of rolling back. The assigned xid forces a commit record; its SyncRep wait covers every earlier WAL record, the earlier
  save's included, so the 202 is given only once that save is on a sync standby. Under `local` the rollback stays.
- B2 A failed barrier (statement or commit) fails the group retryably, exactly as a failed commit of written rows does
  (no 202; InDoubt only where an xid of written rows exists today — the barrier writes no rows, a lost barrier commit is
  simply retryable).
- B3 PgIntake learns the profile through its constructor (a boolean or the Durability value from Node), never from Runtime.
- B4 Docs: ARCHITECTURE §4 durability paragraph drops the F3.2 residual (now closed) and states the barrier; changelog;
  D-128; D-109's duplicate rule amended; F-29 F3.2 row done at the commit.

## Red tests (test-author)
- PgIntakeIT (or the existing intake IT): under ha a duplicate-only group consumes an xid and commits (observable: the
  server's next xid / pg_current_wal_lsn advances, or a commit count) and answers the duplicate; under local it consumes none.
  A failing barrier (e.g. a session where pg_current_xact_id is refused, or the commit failing) → no 202, retryable.
- PgPromotionLedgerIT: `aRetriedDuplicateAfterATerminatedSyncWaitIsNot202UntilReplicated` — ha, receipt stopped; a
  dedupe-keyed post waits and its backend is terminated (pg_terminate_backend) → 503; its retry with the same key while
  receipt stays stopped is not 202 (waits, 503 at saveTimeout); receipt resumed → a retry gets 202; SIGKILL + promote →
  the id is on the promoted server.
- No sleeps; red observed.

## Implementer r1 obstacle → B1 amended (architect, 2026-11-11)
An xid alone writes no WAL, and RecordTransactionCommit waits for the sync standby only when the transaction wrote WAL
(xact.c: wrote_xlog && markXidCommitted) — `select pg_current_xact_id()` commits without waiting; the ledger red stays 202.
B1 amended: the barrier is `select pg_current_xact_id(), pg_logical_emit_message(true, 'flottila', '')` — one
transactional WAL record, no row; probe green (PgPromotionLedgerIT 6/0, PgIntakeIT 26/0, plain role + pg_monitor,
wal_level replica; FIX-137-probe.log). A revoked EXECUTE fails every ha duplicate retryably and loudly (documented).
Rejected: a heartbeat row or a row lock (rows written, B2).

## Owner decision (2026-11-11, chat)
EXECUTE on pg_logical_emit_message is a condition of the ha profile: under `ha` the start check refuses a role that may not
run it (has_function_privilege), naming the GRANT, like the pg_read_all_stats refusal — never discovered only at the first
duplicate. Scope added to FIX-137: B5 start refusal + red tests (PgDurabilityTest field/case; PgPromotionLedgerIT revoke case).

## B5 (owner decision) — spec for the red

- Under `ha`, false → start refused before migrating; message names the function and the fix:
  `GRANT EXECUTE ON FUNCTION pg_catalog.pg_logical_emit_message(boolean, text, text) TO <user>` and D-128.
  Under `local` the field is ignored (no barrier runs). Order among refusals: listed after the pg_read_all_stats one.
- Red: PgDurabilityTest — ha + false refused naming that GRANT and the user; ha + all true accepted; local + false accepted.

## B5 red approved (2026-11-11) + signature decision
PG 17 has only pg_catalog.pg_logical_emit_message(boolean,text,text,boolean) (+ bytea twin); the 3-arg form is PG 16.
Decision (architect, reversible, in D-128): the start query reads `coalesce(has_function_privilege(current_user,
to_regprocedure('pg_catalog.pg_logical_emit_message(boolean,text,text,boolean)'), 'EXECUTE'), false)` — never ERRORs
(local on any version starts); under ha false is refused naming `GRANT EXECUTE ON FUNCTION
pg_catalog.pg_logical_emit_message(boolean, text, text, boolean) TO <user>` (D-128). So ha needs PostgreSQL ≥ 17: state it
in D-128 and §4. The barrier statement itself is unchanged (3 args, flush defaults false on 17).
