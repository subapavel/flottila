## The invariant (from the FIX-71 r4 review, re-checked in the code for this packet)

At rest, either `queue.size() < options.batchSize()` or `inFlight == options.commitConcurrency()`.
Waiters exist only when the queue is full, which implies `inFlight == commitConcurrency`.

Walk `takeLocked` (`:242-259`) with that in hand. Its loop condition is at `:244-245`:

```java
while (!queue.isEmpty() && inFlight < options.commitConcurrency()
        && (inFlight == 0 || queue.size() >= options.batchSize() || windowElapsed)) {
```

- entered with `inFlight == commitConcurrency`: the second clause is false, the loop never runs.
- entered with `queue.size() < batchSize`: the first pass takes `min(batchSize, queue.size())`, which
  is the whole queue, so `queue.isEmpty()` ends the loop — **unless** the inner loop at `:252-256`
  refills the queue from `waiters`. But waiters exist only when the queue was full, which means
  `inFlight == commitConcurrency`, which is the case that never entered the loop at all.

So **each drain takes at most one batch**, the outer `while` at `:244` runs at most once, and
`dispatch`'s `forEach` at `:272` iterates at most one element. Only FIX-69's removed `continue` ever
produced several batches in one drain.

## The decision (architect, binding — the row left it open)

**Keep the loop. Fix the javadoc.** Not narrowed to an `if`.

The reason is the failure mode, not elegance. If a future change breaks the invariant — and FIX-69's
`continue` is proof that this code has had that shape before — a `while` degrades into taking several
batches, which is correct behaviour, merely more than needed. An `if` would instead leave items queued
with no commit in flight and no window armed: a silent stall, and a stall is the worst failure this
class can have. The `while` is the cheap insurance and it costs one surviving equivalent mutant, which
is a price this project already pays knowingly elsewhere (see FIX-135 on PIT's noise).

This is recorded as **D-112** by the architect at commit time. The implementer does not edit
`docs/DECISIONS.md`.

## What to change

In `flottila-core/src/main/java/io/flottila/core/batch/BatchingWriter.java`, two javadoc sites:

1. **`drainLocked`, the second paragraph at `:204-207.`** It currently says "a younger batch can reach

2. **`takeLocked`'s javadoc at `:241`.** One line today. Add the invariant and the consequence: the
   loop runs at most once given the invariant above, and it is a loop rather than an `if` so that a

   **D-112**, and name FIX-69 as the one change that ever produced several batches per drain.

Say "unreachable today, and here is the invariant that makes it so" — never "unreachable" alone,
which reads as a dead-code claim a reader cannot check.

## No test, and why that is not a lapse

Nothing observable changes, so there is nothing a test can assert. The obvious candidate — a test that
tries to make a drain take two batches and asserts it cannot — would pass because the setup is
impossible to construct, not because the code is right. That is a vacuous test, and this project has
spent real time this week on assertions that passed for the wrong reason. The precedent for a
documentation-only row is **FIX-129**.

The implementer runs the module's existing tests to show nothing broke, and that is the whole of the
evidence this task can offer. Say so plainly rather than dressing it up.
