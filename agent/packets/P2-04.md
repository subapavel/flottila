## Acceptance
- runtime class `Secrets` (no interface: one implementation today; the wallet later replaces it): built from the env map NodeConfig
  already holds; `secret://<name>` with name `[a-z0-9][a-z0-9._-]*` → env `FLOTTILA_SECRET_<NAME>` (upper case, `.` and `-` → `_`).
  A second factory for the CLI dry build: syntax checked, resolves every well-formed reference to a fixed placeholder (say which).
- Resolution: a string option value that is exactly `secret://…` is resolved, recursively through nested maps and lists, in the
  effective endpoint options (after the env overlay and the schema check) where runtime builds the EndpointConfig for `consumer` and for
  the producer path — both paths get the resolved config. A string that merely contains `secret://` is left as it is; a malformed
  reference (`secret://`, `secret://Bad Name`) is a problem.
- Missing variable → the deploy is refused (422 / FAILED as any config problem) with a problem
  `endpoint '<id>': secret 'secret://<name>' is not set (FLOTTILA_SECRET_<NAME>)`; never a value in any problem.
- The resolved value appears only in the EndpointConfig handed to the component: the admin listing / deployment record / archive, the
  timeline, recordings and problems carry the reference. Test it where the endpoint config is observable today (admin GET, the
  deployment record, whatever the test-author finds).
- Node wiring: Main passes its env map; Validate and FlowTests use the placeholder factory, so `flottila validate`/`flottila test`
  never need a secret. No `api` change; components unchanged.
- Fixture comments `${secret://partner-token}` (packages/demo/endpoints/partner-domestic.yaml:12 and the cli fixtures) reworded to the
  bare syntax by the test-author (demo: comment only).
