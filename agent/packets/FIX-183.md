Row: `agent/BACKLOG.md` FIX-183, under MAIN-1 since `ci` run 218 failed on it (`agent/work/MAIN-1-ci.md`):

`PeerProtocolTest.theOwnerServesAtMostPeerReadsOfALinkAtOnce:270 the second READ waited for the first to be

## The fault (read from the code, the red confirms it)

`platform/runtime/src/main/java/dev/rail8/runtime/journal/peer/PeerServer.java`, class `Serving` (:259-300):
`received` (:268) starts one virtual thread per READ (:281) and the thread takes the permit of the link's fair
`Semaphore serving` as its first statement (:282). The semaphore is fair among threads that have called
`acquire`; which of two threads started back to back calls it first is the scheduler's choice. With
`RAIL8_PEER_READS` 1 the second READ's thread can take the permit first and is then served whole before the
first. The bound itself (at most `reads` at once) holds; the order does not.

## Scope

This task: the order in which a link's READs begin service. Nothing else of the old row — the event-loop
assertion in `PeerLink.send` on a link being disposed, the stale line references in `PeerKnownAnswerTest`, and
the relay's blame of a write failure move to a new row as they stand (the architect's ledger, not yours).

## Acceptance

1. With `RAIL8_PEER_READS` 1, READs of one link begin service in the order the owner received them: READ
   n+1's first answer frame follows READ n's last, for every n. Pinned by a case that sends many READs of one
   link back to back (as many as the protocol's bound of open READs allows with room to spare, see
   `PeerConfig.READS_MAX` and `aDialerWithMoreThan64ReadsOpenIsClosed`) and asserts the ids of the answers in
   order — so one inversion anywhere fails it.
2. With a bound above 1 the order of *beginning* service is the arrival order too; what the case can observe
   of it without tempo, it asserts; what it cannot, the hand-back says.
3. `theOwnerServesAtMostPeerReadsOfALinkAtOnce` and `aDialerWithMoreThan64ReadsOpenIsClosed` stay as they are
   and pass. The receiving side is never blocked by a READ that waits for its turn: the 65th open READ still
   closes the link while 64 wait.
4. A READ that waits for its turn when its link closes ends as today (it fails at its first write or is never
   served); the server's close still completes within the tests' bound; nothing is left running.
5. Red first: the new case fails against the code as it stands. The fault is a race, so the red is a rate:
   run the case alone enough times to state it (at least 20 executions; `@RepeatedTest` in a throw-away copy
   or repeated Maven runs — never kept in the tree) and hand back "red k of n" with one failure text. If it is
   red in fewer than 19 of 20, make the case sharper (more READs in one write, a large record first so the
   others queue behind it) before you hand back — a case that is usually green against the fault pins nothing.
   After the fix: green by construction, 20 of 20, and the old case :270 20 of 20.
6. No sleep, no wall-clock wait other than the package's existing bound.

## Design (the architect's; the implementer may hand back a better one before writing it)

- One FIFO per link, owned by `Serving`: `received` — which stays non-blocking — appends the parsed READ and,
  when fewer than `config.reads()` READs of this link are in service, starts one virtual thread for the head.
  A serving thread that finishes takes the next head and serves it, or ends when the FIFO is empty.
- One lock per link guards the FIFO and the count in service. Nothing of `serve` runs under it and nothing
  waits under it. The `Semaphore` goes.
- The FIFO is bounded by the existing check on `open` (`PeerConfig.READS_MAX`); `open` still counts a READ from
  its arrival to the end of its service. No new limit, no new configuration.
- Threads keep the name `rail8-peer-serve`. A virtual thread per READ in service, none for a READ that waits.
