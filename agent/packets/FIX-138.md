# FIX-138 — pin the consequence D-104 states for a throwing cancel()

Class A. Depends on FIX-71 (done). Raised by the FIX-71 r5 test-author, which deliberately left it
out of that round's scope. One test and one javadoc sentence. **No production logic changes.**

## The defect that is not a defect

`flush()` (`BatchingWriter.java:178-190`) drops the armed window at `:185`:

```java
if (armed != null) { cancelQuietly(armed); armed = null; }
```

`cancelQuietly` (`:230-239`) swallows a throwing `cancel()` and logs once per writer. So when
`cancel()` throws, `armed` is nulled but **the timer handle stays scheduled**. It fires later, enters
`onWindow()`, which sets `armed = null` — nulling whatever window is armed by then, possibly a newer
one — and drains with `windowElapsed = true`, handing a newer partial batch to the sink before that
batch's own window elapses.

D-104 accepts this: a loss of batching, never of data and never of order. The row's point is that
**nothing asserts it**, so the opposite could silently become true. Mutant 8 in the FIX-71 round
produced this exact effect and turned out to be observable, which is why the non-throwing twin
`aWindowThatFlushDroppedNeverFiresSoANewerPartialBatchWaitsForItsOwnWindow`
(`BatchingWriterErrorTest.java:288`, javadoc at `:280-285`) exists. This task writes its throwing twin.

## There is no red in the ordinary sense, and here is the red you must produce instead

Nothing about the behaviour changes, so the new case is **green the moment it is written**. That makes
it a characterisation test, and a characterisation test is worthless unless it is shown to be
non-vacuous. Do not hand back a green case and call that evidence.

**The red:** run the case once with the throwing cancel disabled — `cancelThrows` left `null`, so the
flush cancels the window cleanly and the orphaned window never fires — and the case MUST fail. Quote
that failure line. That failure is this task's red, and it proves the case is asserting the throwing
path rather than something that holds either way. Then restore `cancelThrows` and show it green.

If the case passes with a non-throwing cancel, it asserts nothing this task cares about. Rewrite it.

## The worked example to mirror

Mirror the twin at `:288` exactly — same shape, same window, same batch size, same commit
concurrency — so the two read as a pair and the single difference between them is the throwing cancel.
Window 50 ms, batch 2, commit concurrency 2, `FakeSink` in `manual` mode:

- t0: `save("a")` — idle, a goes alone. `save("b")` — a is in flight, b is queued, W1 armed for t50.
- set `cancelThrows` to an `IllegalStateException`, call `flush()`, then set it back to `null` so that
  no later cancel in the case throws. The flush's cancel of W1 throws and is swallowed; `armed` is
  nulled; **W1 is still scheduled**; b goes on the second slot. Sink holds `[a]`, `[b]`.
- complete both gates; a, b and the flush succeed.
- t10: `save("c")` — idle again, c goes alone. `save("d")` — d is queued, W2 armed for t60.
- t50, W1's due time: **the orphaned W1 fires.** This is the whole point of the case. It nulls W2's
  handle reference and drains with `windowElapsed = true`, so `[d]` reaches the sink at t50 — ten
  milliseconds before d's own window.
- t60, W2's due time: W2 is still live in the fake timer, because `onWindow` nulled `armed` without
  cancelling it. It fires into an empty queue and must take nothing and fail nothing.
- complete the gates.

## What the case must assert

Four things, and the done-when is written from them:

1. **The early hand-off happens.** At t50, `[d]` is in `sink.batches`. Assert this positively — not as
   "d is not still waiting", which would also pass if d had been lost.
2. **Every item reaches the sink exactly once, in arrival order.** The concatenation of
   `sink.batches` is `["a", "b", "c", "d"]`. This is the assertion that makes the "loss of batching,
   never of data or order" claim in D-104 true rather than asserted.
3. **Nothing fails.** All four futures and the flush succeed; `w.inFlight()` returns to 0; the fake
   timer's `pending()` returns to 0, so no handle is leaked by the double-nulling.
4. **The throwing cancel is logged once, not twice and not never.** The fixture already has
   `batchWarnings()` for this. One throwing cancel, one WARNING.

Put the case in `BatchingWriterErrorTest`, directly after its non-throwing twin, with a javadoc in the
twin's style that spells out the timeline as a worked example with its millisecond marks. A reader
must be able to check the claim without running it.

`CancelThrowingTimer` and `batchWarnings()` already exist in that class — `grep -n 'CancelThrowingTimer\|batchWarnings' flottila-core/src/test/java/io/flottila/core/batch/BatchingWriterErrorTest.java`.
Reuse them. `FakeTimer` is `flottila-testkit/src/main/java/io/flottila/testkit/FakeTimer.java`. The
clock is a fake: no sleep, no real time, nothing timing-dependent.

## The javadoc sentence

`flush()`'s javadoc, `BatchingWriter.java:176`, today reads:

```
 * Never throws: a dropped window whose {@code cancel()} throws is tolerated (logged once).
```

"Tolerated" is accurate and incomplete, and this is the one place a reader of the code looks for what
D-104 records. Add the half-sentence: the dropped window stays scheduled, so it may fire later and hand
a newer partial batch to the sink before that batch's own window — a loss of batching, never of data or
of order (D-104), pinned by the new test. Name the test.

You may add a one-clause cross-reference to `cancelQuietly`'s javadoc (`:225-228`), which today covers
only the waiter-deadline case. Optional, and one clause at most.
