## The harm, stated precisely — this is what the test must show

The row says the message "loses the history of every run but its first". That undersells it. If run
1 fails at step 3 and run 2 reaches step 7, `timeline(id)` returns **steps 1-3 from run 1 and steps
4-7 from run 2, in one sequence, with nothing marking the seam** — and step 3 reads `FAILED` while
steps 4-7 read `OK`, which is a sequence no single run can produce. The timeline is not short, it is
a chimera, and an operator reading it cannot tell what happened. That is the observation worth
pinning.

## Acceptance

1. One test in `flottila-core` drives **one** message id through `FlowWorker` twice against the
   in-memory store: run 1 fails at a middle step, the lease expires or a second claim happens, run 2
   gets past that step. Reuse the machinery `FlowWorkerTest` already has rather than inventing a
   path.
2. `timeline(id)` is then asserted **row by row**: which step numbers exist, and for each row which
   run it came from — distinguished by a value the two runs genuinely differ in (step name, outcome,
   or a prop), not by position. Not a size assertion, not a `contains`.
3. The stitch is asserted explicitly: a `FAILED` row at step N and `OK` rows at steps greater than N
   in the same timeline.
4. Whether the attempt is visible anywhere in that timeline is asserted either way. If
   `Envelope.ATTEMPT` does reach run 2's props and so appears in the props of the rows run 2 did
   write, assert that it does and that it is absent from the rows run 1 wrote — that asymmetry is
   the one place a reader could notice two runs, and CONSIDER-12 needs to know it exists. If it
   reaches nothing, assert its absence from every row.
5. The test is **green on today's code**, and its naming makes unmistakable that it documents a
   defect: the method name states the wrong behaviour as a fact, and the javadoc cites FIX-131, F-29
   and CONSIDER-12 and says the test is to be inverted when the row key gains `attempt`. Do not give
   it a name that reads as intended behaviour — `...DuplicatesAreIgnored` at `PgMessageStoreIT:122`
   is exactly that trap, and it is part of why this went unnoticed.
6. No production change, and no new seam added to production code for testability.
