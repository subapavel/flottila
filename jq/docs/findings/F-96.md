# F-96 — a parameter chain can spend the specialisation cap before a later prelude loop

- **Assumption** (ADR-0045 #117, S2): keys are spent in Source order. F-94 left open whether a chain
  placed first could leave a later `recurse` key unspecialised.
- **How it fails**: on the #117 test author's toy specialiser,
  `0|g600(.) | [label $f | 0 | recurse(if . >= 3 then break $f else .+1 end)]` spends 16 382 of
  16 384 nodes and refuses 406 keys. Recurse's key costs 13 nodes against a remainder of 2, so S2 as
  written refuses it. All numbers are the toy's, UNVERIFIED on a real pass.
- **Severity**: minor. The cap bounds compile work, the refused loop runs with real closures, and
  the depth budget still counts them. At the default depth of 4 194 304 the order case should still
  give jq-ref's `29999` (NOT_RUN). A 3 000 000-level loop after such a chain would end
  RECURSION_DEPTH where jq gives a result.
- **Evidence**: t/117-specialise at b818e41 (`.logs/117-census-probe.log`); the grilling-adviser's
  ruling of 2026-11-15, which also ran jq-ref on the order filter (`29999`, rc 0).
- **Change made**:
  - The order stays. Reversing it needs a two-phase queue and does not close the gap: any finite cap
    with a fixed order has a prefix that exhausts it.
  - ADR-0045 #117 "Order and cap" names `specialise/order-param-chain-then-recurse` as refused by
    design and adds one sentence on later keys.
  - The order test asserts `refused > 0`, `specialised ≤ 16 384` and `[29999], ran out` exactly in
    both modes at `Limits.cli()`'s depth. It does not pin whether r/0 gets a copy.
- **Reopen**: when a real corpus filter is refused outside the list (S5), with that filter as the
  measured case.
