# F-98 — #117's red needs #116's value form, which no blocking edge said

- **Assumption**: #117 is blocked by #114, #110 and #108. Its red, approved at 7c5a5ff, includes
  `SpecialiseExplainTest.overInlineCapStillSpecialisesRecurse`, which expects the OPTIMISED run of an
  over-INLINE_CAP ladder before `recurse` to finish at `recursionDepth` 40 000.
- **How it fails**: with the specialiser built, the copy of recurse's function is made
  (`specialised=56`), but the run ends `BUDGET RECURSION_DEPTH`. The ladder functions f0–f15 have no
  closure parameter, so specialisation has nothing to copy for them. In the push form their PLAIN
  activations stay live while the rest of the pipe runs (ADR-0045 #107): the least depth that passes,
  measured, is 95 522 = 30 000 + 65 522. Only #116's value form ends an activation when its `eval`
  returns (ADR-0047 #116 C2). At the red the test failed earlier, at `copyOf`, so this premise was
  never reached.
- **Severity**: minor. It is an ordering error, not a behaviour defect.
- **Evidence**: the #117 implementer's hand-back and the Spec review of impl/117 at 562feb4
  (`.logs/117-verify.log` in its worktree).
- **Change made** (superseded by F-100): #117 is blocked by #116 as well. The test is not re-pinned; it must pass once
  #116 is merged into #117's branch. The CONSERVATIVE half, which now ends RECURSION_DEPTH because
  of the ladder, is checked again at that point.
