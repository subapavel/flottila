# F-107 — The lifted form left out the level of a Call's value Vars

- **Assumption**: ADR-0040 #114: the lifted form of a call site is "a Call plus each closure argument
  lowered once". The measure took the Call as one level (`acc.own(0, around + 1)`).
- **How it fails**: the Resolver builds a Var under the Call for each value parameter and each value
  capture (Resolver.java:809, :815), one level below it, and `within` counts those Vars. So
  `def r($a): if false then r($a) else . end; r(.)` is 3 levels but measured 2. At 513 levels such a
  filter hits the IR depth Stub where the measure says it fits.
- **Evidence**: the third Standards review of #114 (8471728) predicted it from the source. The
  implementer's rows were red before the fix: `.logs/114-edges4-vars-red.log` and `-red2.log` in the
  impl/114 worktree. The fix is ExpansionMeasure.java:99-103 at ab9a86e, and each half of its new
  condition fails its own row when dropped.
- **Severity**: moderate. A filter near the IR depth bound became a Stub instead of a PLAIN call.
  Results were never wrong: the backstop Stub is a clean failure.
- **Change made**: ADR-0040's lifted-form sentence names the Vars level. #114 carries the fix and its
  rows at IrDepthTest.java:762-764.
