# F-93 — stack probes in child and test threads do not prove their thread's size

- **Assumption**: a thread started with `new Thread(group, task, name, stackSize)` has a stack of
  `stackSize`. `oracle/StackProbe`'s reference thread, the `JqTestOracleTest` check
  `everyCaseRunsOnTheRunnersOneThread`, and the R4 child of `DeepStackFreshJvmTest` rely on this.
- **How it fails**: glibc caches the stacks of ended threads. A new thread with a small stack can
  be given a larger cached one.
  - #111's measurement found a 512 KiB `-Xint` thread reaching 4 772 frames on a fresh launcher
    main thread. A reused cached stack reaches about 10 729.
  - #111's first gate run: `everyCaseRunsOnTheRunnersOneThread` saw 31 115 frames against a
    reference of 83 031 on a "fresh 2 MiB" thread, inside the full oracle run. The same class run
    alone passed 511 of 511 (`.logs/111-jqtest-oracle.log`), and the second gate passed. Its Jqj is
    a fake, so no jqj code was involved.
  - So a pass of `DeepStackFreshJvmTest`'s 512 KiB child does not prove a 512 KiB stack.
- **Severity**: major. A stack check can flake, or pass on a larger stack than it claims to test.
- **Evidence**: the #111 implementer's hand-back (2026-11-15), `.logs/111-gate.log`,
  `.logs/111-measure-b.log`.
- **Change made**: none yet.
  - #111's own b cells run on the launcher main thread sized by `-Xss`. That thread is never served
    from the cache, and each cell first proves its size with a plain recursion count.
  - #113's calibration harness uses the same method for every cell. A virtual thread is the
    exception: it proves its depth with the same count.
  - Owed: a class-B ticket that makes `StackProbe` and `DeepStackFreshJvmTest` prove their thread's
    size, for example by running on a `-Xss` main thread of a child JVM. Spec 2b's final review
    lists this finding.
