# F-113 — `StackProbe` compares frame counts of different JIT tiers

- **Assumption**: `oracle/StackProbe`'s javadoc says that once the probe is warm, the thread under
  test and the fresh reference thread count the same compiled frame, so the two counts compare.
  `StackProbe.warm` runs the probe six times to get there.
- **How it fails**: six rounds do not fix the tier. In a scratch copy of the probe on JDK 25.0.5
  and this machine, a fresh 2 MiB thread counted 19 160 frames interpreted, 49 819 under C1 and
  83 033 under C2. C2 code arrived at round 3 in one run and at round 22 in two others.
  - In #199's full suite, `JqTestOracleTest.everyCaseRunsOnTheRunnersOneThread:120` saw 49 785
    frames, which is C1, against a reference of 83 033, which is C2. The floor is 4/5 of the
    reference, 66 424, so the test failed. Both threads were 2 MiB.
  - The test's `Jqj` is a fake. `StackUnits.RESERVE` cannot reach the probe, so #199's reserve edit
    changed only the JIT timing. The class passes when run alone.
  - The same pin is used in `DifferentialOracleTest:103` and `CompileCorpusTest:69-70`.
- **F-93 corrected**: #111's 31 115 frames against 83 031 lies between the interpreted count and
  the C1 count. It was this tier defect, not glibc's stack cache, which can only make a thread
  larger. F-93's cache half stays open: in scratch, a 1 MiB request was given a cached 2 MiB stack
  when no 1 MiB stack was cached.
- **Severity**: major. A stack pin flakes with the JIT and blocks a gate with no product cause.
- **Evidence**: in the #199 worktree, `.logs/199-green5.log`, `.logs/199-oracle-module-M.log`,
  `.logs/199-oracle-rerun.log` and `.logs/199-oracle-at-head.log`. The tier counts are the
  grilling-adviser's, 2026-11-16.
- **Change made**: owner, 2026-11-16 (Fable's recommendation). `StackProbe` takes a reference
  before and after the count on the thread under test. It judges only when the two references are
  equal, retries a bounded number of times, and otherwise fails loudly. The 4/5 floor stays and
  `warm` goes. A class-B ticket, written by the implementer, blocks #199. The pin must still fail
  on a 1 MiB runner thread: at one tier, a 1 MiB thread counts 47 % of a 2 MiB thread.
