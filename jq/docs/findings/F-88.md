# F-88 — the oracle runners do not run on a thread of 4× the declared stack

- **Assumption** (ADR-0046 "Where the stack is tested"): in-suite tests run on a thread of at least
  4× the declared `stackBytes`.
- **How it fails**: `DiffRunner`, `JqTestRunner` and the compile-mode hook (`CompileModes`) run each
  case on JUnit's own thread, whose size the launcher picks (about 1 MiB on Linux x64, unverified).
  That is 2× `Limits.cli().stackBytes()` (512 KiB), not 4×. Spec 2a's cases were shallow, so nothing
  showed it. #111's `diff/deep` cases and the `trampoline` run (`stackBytes` 0) would run on that
  thread.
- **Severity**: major (blocks #111's deep reds; a red seen on JUnit's thread may not be the red on
  the gate's thread).
- **Evidence**: #111 designer draft (C3); the grilling-adviser's ruling of 2026-11-15, which found
  the third runner (`JqTestRunner`) the draft missed.
- **Change made** (ruled by the grilling-adviser for the owner under the delegation of 2026-11-14):
  #111 is widened. Its first red and first commit run every case of all three runners on one fixed
  thread of `max(4 × Limits.cli().stackBytes(), 2 MiB)`; the floor covers the `trampoline` run's
  0. No case sets `stackBytes`. A separate ticket and `-Xss` in the pom were considered and
  rejected (one more gate and review, a collision with #109's edits to `CompileModes`; every
  module's tests would change).
- **Note (#111 red, 2026-11-15)**:
  - The json oracle's `JsonCorpus` runs a `DiffRunner` too. It is a fourth runner, and #111 moves
    it onto the same thread.
  - The thread is set at the oracle tests' runner factories, not in `CompileModes.cli/api`. Oracle
    main does not read jq-core, and #109's 256 KiB small-stack tests call `CompileModes` directly.
