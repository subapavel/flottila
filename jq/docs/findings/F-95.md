# F-95 — the provisional b does not cover a Collect-heavy descent

- **Assumption** (ADR-0046 #111): `b = 96` bytes per stack unit, the largest slope over #111's
  measured shapes, keeps every push-form run under the declared stack until the trampoline starts.
- **How it fails**: #114's IrDepthTest and OperatorChainTest children run 30 001 levels of PLAIN
  Calls whose bodies each descend through about 100 Collects. Each Call shows `units=107`. On a
  512 KiB thread with `Limits.embedded()` the run overflows between 20 and 50 nested Calls
  (`-Xlog:exceptions` names nested `CollectOp.run` frames), while U_f ≈ 4 096 − D_f lets about 38
  Calls run before the trampoline. So a Collect frame costs more than 96 B, and the run ends with
  `Stack exhausted` instead of switching (the #114 implementer's probe, 2026-11-15).
- **Severity**: major. A filter the ADR says reaches the trampoline ends in a STACK termination
  instead.
- **Evidence**: `.logs/114-green3.log` in the #114 worktree; the implementer's hand-back.
- **Change made**: none yet. #113's calibration matrix owns b. Its shapes gain a Collect-heavy
  descent (the #114 30 001-level filter), which is a red #111's constants do not fit. #114 merges
  after #113.
