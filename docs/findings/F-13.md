# F-13 — a closing trail drops whole timelines on writer overflow, silently

Date: 2026-10-28 · Task: P1-10d · ARCHITECTURE section: §8 write path (version 3.4)

- **Assumption in the document:** §8 — "Overload shows as a bounded queue filling, which is itself an alert; nothing is dropped
  silently"; F-10 — "a slow Postgres shows up as admission refusals".
- **How it fails in practice:** a sync flow with `keep` at c=64 holds a permit per message until its trail closes (Delivery:168);
  replies outrun trail closes, so up to maxInFlight trails close together and hand their rows to the node's one BatchingWriter
  (backlog 6400, BatchingWriter:76, Node:154). Rows past the backlog likely fail `PgMessageStore.record` with OverloadedException (the likely cause — FIX-66's designer
  confirms it, e.g. by logging the cause class at PgMessageStore:80)
  (PgMessageStore:79); `Trail.write` / the flush's `transform` (Trail:146, :157) swallow it — no log, no retry; only the
  `snapshotWriteFailures` health counter moves. The bodies were persisted, the timeline rows are gone. Most requests at c=64 were also not answered 200 (cause not split).
- **Severity:** major (monitoring is the product: an answered message without its timeline)
- **Evidence:** P1-10d native runs at e129c77, `NodeBenchMain --scenario sync --recording keep` c=64 (maxInFlight 64×64 =
  4096, NodeBenchMain:102/:278) failed 3/3 at settle: targets 7915 / 7178 / 6942 (target/P1-10d-node-sync-keep-r{1,2,3}.log;
  target = warm-up + 20 000 − failed, NodeBenchMain:412), so ≥ 13 085 of the 20 000-request window per run were not answered 200 — the
  harness does not split 503 / timeout / error (NodeBenchMain:486-515; FIX-67). Diagnostic run (target/P1-10d-f13-diag.log,
  -health.log, -db.log): 21 000 sent; `messages` 11 440 rows = 5 720 ids × (ingress, partner); `bodies` 15 240 rows = 11 440 +
  3 800; /health `snapshotWriteFailures` 3 800, constant to the end; no log line mentions overload or backlog. The counter is
  PgMessageStore:80 (any BatchingWriter failure; :76 throws OverloadedException at the 6400 backlog, Node:154). Observed: 3 800
  rows whose bodies persisted were never written and nothing logged them; which failure kind they were, and how many of the
  lost rows belong to messages answered 200, is not established. Diagnostic command: `NodeBenchMain --scenario sync --recording keep`, c=64, 20 000 + 1 000 warm-up, maxInFlight 4096, commit
  e129c77, native PG 16.15. 15 240 bodies / 2 = 7 620 messages ran, 5 720 have rows: 1 900 whole timelines (3 800 rows) lost.
  c=8 keep (20 000) passes with 0 failures.
- **Change made:** none yet — design goes to the designer (row FIX-66 [C]): an overloaded store write is backpressure, not loss
  (the trail keeps its permit and retries until the row lands, so overload surfaces as 503 admission refusals), and any row that
  is finally given up is logged per message at WARNING like a metadata-only row; the writer backlog and the flows' maxInFlight
  × rows per trail are sized together.
