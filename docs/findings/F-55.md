# F-55 — replay leaves Rail8: one id per message; retry and cancel of a failed one are the only operations

Date: 2026-11-15 · Task: FIX-262 · ARCHITECTURE sections: §1, §2, §4, §5, §6, §7, §8, §12–§14 (version 3.27)

- **Assumption in the document:** §1 says every message is "captured, searchable and replayable".
  §4's lifecycle table has a column "Replay" ("from any recorded step" for sync, "yes" for
  at-least-once). §4 and §6 describe `POST /admin/dlq/{id}/replay` as "a new copy with a new id"
  beside the same-id `/retry` (D-136). §6 Recording says "Replay from step N needs the recorded
  output of step N−1" and "Replay from any recorded step works after a restart". §8 promises
  "replay from any recorded step" and, on the message screen, "replay or resend from any step".
- **How it fails in practice:** the owner's use is one message under one id — find it, remove the
  cause, then retry it or cancel it — and he sees no use for replay: "Replay nechci, dle mě k tomu
  není use case a za 20 let praxe ani nebyl" (D-156, answering CONSIDER-25, where main and a side
  branch said opposite things). Both routes of the code mint a new id (`AdminServer.java:736`,
  `:755`), so one business message gets two histories, and a partner that dedupes on the id takes
  the copy for a second message.
- **Severity:** major — a documented mechanism goes. The intent stays: every message, step and
  payload is recorded and searchable, and a failed message is never lost.
- **Evidence:** D-156, the owner's word. The scout's list of every place that implements, documents
  or tests the operation (`agent/work/FIX-262-scout.md`); the designer's draft and the architecture
  advisor's pass over it (`agent/work/FIX-262-designer.md`, `agent/work/FIX-262-advisor.md`). Read
  in the code: the two routes (`AdminServer.java:410-413`); the same-id retry, untouched
  (`AdminServer.java:772-802`); every worker run starts from the recorded ingress row
  (`FlowWorker.java:641-646`); retention never removes a message, body or ref a DLQ row names
  (`Retention.java:31-45`). Nothing was run: this finding changes documents only.
- **Change made:** the document now; the code by the rows named.
  - Out: the operation — a copy of a message under a new id — in both forms. FIX-263 removes the
    two routes, FIX-264 `Replay`, `FlowBuilder.replay`, the deployments' replay pipelines and the
    simulation's replay action, FIX-265 `Envelope.REPLAY_OF` and the guards on it, FIX-266 the word
    in the documents outside ARCHITECTURE. Until then the document is ahead of the code.
  - Stays: the same-id retry (`POST /admin/dlq/{id}/retry`; D-135, the first half of D-136); a row
    per attempt (D-140); recording levels and per-step bodies; the journal's recovery after a
    restart; the worker's reruns; the simulation's "replay a seed" command and Kafka's log replay
    (§7, §11, §14 — other meanings of the word); the mapping trace on demand (§8 — it re-runs a
    mapping over a stored input and sends nothing).
  - Written in, from D-156 (which made the side branch's D-107, D-109 and D-106 the rule on main;
    the document cites D-156 only, because main's own D-106, D-109 and D-110 are other decisions):
    a message has one id from ingress to its end and one history; the operator's operations on a
    failed message are retry and cancel, both under that id; no cap on manual retries; a sync
    message and a cancelled one are never resent; a retry that succeeded shows in the message's history and
    nowhere else. A cancelled message counts as a failure of its flow: the architect's default,
    which the owner has not answered (ISSUE-10).
  - What recording is for now (§6): monitoring — the timeline, each step's body, search by key,
    the diagnosis of an error, "save as test case" — with one exception. The at-least-once ingress
    row and body are the durable save every run and every retry starts from, whatever the level.
    A retry resumed at the failed step (CONSIDER-13, accepted in D-142) will keep an envelope of
    the worker's own, never the recorder's, so "a retry needs no recorded step body" holds today
    and after it.
  - Cancel does not exist in the code. The document names it "(FIX-267, pending)" and promises no
    route and no storage. Nor does anything record who retried a message and when: `/retry` takes
    no actor and writes no audit row, and §8 says there is no message log. FIX-267 designs the two
    as one thing — the operator's events on a message.
  - Not carried over: "a retry refused 409, removed by retention". Retention never removes a parked
    message's rows, body or ref, so the case cannot occur; §6 says so and §7's F-20 exception for
    it is deleted. A lost body stays 409.
- **The operator's hole until cancel exists, stated exactly.** A parked message that never succeeds
  already stays for ever today: the DLQ replay removed its row only after the copy had succeeded
  (`Replay.java:154-159`), so such a row pins its message rows, bodies and refs before and after
  this change. What FIX-263 newly strands are rows `/retry` refuses and a copy could have
  delivered: a flow redeployed as sync or at-most-once; a park that is not the worker's step-1 park
  with an attempt (only `FlowBuilder.build()` or an old replay row writes one); a keyed row parked
  before V17. Stuck before and after: a flow that is not deployed, a lost body. The hole opens
  with FIX-263 and lasts until cancel's implementation row, after FIX-267's design, lands; it is
  accepted because there is no release and no production data, and no stopgap delete is built (it
  would be cancel without its record, then changed). Cancel must work for every one of these rows:
  it must need neither the deployed flow nor the body (FIX-267's brief).
