# F-11 — replay and retry run the flow version deployed now

Date: 2026-10-27 · Task: P1-09c2 · ARCHITECTURE section: §6 (version 3.4)

- **Assumption in the document:** §6 Recording — "Every message pins the flow, partner-directory and routing-table versions
  it ran with, so monitoring tells the truth and replay uses the same configuration."
- **How it fails in practice:** replaying on the pinned version means keeping every old package dir and building old
  versions on demand; and the main use of a DLQ retry is to rerun a parked message after the flow was fixed, which needs the
  version deployed now. A node also only runs one version per flow after a swap (D-063).
- **Severity:** major
- **Evidence:** P1-09c designer draft (D-067, rejected alternative "replay on the pinned old version");
  AdminServerReplayRaceTest#aFlowReplacedByTheRunIs409, DeploymentsProducersTest#aSwapClosesTheReplacedReplayOnceItsRunEnded.
- **Change made:** `POST /admin/messages/{id}/replay` and `POST /admin/dlq/{id}/retry` run the flow version RUNNING on the node
  now; the new message's snapshots carry the versions it ran with, so the timeline still shows which configuration each run
  used. A replay whose flow is not RUNNING here, or is swapped under it, is 409. Pinning still holds for the record.
- **ARCHITECTURE.md edit:** §6 Recording sentence and changelog row (3.4) at the P1-09c2 commit; F-8's row closed.
- **PROGRESS entry:** P1-09c2 marked `Deviation: F-11`
- **For the owner's review:** replay on the current version (rejected: replay on the pinned version — kept dirs, builds of
  old versions, and a retry after a fix would rerun the bug).
