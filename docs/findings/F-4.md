# F-4 — runtime wires the shipped components and steps through `Main`

Date: 2026-10-26 · Task: P1-09b · ARCHITECTURE section: §7, §12 (version 3.3)

- **Assumption in the document:** §7 discovers components and steps through `ServiceLoader`; §12 gives `flottila-runtime` one module dependency, `core`, and lets components depend on runtime "where a shared client is needed".
- **How it fails in practice:** the node must name what it runs. `runtime.Main` constructs the http component and the xslt/xpath and xsd steps, and `runtime.node` validates packages with `flottila-schemas`. ServiceLoader cannot replace `Main`: components need `Vertx` and the node's `BlobStore`, which `api` may not name (D-057). A component depending on runtime would now be a reactor cycle.
- **Severity:** minor
- **Evidence:** D-057 (b) design draft 2026-10-26; `COMPONENTS_DEPEND_ON_API_ONLY` already refuses component → runtime; no existing ArchUnit rule limits runtime's dependencies.
- **Change made:** runtime gains compile dependencies on schemas, component-http, step-xslt and step-validate. Two ArchUnit rules are added (an architecture change): no runtime class except `io.flottila.runtime.Main` depends on `io.flottila.components..` or `io.flottila.steps..`, and no runtime class depends on `io.flottila.components.mock..`. Runtime still reaches components and steps only through the SPI, and only at the wiring point. A separate node module stays rejected (one class, no rule needs it).
- **ARCHITECTURE.md edit:** §7 (ServiceLoader sentence replaced by explicit wiring in `Main`), §12 runtime and components rows; changelog 3.4. The `Component` javadoc's ServiceLoader sentence goes.
