# F-15 — The sftp row assumed a Vert.x SFTP client, a platform `BlockingConsumer` wrapper and a component-held Valkey lease

Date: 2026-10-28 · Task: P2-02 · ARCHITECTURE section: §7 Components (:239, :245), §7 State placement (:258), §13 Phase 4 (version 3.4)

- **Assumption in the document:** §7 named "Vert.x SFTP client" for sftp, said blocking SDKs implement
  `BlockingConsumer/BlockingProducer` wrapped by the platform, and put the "lease per endpoint in Valkey" on the sftp row;
  §13 placed sftp in Phase 4 while BACKLOG P2-02 and GATE.md check 5 need it in Phase 2.
- **How it fails in practice:** Vert.x 5.1.10 ships no SFTP client (no artifact in the resolved set). `BlockingConsumer`
  would be an interface with one implementation (against the "second implementation on day 1" rule). Components depend on
  `api` only and Valkey clients are banned outside runtime (ArchUnit Rules.java:51,104), so a component cannot hold a
  Valkey lease without a new api type every poller would repeat. GATE.md check 5 also asks that a kill "duplicates
  nothing", which a delete-after-save poller alone cannot promise.
- **Smallest change keeping the intent:** Apache MINA SSHD (Apache 2.0) on virtual threads the consumer starts; the lease
  is the node's (P2-02L), not the component's; duplicates are dropped at the save by a consumer-supplied file key
  (P2-02D); the sftp consumer moves to Phase 2, its producer stays in Phase 4. Durable save before delete is unchanged.
