# F-31 — batched completion widens D-101 (2)'s letter and keeps a delete per message (CORE-7)

Status: open — draft decision D-122, review at hand-over.

1. D-101 (2) / ARCHITECTURE §4 say a fenced node "stops committing completions before any other node may take over". With a shared
   batch (CORE-7), a completion handed over while the fence was open may commit after the fence closes — behind the statements in
   flight (at most 2) and the gathered backlog ahead of it (at most 8192 members, 256 per statement). Statements have no time bound,
   so nothing bounds that delay in time (review r1 corrected an earlier "one batch, plus 5 s"). It is safe: each row is deleted only while its attempts token is current, and a
   takeover's TAKE bumps it. The smallest change that keeps the intent: amend the sentence to "stops handing completions over; one
   already handed over commits only while its row's token is current".
2. The BACKLOG row said "no delete per message on the hot path". Unkeyed completions become one statement per batch, but every
   row is still deleted, and keyed rows keep one transaction per message (EOIO, D-116). A done marker or partitions would not remove
   the per-row write (rejected in D-122).
