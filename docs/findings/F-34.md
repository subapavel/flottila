# F-34 — ARCHITECTURE still described the pre-rework core (Kafka path, S3 and Postgres bodies, old levels)

Date: 2026-11-12 · Task: CORE-12 · ARCHITECTURE section: amendments, §3–§8, §11–§14 (version 3.14)

- **Assumption in the document:** v3.3 and its amendments put the monitoring ingest on a Kafka
  topic into ClickHouse's Kafka engine and the `/xi` door's durability in Kafka (amendment 1, §4
  Event bus, §7 Queues, §8 Write path, §14 item 1). They put bodies in a memory tier, an encrypted
  spool and S3, with Postgres `bodies` as the stop-gap durable tier (§3, §5, §7). ClickHouse payloads
  were "≤ ~256 KB inline, larger by S3 reference" (§8, §14). Recording levels were
  `all | ends | errors | off` × `keep | metadata-only` (§6), and retries were a backoff in the run
  plus a `maxAttempts` bound (§4, §6).
- **How it fails in practice:** the owner's brief `docs/CORE-REWORK.md` (approved 2026-11-03,
  D-103) replaces each of these. Kafka is an optional add-on (O-1). There are no bodies in Postgres
  (O-5): a node-local body journal holds them (O-6), with copies per environment (O-7). S3 is only
  ClickHouse's cold tier (O-4), and ClickHouse is fed by an own mover (Q-3). Sends retry on a
  schedule and are then parked (Q-7), and recording and retention work as in SAP PO (Q-9). Part of
  this is built already (CORE-4, CORE-6, CORE-7, CORE-9) and part is pending. A reader of
  ARCHITECTURE got the old core.
- **Severity:** major (documented mechanisms replaced: Kafka ingest, the S3 and Postgres body
  tiers, the levels; the intent, which is monitoring as the product, durable bodies by reference
  and replay, is kept)
