# F-18 — one-transaction durable ACK misses 5 ms at c=1 and costs throughput under load

Date: 2026-10-29 · Task: P2-08b · ARCHITECTURE section: §7 Sizing, §4 durable save (version 3.4)

- **Assumption in the document:** §7 Sizing named < 5 ms p99 at c=1 as the Phase 2 tuning target, reachable by "one commit,
  group commit, faster storage" (P2-08a/b, F-14, D-073 option 2).
- **How it fails in practice:** on this VM the ACK floor is not the WAL flush. After P2-08a (body, ingress record and work item in
  one transaction, D-082) the durable ACK p99 at c=1 is 8.80 ms (before 10.58 ms, −17 %); with pg_wal on tmpfs (FLOOR, not durable)
  it is still 8.04 ms, so faster storage alone cannot reach 5 ms here. `commit_delay` (214 µs, ½ the first fdatasync reading of 429 µs; the logged rerun's 381 µs would give 190 µs; c=8/64 only, not run
  at c=1) did not gain ≥ 10 % p99 on all 3 runs at either level (medians −6.7 % at c=8, +2.9 % at c=64; one c=8 run −16.1 %). The worker's and the recording's commits still share the WAL with the ACK (≈ 5 WAL syncs and ≈ 12
  transactions per message at c=1). Under load P2-08a is slower than before on every run at c=8 p99 (31.83 [31.68–33.07] → 41.38 [38.79–41.73] ms),
  c=64 p50 and c=64 throughput (median 833 [810–896] → 733 [687–736] msg/s, −12 %); c=64 p99 medians 146.00 → 163.29 ms
  overlap (before 143.69–164.26, after 157.38–166.39). The commit_delay and FLOOR cells ran after the main cells, not alternated. The likely causes are the ingress row leaving the BatchingWriter (one row per transaction
  instead of a multi-row batch) and each save holding a pooled connection for five statements plus BEGIN/COMMIT (pool 16); not yet
  isolated.
- **Severity:** major (a documented target is not met; a Phase 2 change trades load throughput for c=1 latency and atomicity).
- **Evidence:** bench/RESULTS.md "P2-08 — durable ACK, one transaction" (3 runs per cell, 20 000 msgs + 1 000 warm-up, medians
  [min–max]); raw JSON and manifest target/P2-08b-raw/ (not committed); pg_test_fsync (logged rerun, target/P2-08b-fsync2.log) in
  pg_wal on /dev/vda fdatasync 2628 ops/s (381 µs), /dev/shm 963 458 ops/s (first, unlogged run: 2331 / 779 901). Machine: 4 × "Intel(R) Xeon(R) Processor @ 2.80GHz" (model hidden), 16 GB, kernel 6.18.44-fc-v185,
  virtio-blk ext4, native Postgres 16, synchronous_commit on.
- **Change made:** none to the save (atomicity, D-082, stays). §7 Sizing restated with the measured numbers. FIX-95 [C] raised: recover
  the under-load throughput without giving up the one-transaction invariant (isolate the cause first: batching several concurrent
  intakes into one transaction, statement pipelining, a single-CTE save, pool size). No ISSUE for other hardware: the tmpfs FLOOR is
  above 5 ms too, so storage is not the limit on this machine.
- **ARCHITECTURE.md edit:** §7 Sizing sentence; changelog row 2026-10-29 naming F-18.
- **PROGRESS entry:** P2-08b marked `Deviation: F-18`.
- **For the owner's review:** whether < 5 ms p99 at c=1 stays a target (it would need the CPU/round-trip path cut, not storage), and
  whether the c=8/64 throughput loss of P2-08a is acceptable until FIX-95; reverting P2-08a was considered and rejected (it would give
  back the all-or-none save for a load regression that a batching intake can likely recover).
