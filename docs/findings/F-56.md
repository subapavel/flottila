# F-56 — toward the partner Rail8 is at-least-once: three sentences read wider than what is built

Date: 2026-11-16 · Task: FIX-270 · ARCHITECTURE sections: §4, §5, §13 (version 3.28)

- **Assumption in the document:** §4, XI quality of service: "exactly-once = at-least-once +
  `processed_ids` dedupe table" — read alone, exactly-once end to end. §5: "Every producer sends the
  message id to its partner as `x-message-id`" — read alone, true of every transport. §13, the
  Phase 2 gate: "Postgres failover during load with no loss or duplicate" — read alone, no repeat
  toward the partner either (`docs/GATE.md` check 5 says "duplicates nothing" of a kill between
  pick-up and delete). And no sentence told a partner or a flow's author that a message can arrive
  again; the nearest were §5's "so the partner can dedupe a rerun" and §4's "each attempt reruns
  from the ingress".
- **How it fails in practice:** the dedupe table makes the intake exactly-once only where the
  endpoint's component names a dedupe key — sftp's file key today, http names none — and only while
  retention keeps the key.
  Toward the partner the platform is at-least-once. The in-step retry (in every delivery
  mode), a scheduled retry, a run left to its lease after the partner received the message, and an
  operator's retry each send the message again under the same id, with nothing on the wire that
  marks a repeat. A partner that reads "exactly-once" does not dedupe and acts twice. The owner met
  it as the second delivery at a node's death and asked for its cause (2026-11-15). And a transport
  without headers has no carrier for the id: the sftp producer is Phase 4's.
  A failover under load fails the settle of the runs in flight, so each of them is sent again: read
  toward the partner, the Phase 2 gate's clause cannot be met as designed (D-160 (a), D-161).
- **Severity:** minor for §4 and §5 — the document is imprecise, the code follows the intent, no
  mechanism changes. For §13's gate clause the reading decides, and the reading is the owner's
  (ISSUE-11 item 6): read as "no message lost and none saved twice" it is imprecise only; read
  toward the partner it would be blocking.
- **Evidence:** the eight characterization cases of CONSIDER-24 (`FlowWorkerRerunWindowTest`, five;
  `RerunWindowIT`, three); the window measured in `bench/RESULTS.md` (2026-11-16);
  `FlowBuilderTest.aRetryableStepIsRetriedWithTheFlowsPolicyAndANonRetryableOneIsNot`;
  `SftpComponent.producer` refuses ("sftp has no producer before Phase 4"); D-160, D-161.
  A rerun past its bound is parked without running:
  `FlowWorkerFenceTest.aNodeKilledMidSendIsRerunInDoubtWithTheSameIdAndParkedPastMaxAttempts`,
  `FlowWorkerRetryTest.aRestartedRowTakenOverInDoubtIsParkedUnsent` (the same after a death between
  the two writes is not staged: ISSUE-11 item 5, FIX-271).
  Read in the code and not staged by a test, each marked so in the text: a stop past its deadline
  leaves its runs to their lease; only sftp names a dedupe key, so an http sender's resend after a
  lost answer makes a second message (CONSIDER-27).
- **Change made:** nothing is built or changed in the code. The document gains the paragraph *A
  message can arrive more than once* (§4); §4's sentence reads "exactly-once at the intake", where
  a dedupe key is named and kept; §5's reads "every producer whose transport carries headers — http
  and the mock today"; §13's gate clause and `docs/GATE.md` check 5 each carry a dated note with
  the reading "no message lost and none saved twice", marked `draft — review at hand-over`.
