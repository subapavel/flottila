# F-32 — an ordered flow's failure parks and continues; "blocks by default" is not built

Date: 2026-11-11 · Task: FIX-143 · ARCHITECTURE section: §4 XI quality of service (version 3.7)

- **Assumption in the document:** §4: "a failed message in an ordered queue blocks the queue by default (XI behaviour) or
  parks-and-continues per flow config".
- **How it fails in practice:** no config key exists; an item of a `partitionBy` flow is completed after a park at either
  site — a step failure parked during its own run (`ParkedException` → COMPLETE, FlowWorker :584-585, any attempt) or an
  item past `maxAttempts` parked at claim (:574/:583) — so the key's next item runs. A migrated XI EOIO interface silently loses its order
  after one failure. Only a failed park holds the key (D-055).
- **Severity:** major (review F7.4, high).
- **Evidence:** FlowWorker.java:557-592; FlowDefinition.java:78-85 has no failure key; FlowWorkerFastPathTest
  takenSuccessorPastMaxAttemptsParked (:607) and aParkedKeyedItemContinuesItsKey (:636) already pin park-and-continue;
  FIX-143 adds FlowWorkerTest.aKeyedItemParkedPastMaxAttemptsLetsTheNextItemOfItsKeyRun (review r1 corrected "no test").
- **Change made:** a `partitionBy` flow must state `onFailure: park` (parks and continues, today's behaviour);
  `onFailure: block` is refused at load until a durable barrier with release/discard exists (FIX-141); a missing key on a
  `partitionBy` flow is refused, so nobody gets park by accident. `onFailure` without `partitionBy` is refused (no key to
  block).
- **ARCHITECTURE.md edit:** §4 sentence and changelog row (FIX-143).
- **PROGRESS entry:** FIX-143 marked `Deviation: F-32`.
- **For the owner's review:** whether `block` should become the default once FIX-141 lands (XI behaviour), and whether
  requiring the key now is too strict for flows written before it.
