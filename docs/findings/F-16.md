# F-16 — The CLI cannot run flow tests in-process on api + testkit, and it is needed in Phase 2

Date: 2026-10-28 · Task: P2-03a · ARCHITECTURE section: §9 (:319), §11 (:418), §12 (:434, :435), §13 Phase 2/4 (version 3.4)

- **Assumption in the document:** §12 gives `flottila-cli` the dependencies api + testkit (D-021, ArchUnit
  CLI_DEPENDS_ON_API_AND_TESTKIT, Rules.java:97-99) and §13 places the CLI (validate, test, deploy, package) in Phase 4;
  §9 says `flottila validate` does a schema check, an XSLT compile and a dry build of the pipeline.
- **How it fails in practice:** GATE.md checks 2 and 8 (Phase 2) need `flottila deploy`, `flottila validate` and
  `flottila test packages/demo` in-process in seconds. An XSLT compile, a dry build and an in-process flow run need the
  shipped steps, components and the runtime's `Deployments` (check :744, build :929); none is reachable from api +
  testkit. A runner inside runtime would have to name the mock (against RUNTIME_NEVER_NAMES_THE_MOCK, F-4); spawning the
  runtime jar needs Postgres and is not in-process.
- **Severity:** major
- **Evidence:** scout and designer reports for P2-03 (2026-10-28): flottila-cli has no classes; no runner of `kind: test`
  documents exists; Deployments' dev constructor (:197) runs over core's in-memory stores without Postgres.
- **Change made:** `flottila-cli` is the outermost module: it may depend on every module (runtime, components incl. the
  mock, steps) and nothing depends on it (ArchUnit NOTHING_DEPENDS_ON_CLI replaces CLI_DEPENDS_ON_API_AND_TESTKIT; the
  store-client and mock rules keep binding cli). Runtime keeps no mock dependency, so a node still cannot load a mock
  binding. Components and steps are wired at one point, `Main.shipped()`, used by the node and the CLI. The CLI's admin
  client (`flottila deploy`, JDK `java.net.http`) is a tool talking to a node, not a flow's contact with the outside world;
  the Component SPI rule binds the node, not the tool. validate/test/deploy move to Phase 2; package and migrate stay in
  Phase 4. Split: P2-03a (validate, tree, deploy, packaging), P2-03b (the in-process test runner on virtual time).
- **ARCHITECTURE.md edit:** §11 :418, §12 :434/:435, §13 Phase 2 and Phase 4 sentences; changelog row (3.4).
- **PROGRESS entry:** P2-03a marked `Deviation: F-16`
- **For the owner's review:** whether the CLI as the one module allowed to depend on everything is acceptable (rejected:
  a separate `flottila-flowtest` module, which either duplicates Deployments' check/build or depends on runtime anyway).
