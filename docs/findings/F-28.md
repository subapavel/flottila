# F-28 — the error rate drives alerting and the SLA, and nothing defines what counts as an error

Date: 2026-11-14 · Task: CONSIDER-11 (raised by the owner) · ARCHITECTURE sections: §6, §9
(version 3.4)

- **Assumption in the document:** "error rate" appears twice and is defined neither time — once as
  a number on the per-flow screen (§9, `ARCHITECTURE.md:342`) and once as a business alerting
  signal beside SLA and DLQ growth (`:346`). The document treats it as self-evident. It is not: a
  rate needs a numerator, and the numerator is a policy about outcomes, not a measurement.
- **How it fails in practice:** the owner named two everyday cases on 2026-11-14 and the document
  answers neither.
  1. A target system is briefly unavailable. The step fails, the step's own retry (D-045) runs, the
     target comes back and the message is delivered. The run ends `OK`. Does the failed attempt
     count in the flow's error rate? If it does, an integration that is working correctly — the
     retry exists precisely for this — reports errors for every blip of every partner.
  2. The data is wrong at the recipient. The message lands in the DLQ, the recipient fixes their
     side, the operator replays it and it succeeds. A replay runs under its **own new message id**
     (§6), so the original message keeps its `FAILED` history for ever and the flow's error rate
     keeps counting a failure that was resolved. The owner's expectation, and SAP PO's behaviour,
     is that the overall picture is success, with the failure visible in the history.
  Both cases share one shape: a failure that was later made good by a mechanism the platform
  provides. The document has no word for that state, so every screen and every alert has to invent
  one, and they will not agree.
- **What is already decided and what is not:** D-105 (owner, the same day) settles exactly one of
  the three cases — a failure a user error handler handled is a successful run, out of the error
  rate, carried by a `handled` number of its own. It deliberately does not settle a retried attempt
  or a replayed message, because those are not handler behaviour and a decision made in passing
  would be worse than none.
- **Smallest change that keeps the documented intent:** define the numerator once, in §9, as a
  property of a **run's final outcome** rather than of any row in it, and give the resolved-later
  states their own numbers beside it the way D-105 gives `handled` its own. Three questions had to
  be answered to do that. The owner answered all three on 2026-11-14:
  1. **Answered — D-106.** A retried attempt that later succeeded is visible in the message's own
     history and nowhere else ("v detailech logu zatím"): no `retried` number on the per-flow
     screen, nothing in alerting, nothing in the error rate. The attempt rows stay in the timeline.
  2. **Held, and its premise rejected.** The owner said wait, and said why: a resent message cannot
     have a new id, it is still the same message. That contradicts §6 ("under its own new id") and
     the shipped admin answer (`{id, replayOf, ...}`), and it collides with the recording key
     `(id, step)`. It is therefore no longer a question about how to mark a resolved message: it is
     a question about message identity, which is bigger than this finding. Written up as **F-29**,
     open. CONSIDER-11g is `blocked` on it.
  3. **Withdrawn by the owner.** "SLA bych do architektury zatím nemíchal" — keep the SLA out of the
     architecture for now. The question was whether an SLA breach cares about the first failure's
     wall time even when a retry later succeeded; the owner has not met the case in twenty years of
     practice, so it is not worth a sentence in the document. Note for whoever reopens it: §9 still
     lists "SLA" as a business alerting signal (`ARCHITECTURE.md:346`) with nothing behind it. That
     word stays as it is; this finding does not touch it.

- **Severity:** major, now mostly settled. Not a defect in code: the platform behaves correctly in all three cases and
  nothing is lost. It is a hole in the definition of the number the product is sold on — monitoring
  is the product, and the one metric an operator looks at first has no written meaning. It will be
  decided by whoever writes the first dashboard query unless it is decided here.
- **Not in scope of CONSIDER-11:** the CONSIDER-11a..g rows implement handler behaviour and D-105.
  They must not quietly answer (1) or (2) on the way past; if an implementation forces one of them,
  that is a finding of its own, not a decision for the implementer.

## Two facts established 2026-11-14 (architect, by grep; not a design)

- **Nothing computes an error rate today.** `grep -rln 'errorRate|error_rate'` over `.java`, `.sql`,
  `.ts` and `.tsx` returns nothing. The number exists only in §9 prose and in the alerting
  paragraph. So this finding costs nothing to settle now and will cost a migration and a dashboard
  rewrite to settle later — it is the cheapest it will ever be.
- **The stored vocabulary is already three-valued and does not include a handled run.**
  `deploy/postgres/V2__snapshots.sql:7`: `alter table messages add column outcome text not null
  default 'ok';  -- ok | filtered | failed`. A message's final state is therefore stored on the
  message row, separately from its step rows. D-105 says a handled run is successful, which this
  column cannot express without either collapsing it to `ok` (and then the `handled` number has to
  be derived by joining the marker rows) or adding a fourth value.
  That choice belongs to CONSIDER-11d and is stated in its row; it is not one of this finding's
  three questions.
