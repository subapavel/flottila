# F-17 — The scheduler MXBean does not see a virtual thread blocked on a monitor

Date: 2026-10-29 · Task: P2-03b1 · ARCHITECTURE section: §11 flow tests (D-080) (version 3.4)

- **Assumption in the document:** D-080 (draft): virtual time may advance after two consecutive samples with
  `VirtualThreadSchedulerMXBean` mounted==0 and queued==0 and an unchanged fingerprint (timer, clock, mock records, queue size,
  DLQ rows, answer).
- **How it fails in practice:** since JEP 491 a virtual thread blocked on a monitor leaves its carrier; until the JDK's
  `VirtualThread-unblocker` queues it again it is neither mounted nor queued. The clock thread made that window likely: its
  fingerprint read the stores' synchronized `size()` and `fireDue` held FakeTimer's lock. One run in 100 advanced the clock early
  and printed a wrong flow time (1250 ms instead of 300 ms).
- **Severity:** major
- **Evidence:** target/P2-03b1-unit5.log (the wrong report line); implementer's reading of the JDK 25 VirtualThread source.
- **Change made:** the fingerprint takes no lock (timer calls, clock moves, clock instant, door deliveries, mock send counts,
  an answer-done flag set by `onComplete` — no store reads and no read of a Vert.x Future, whose accessors such as
  `isComplete()` are synchronized in Vert.x 5.1.10, javap FutureImpl); a thread inside a timer call counts as busy; quiet must hold for 1 ms of wall time under one
  fingerprint. 1000 runs (half under CPU load) gave identical reports. It stays a heuristic: a monitor-blocked thread whose unblock
  is delayed beyond 1 ms (a GC pause, or the OS descheduling the JDK's unblocker thread under CPU load) could still be missed. Exact detection needs a hook in core that sees each node thread's state;
  not done (CONSIDER-5).
- **ARCHITECTURE.md edit:** §11 changelog row (3.4) names F-17 and says the quiescence is a heuristic; D-080 amended.
- **PROGRESS entry:** P2-03b1 marked `Deviation: F-17`
- **For the owner's review:** whether a heuristic quiescence is acceptable for `flottila test`, or a core hook (a counted
  ThreadFactory through Runtime) should replace it — an api change, rejected for now as expensive to reverse.
