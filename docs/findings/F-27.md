# F-27 — the at-least-once hand-over ceiling (CORE-15 preview, code read)

Date 2026-11-05. Source: designer analysis (owner request), code read only, nothing measured; evidence bench/RESULTS.md
"CORE-15 preview" (6d5e4c3, raw agent/work/step-r2000.json). Status: open; drives the order below.

## What the preview shows
At 2 000 msg/s the backlog grew ~497/s for the first 30 s of the window (receipts ≈ 1.3–1.5 k/s), then ~1 766/s (receipts
≈ 170/s) from depth ≈ 17 k: the worker collapsed ~8×, it is not a flat ceiling. The 223/s settle figure is a bench artifact:
the settle probe runs `count(distinct id)` over 360 k messages every 5 ms (NodeBenchMain.java:904-911) — withdrawn.

## Cost per message (bench flow: unkeyed, recording off, payload keep)
Intake: journal force (fdatasync per round) before any statement; per group BEGIN | rows | COMMIT (1 WAL flush / group); per
member a work insert (2 indexes) and a KEEP upsert into body_refs (3 indexes). Worker: polls after every accept / finish / 1 s,
one claim in flight; claim = UPDATE … seq IN (index scan from the lowest seq … FOR UPDATE SKIP LOCKED), autocommit, not HOT at
fillfactor 100; timeline SELECT; journal read; send; complete = one DELETE in autocommit. ≈ 3 statements and ≈ 2 WAL-flushing
commits per message on the worker side, all on the node's one 16-connection pool shared with the intake.

## Causes (ranked; each to be confirmed by the named measurement)
- C1 write commits per message (WAL flush on the journal's disk): iostat, pg_stat_wal wal_sync(_time), pg_test_fsync.
- C2 CPU on 4 shared vCPU (bench JVM 1.35 cores; Postgres unmeasured): pidstat / BENCH_PG_CPU.
- C3 one claim at a time.
- Knee at ~30 s: disk credits, first autovacuum/plan flip, or checkpoint FPI surge — iostat, last_autovacuum, auto_explain, wal_fpi.
- D1 dead entries at the queue head (claim always scans from the lowest seq; autovacuum threshold grows with depth).
- D2 segment sweeper: per-segment unindexed `work` check (V12:53-54), O(segments × |work|) per 10 s pass, long snapshot.
- D3 pool queue amplification: slow statements lengthen the shared queue → saves wait → 503 and ACK p99.9 3.2 s.
- D4 location index (262 144 entries) evicts the queue head; FIND's fallback scans `work` without an index.

## Improvements (ranked by gain for cost; all keep D-082, D-101's fence, no loss)
I1 measure first (per-second pg_stat_statements / pg_stat_wal / xact_commit / n_dead_tup / iostat / Postgres CPU in the open
record; fix the settle probe). I2 `work` fillfactor ~70 + aggressive per-table autovacuum. I3 sweeper: one hashed pinned-set query
per pass or V12's deferred index. I4 pool by role (intake connections apart from worker and background jobs). I5 claim debounce
(interim). I6 CORE-7 batched completion (one DELETE … USING unnest, per-row fence kept). I7 P2-16 local hand-off (item written
leased inside the group transaction, no claim). I8 partition `work` by seq range (after I6/I7). I9 before EOIO benches: index
work(flow, partition_key, seq); size the location index or index work(id).
ACK p50 ≈ 10 ms at 500/s: two fsyncs in series (journal force, then the group's WAL flush, often behind worker commits) plus
pool wait. Toward the c=1 p99 5 ms target: overlap BEGIN + rows with the journal force and hold back only COMMIT (keeps "no row
commits before its record is forced", relaxes CORE-3 item 6 "no statement before the force" — owner's call), I4, I6/I7.
If pg_test_fsync p99 on the VM is above ~3.5 ms, 5 ms p99 is out of reach even with one fsync.
