# F-20 — retention cannot work by partition; it deletes by age in keyset batches

Date: 2026-10-29 · Task: P2-07 · ARCHITECTURE section: §7 Persistence tables (version 3.4)

- **Assumption in the document:** §7 and D-026 say "retention is a background job by partition".
- **How it fails in practice:** nothing is partitioned (V1–V9). A partitioned `messages` must carry the partition key (a time
  bucket) in its primary key; then `ON CONFLICT (id, step)` no longer decides first-wins per (id, step) (D-044) across buckets, and
  ids are random UUIDs, so no id range maps to a partition. Dropping partitions would also drop rows an open work item or DLQ entry
  still names.
- **Severity:** major (a documented mechanism is replaced; the intent — background, bounded, never on the hot path — is kept).
- **Evidence:** V1__init.sql:13-25 (PK (id, step), no partition); designer facts for P2-07 (packet agent/packets/P2-07.md); RetentionIT.
- **Change made:** `store.Retention` deletes whole messages older than the cutoff in keyset batches over new created_at indexes
  (V10), keeps any message a work item or DLQ row names, then orphan bodies, then `processed_ids` rows whose message is gone (D-088).
  Known limits, accepted: a replay's rows name the original's bodies by body_key, so once the original ages out the replay keeps
  its rows but not those bodies (P2-07b answers 409 "removed by retention"); an arrival whose dedupe key aged out with its message
  is accepted again; a replay or DLQ retry that parks under an aged-out original's body key can lose the race between its persist
  and its DLQ insert to retention's body delete — an open DLQ row whose body is gone (exception to D-062, closed by P2-07b);
  the batching snapshot writer can commit a step row after its work item completed, so an item held longer than maxAge can leave
  a message partial until the next run; the V10 indexes add insert cost to the intake transaction (measured in bench/RESULTS.md, P2-07).
- **ARCHITECTURE.md edit:** §7 Persistence tables sentence + changelog row (3.4).
- **PROGRESS entry:** P2-07 marked `Deviation: F-20`
- **For the owner's review:** whether time partitions (with a different first-wins key) are worth it at Phase 3 volumes, and
  whether replay should pin bodies (an index on messages(body_key) costs every insert).
