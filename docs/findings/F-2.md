# F-2 — the at-least-once durable save must not depend on the recording level

Date: 2026-10-19 · Task: P1-08 · ARCHITECTURE section: §4 (version v3.3)

- **Assumption in the document:** §4 lifecycle table, at-least-once: ACK "after the durable save, by
  the consumer before its irreversible ACK"; "Durable before processing: yes, with a save timeout".
  Below the table: "The durable save is the consumer's responsibility, never a pipeline stage. Stage 0
  'ingress' is a pure identity whose snapshot shows what arrived." §6 (recording) lets a flow set
  `recording.level: all | ends | errors | off` and `payload: keep | metadata-only`.
- **How it fails in practice:** the only ingress write in the tree is the `Recorder`'s stage 0
  (`FlowBuilder.java:102`), which is gated by `RecordingPolicy.records(0, …)` and whose store future
  is discarded (`Recorder.java:45–46`; `MessageStore.record` is documented as "the message path does
  not wait for it"). A flow with `mode: at-least-once` and `recording: {level: off}` or
  `payload: metadata-only` would ACK 202 with no durable row, or with a row that cannot rebuild the
  message (no body key). The sender would see 202 and the message would be lost on a crash — nobody
  would notice until the kill -9 ledger (P1-10) came back short.
- **Severity:** minor — the document's intent (durable save by the consumer, before the ACK) is
  kept; it was imprecise about the relation between the save and the recording level.
- **Evidence:** `DeliveryModesTest.anAtLeastOnceAckWaitsForTheDurableSave` (red first: a flow with
  `recording: {level: off}` must still have exactly one `ingress` snapshot with `bodyKey` after the
  202) and the scout's reading of `Recorder.java:45–46`, `FlowBuilder.java:102`,
  `MessageStore.java:16–17` on main 1e771d7.
- **Change made:** the delivery handler (`FlowBuilder.delivery`, D-049) records the ingress snapshot
  with its payload itself for at-least-once, awaits it, then enqueues the work item, and ACKs only
  when both are durable; the recording level governs the steps' snapshots only. The worker runs the
  pipeline without stage 0 for a message saved that way. Sync and at-most-once keep stage 0 as the
  policy-gated, not-awaited record it is today.
- **ARCHITECTURE.md edit:** §4, one sentence after the lifecycle table; changelog line 2026-10-19
  (version stays 3.3).
- **PROGRESS entry:** P1-08 marked `Deviation: F-2`
- **For the owner's review:** whether `payload: metadata-only` should be refused outright for
  at-least-once flows at load time (today the save keeps the payload regardless, silently overriding
  the setting for the ingress snapshot); the alternative — making stage 0 itself awaited and
  unconditional — was rejected because it would put the durable save back into the pipeline, which
  §4 forbids.
