# F-3 — no RequestScope wraps a delivery yet; the stop's cancel interrupts the message's thread

Date: 2026-10-26 · Task: P1-08c · ARCHITECTURE section: §4 (version v3.3)

- **Assumption in the document:** §4 runtime core: "A thin `RequestScope` (fork / join / cancel on
  virtual threads) wraps each message so a timeout or cancel stops all of its work". Row P1-08c:
  "in-flight deliveries complete within a stop deadline, then `RequestScope.cancel`".
- **How it fails in practice:** no production path opens a `RequestScope` per delivery — `Delivery`
  never opens one and `Admitted.run` has no production caller (designer's reading, 2026-10-26). A
  stop deadline therefore has no scope to cancel. `RequestScope.cancel()` interrupts a scope's
  children, never its owner (D-038), so even a per-message scope would not stop a sync pipeline that
  runs on the owner thread (D-049 b).
- **Severity:** minor — the intent (a cancel stops all of the message's work within the deadline) is
  kept: the cancel interrupts the message's own virtual thread, which wakes `await` and `Retry` and
  cancels the children of any scope opened on that thread (D-038 `join()`).
- **Evidence:** `DeliveryTest.aSyncDeliveryAwaitingAtTheDeadlineIsInterruptedAndAnswersARetryableNack`,
  `aCancelledSyncDeliveryLeavesTheCallersInterruptFlagClear`, `DeliveryStopPropertyTest`, runtime
  `DeliveryModesTest.aSyncHttpDeliveryCancelledAtTheStopDeadlineAnswers503WithRetryAfter`.
- **Change made:** `Delivery.stop(Duration)` (D-056) interrupts the in-flight sync / at-most-once
  message threads at the deadline and answers a retryable Nack; the per-message scope wrap itself is
  left open (no row; it belongs with the deadline/timeout work that needs a scope per message).
