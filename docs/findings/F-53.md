# F-53 — Order's key-list sort is uncharged, against F-48's reason

- **Assumption** (ADR-0037 "Ticks"): "its scratch key orders are not charged" (design approval O1).
- **How it fails**: F-48 later made a sort's compares tick because an uncharged sort of n long
  strings escapes the step budget (ADR-0008). `Order.java:192` still sorts each object's key list
  with `List.sort` and charges nothing, so comparing two objects of many long keys does
  O(n log n · key length) uncharged work.
- **Severity**: minor (no crafted case in 2a's tests; bounded by the document).
- **Evidence**: spec 2a review (#56, reviewer-standards, jq-core).
- **Change made** (#104, designer draft approved by the architect, 2026-11-14):
  - Ticking through jqj's merge sort. Reusing the key proof's sorted keys is rejected: they exist only on a read
    object's over-budget path, the right side's proof overwrites the scratch before the left list is used
    (ADR-0044, #95), and the count would depend on the proof's path.
  - The generic merge sort moves from `internal.op.Sort` to `internal.value.MergeSort`; `Sort`, `Built` and
    `Order` call it. One tick per compare, max(1, started KiB of the shorter key), as `keys`.
  - The order of the result does not change: one walk's keys are distinct.
  - ADR-0037 "Ticks", its status and its considered option are amended. Design approval O1 gives way to this
    finding, as it did to F-48.
  - Accepted: a constant comparison that now runs out of the compile's fold steps falls to the run, which
    gives the same value (O6).
