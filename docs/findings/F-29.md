# F-29 — a resent message is the same message, and the key `(id, step)` cannot hold two runs of it

Date: 2026-11-14 · Task: CONSIDER-11 / F-28 question 2 · Raised by the owner · ARCHITECTURE
sections: §6, §4 (version 3.4) · **Direction settled by the owner 2026-11-14 as D-107; the shape is
in class-C design. Nothing in ARCHITECTURE.md is changed yet.**

- **What the document says:** §6 (`ARCHITECTURE.md:276`): "a replay restarts the main pipeline from
  a recorded main step **under its own new id**". The implementation agrees: the admin answer is
  `{id, replayOf, from, outcome}` (`AdminServer.java:118`, `:588-589`), so a replay today is a new
  run with a new id that names the original in `replayOf`.
- **What the owner says (2026-11-14):** "přeposlaná zpráva nemůže mít nové id, je to pořád ta samá
  zpráva" — a resent message cannot have a new id; it is still the same message. Together with the
  owner's earlier sentence, "v logu v historii to bude zaznamenané", the requirement is: **one
  message, several runs, the whole history kept.** That is SAP PO's model and it is a reasonable
  thing to want: the business asks "where is invoice 4711", not "where are the three runs of
  invoice 4711".
- **Why the document chose otherwise, and the wall the owner's version hits:** the recording key is
  `(id, step)`, the primary key of `messages` (`deploy/postgres/V1__m1_schema.sql:25`). Message
  bodies are keyed the same way — message id plus step (CLAUDE.md, design rules; `BlobKey` is
  `[messageId, step, part]`). So a replay that keeps the id and re-runs step 2 writes a row and a
  body that already exist. The two requirements are therefore in tension **as currently keyed**:
  the same id and a kept history cannot both hold, because the second run's rows would overwrite
  the first run's — losing exactly the history the owner wants kept. A new id was not a whim; it
  was how the document avoided that collision.
- **Correction to my own first estimate (established by recon 2026-11-14, with line references).**
  I priced this finding before checking it and the price was wrong in three ways. All three make
  the change *cheaper*, so the correction matters to the decision.
  1. **An attempt dimension already exists.** `Envelope.ATTEMPT` is a prop (`Envelope.java:40`),
     set by the worker from the work item's second claim onwards (`FlowWorker.java:338`), and
     `Envelope.nextKey(part)` (`:90-96`) already encodes it into the body key's **part**:
     `part~2`. `ComponentContract.java:320-321` asserts that. So a redelivery of the same message
     id already writes its bodies under distinct keys, and the "same message, several runs" model
     is half built.
  2. **`BlobKey` probably needs no change at all**, which was the expensive half of my estimate.
     It is `record BlobKey(String messageId, int step, String part)` (`flottila-api/.../BlobKey.java:15`)
     and the attempt already rides inside `part`. The width I quoted was also wrong: only
     **one** interface mentions `BlobKey` in its signatures (`BlobStore`, `api/BlobStore.java:19`),
     with 3 implementations in production and testkit and about 20 test doubles — not "every store".
     What a component change would have cost is the 321 `BlobKey.body(...)` / `.attachment(...)`
     factory calls in tests; keeping the arity avoids all of them.
  3. **`replayOf` does not "disappear"** — it is persisted, as the prop `Envelope.REPLAY_OF`
     (`Envelope.java:33`, set at `Replay.java:250`) written into `messages.props` and `dlq.props`
     jsonb, asserted by `NodeIT.java:1590`. It is stored data on every row of the replayed run, not
     a field invented by the admin answer.
- **What a same-id replay would actually cost, on the facts.** Only two tables have a composite key
  involving `step`: `messages`, PK `(id, step)` (`V1__m1_schema.sql:24`), and `bodies`, PK
  `(message_id, step, part)` (`V6`). `bodies` needs **no migration**, because `part` already carries
  `~N`. `message_keys.step` and `work.step` are plain columns, and `processed_ids` keys on
  `(scope, key_hash)` — no migration for any of them, and no table has a foreign key to `messages`.
  So the shape is: one migration adding the attempt to `messages`' key; `Replay` stops stripping
  `ATTEMPT` from the carried props (`Replay.java:250-252` removes it today, which is precisely what
  makes a replay a first run under a new id); `Recorder` carries the attempt into the snapshot;
  `Snapshot` gains a field. One open sub-question: `dlq`'s PK is `id` alone (`V1:39`, `on conflict
  (id)` at `PgDlq.java:58`), so a replay that fails again cannot park a second row under the same
  id without a decision about what the DLQ row means.
- **A defect this uncovered, which is not the owner's question and is worse than it.** `messages` is
  written with `on conflict (id, step) do nothing` (`PgMessageStore.java:55`) and its rows carry no
  attempt. So when an at-least-once message is **redelivered** today — a lease expiry or a second
  claim, no replay involved — the second run's bodies land under `part~2` but its snapshot rows are
  **silently dropped**. The timeline then shows the first attempt only. That is the platform
  already failing the owner's own D-106 ("a retried attempt is visible in the message's own
  history"), by construction and without a word of warning. It needs a test to confirm against a
  real Postgres rather than a code read: row FIX-131.
- **Severity:** major, and cheaper than this finding first claimed. It blocks one row rather than many: CONSIDER-11g is set `blocked`,
  because its acceptance cites the new id and implementing it would bake in the premise the owner
  has just rejected. CONSIDER-11a..f do not depend on message identity and stay `ready`.
- **What I did not do:** change §6. The owner said wait, and the smallest change that keeps the
  documented intent cannot be chosen before the keying question is answered. Writing "the same id"
  into §6 while `(id, step)` is still the primary key would make the document describe something
  the platform cannot store.

## The owner's answer, 2026-11-14 (D-107)

The owner settled the direction rather than the mechanism, and narrowed the problem by removing a
capability instead of generalising the key:

- One id for the life of a message. Its own log says that it failed, that it was resent, that it
  was cancelled — the operator's scenario (a colleague hands over the id of a failed message; you
  find it, remove the cause, resend; it ends successful, or you cancel it and it ends cancelled).
- **Replay of a successful message goes out of the architecture**, and with it "replay from any
  recorded step". The only operations on a message are retry of a failed one and cancel of a
  failed one. Both SAP PO and CPI work that way.
- `cancel` does not exist in the codebase at all today — a grep over `core/flow` and
  `runtime/admin` found only timer cancellations. It is new surface, not a rename of something.
- What the platform supports today and the owner never asked for: `Replay.from` requires only that
  the previous step was recorded `OK` (`Replay.java:22` of the `:80-110` span), so a successful
  message can be replayed from any recorded step; `ARCHITECTURE.md:343` (§9, per-message screen)
  and the §6 changelog row of 2026-10-27 both promise it.

**The correction the owner needs, and the reason this finding does not close here.** Removing
replay-of-successful does not remove the need for an attempt in the recording key. `Replay.retry`
of a *failed* message re-runs steps that already have rows and collides on `messages`' primary key
`(id, step)` in exactly the same way — and `PgMessageStore.java:55` writes with `on conflict
(id, step) do nothing`, so the second run's rows are dropped silently rather than refused loudly.
The keying change is therefore required by the owner's own scenario, not by the capability being
dropped. FIX-131 confirms the same mechanism already costs the platform the history of every
redelivered run today.

## Corrected again by the design pass (2026-11-14), and closed except for two owner questions

My cost list above said "one migration adding the attempt to `messages`' key". That is incomplete,
and the design pass found what it missed. Recorded here so the next reader does not inherit my
undercount a second time:

- `messages_created_at` (`deploy/postgres/V10__retention.sql:5`) is `(created_at, id, step)` and
  must be dropped and recreated as `(created_at, id, attempt, step)`; the retention job's keyset
  cursor changes with it, in code.
- `Snapshot` and `Parked` gain a field each — public `api` / `core` record arity.
- Two store-contract javadocs state the behaviour being changed: `Dlq`'s "a second park … the first
  wins" and `MessageStore`'s "a second snapshot for the same (message, step) is ignored".
- Nothing else in my facts was wrong when the designer read the files.

The shape is D-108, draft. **The documents that promise what is being removed, all to be amended
in one pass and not silently:** §6 `:251` (both replay-from-step sentences), §6 `:277` ("under its
own new id", and the `Replay.from` sentence), §4 `:172` (sync: "from any recorded step"), §9 `:343`
("replay or resend from any step"), §12 `:519` ("replay/resend from the UI"), the §6 changelog row
of 2026-10-27, and `docs/GATE.md` check 7, which names replay. The tests that pin the removed
surface are listed in the CONSIDER-12 row.

**One thing the owner's model cannot cover as stated, and it is not a detail.** A sync
request/reply flow parks nothing — §4 `:172` is explicit that the error goes to the caller — so
once replay-from-a-step is gone, a failed sync message has neither a resend handle nor anything to
cancel. The owner's scenario ("a colleague gives you the id of a failed message") therefore holds
for asynchronous flows only. Either sync stays "the caller retries", or a final sync failure is
given a DLQ row that is a resend handle and not a queue, which is new behaviour. Answered by the owner 2026-11-14 (D-109): sync
stays "the caller retries" — a sync message is never resendable — so §4 `:172` keeps its
sentence about the error going to the caller and loses only the "from any recorded step" clause.

## Closed 2026-11-14

Every question this finding opened is answered: the direction is D-107, the shape D-108, and the
owner closed the last three points in D-109 (no cap on resends, a sync message is never resendable,
a cancelled message is never resendable — cancel is terminal). D-110 records the one point the
owner's answer did not cover, decided by me on his own principle: a cancelled message counts as a
failure of its flow, because the operator abandoned it and it was never delivered.

Implementation is CONSIDER-12 with its three children; CONSIDER-12a is `ready`. The document pass
that amends the seven places promising the removed surface is part of CONSIDER-12 and must carry a
changelog entry. ARCHITECTURE.md is deliberately still untouched: the direction is settled, but the
document changes belong with the code that makes them true, in one commit, so the repository never
describes a platform that does not exist.


## Addendum 2026-11-14 — the defect is worse than this finding first described it

FIX-131 came out of this finding's recon as "a redelivered at-least-once message loses the history
of every run but its first". That wording is too mild, and a second recon pass established why.

`Snapshot` carries no attempt (`Snapshot.java:36-38`); `Envelope.ATTEMPT` is only a props key
(`Envelope.java:40`), set on rerun ingress at `FlowWorker.java:338` and read by nothing in the
`record` package. Both stores then drop a repeated `(id, step)`: Postgres by `on conflict (id, step)
do nothing` (`PgMessageStore.java:51-55`), the in-memory store by `rows.putIfAbsent(new
Row(messageId, step), snapshot)`. So a second run of one id does not fail to be recorded — it is
recorded only where it reaches a step the first run never reached.

The consequence is a **stitched timeline**. If run 1 fails at step 3 and run 2 reaches step 7,
`timeline(id)` returns steps 1-3 from run 1 and steps 4-7 from run 2, in one step-ordered sequence.
The operator sees `FAILED` at step 3 followed by `OK` at steps 4 to 7 — a sequence no single run can
produce. A truncated history is obviously incomplete; a chimera reads as complete and is false. That
is the harm, and it is the thing D-108's `(id, attempt, step)` has to fix.

Measured, not reasoned: the test written for FIX-131 drives exactly this and `timeline(id)` came back
as `0 ingress OK`, `1 mark OK`, `2 enrich OK`, `3 check FAILED`, then `4 map`, `5 route`, `6 audit`,
`7 partner`, all `OK`, with the store's own counter showing two record calls each for steps 1, 2 and 3
and one each for 4 to 7. So run 2 did write the colliding rows and the store dropped them.

One correction to my own wording above, from that measurement: the seam is **not** entirely unmarked.
`Envelope.ATTEMPT` = 2 is present in the props of every row run 2 wrote and absent from every row run
1 wrote, and that asymmetry is the only mark there is. It does not rescue the timeline. The value sits
in a props map, which neither `MessageStore.timeline`'s contract nor any reading surface treats as a
run boundary, and it is a property of the rows that happen to have survived rather than a statement
about the rows that did not. It does mean D-108 has the value it needs already flowing to the store;
what is missing is a column that means it.

Two notes on how this went unnoticed. The Postgres half is already pinned by a passing test,
`PgMessageStoreIT:122-132`, under the name `aBatchCarriesManyMessagesAndDuplicatesAreIgnored` — the
drop is named as a feature, because for an idempotent batch replay it is one. And the `-Pit`
confirmation this finding asked for was unnecessary: with both implementations dropping by
construction, a real Postgres adds nothing a core test does not show. FIX-131 is therefore test-only
and needs no container; the premise is withdrawn in its row.

### The shape that is actually dangerous

The stitched timeline above needs run 1 to have left a `FAILED` row, and that needs the park to have
been refused. The common production event is different: a node dies in the middle of a run, the item
is left to its lease, and another worker picks it up. Writing the FIX-131 test exposed why that case
is worse, and the second case of that test measures it.

`Recorder.wrap` catches `Exception` only (`Recorder.java:84`, read and verified). A step that throws
an `Error` therefore leaves **no row at all** — not a `FAILED` row, nothing. Run 1's trail still
flushes the rows for the steps it completed, because the trail closes in a `finally`
(`FlowWorker.java` around `:344`). So for a crash at step 3, `timeline(id)` came back as: `0 ingress
OK`, `1 mark OK` and `2 enrich OK` from run 1, then `3 check OK`, `4 map OK`, `5 route OK`, `6 audit
OK`, `7 partner OK` from run 2. No row anywhere is `FAILED` and no row carries an error. The store's
counter shows `mark` and `enrich` recorded twice, `check` recorded once — by run 2 only, because run
1 never handed the store a row for the step it died on.

That timeline is indistinguishable from one clean successful run. The first shape at least shows an
operator something impossible and invites the question; this one shows nothing wrong at all, and it
is the shape a node crash produces. `Envelope.ATTEMPT` on steps 3 to 7 remains the only trace, in a
props map, and the rows of the run that actually died are simply not there.

The `Recorder.wrap` gap is a defect in its own right, independent of the key: a failure the timeline
cannot show is a product defect for a platform whose product is monitoring, and D-104 already made
the opposite call for `BatchingWriter` (`RuntimeException` and `Error` alike). It is FIX-133, and it
does not wait for CONSIDER-12.
