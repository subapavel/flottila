# F-12 — S3 becomes a start dependency of a deployed node

Date: 2026-10-28 · Task: P1-09c3b · ARCHITECTURE section: §9 (version 3.4)

- **Assumption in the document:** §9 "Deployed state lives in Postgres"; D-058 kept S3 off the Phase 1 path (blob tier at P2-05),
  so a node needed only Postgres to start.
- **How it fails in practice:** a restarted node with an empty data dir must get its packages back without a PUT (P1-09c done-when).
  The owner ruled out bytea in Postgres and nodes fetching git (git-first, option A), so the archive lives in S3 and every deployed
  node reads S3 at start.
- **Severity:** major
- **Evidence:** owner's decision 2026-10-27 (D-070); RestoreIT (Postgres + LocalStack); NodeIT aPutOnAnS3NodeStoresTheArchiveBySha256AndRecordsTheRow.
- **Change made:** Postgres keeps the record, S3 the archive by sha256; restore runs before the admin API; an unreachable S3 makes
  every package FAILED and /health DOWN (no retry), the hot path never touches S3 for deployments; a deployed env refuses the dir store.
- **ARCHITECTURE.md edit:** §9 Deployment mechanics and changelog line (3.4) at the P1-09c3b commit.
- **PROGRESS entry:** P1-09c3b marked `Deviation: F-12`
- **For the owner's review:** whether a FAILED-on-S3-down start should retry with a bound (CONSIDER-1) rather than wait for a restart or
  a PUT; the gate's compose stack has S3, so GATE check 1 is unaffected.
