# F-1 — testkit cannot depend on core

Date: 2026-10-18 · Task: P0-06 · ARCHITECTURE section: §12 (version v3.3)

- **Assumption in the document:** §12 module table: `flottila-testkit` "fake Runtime, contract
  suites, golden-test runner, protocol doubles, fake clock — depends on **core**".
- **How it fails in practice:** core's own tests need the fake clock and fake timer (the batcher's
  window flush is driven by them instead of `Thread.sleep`). A testkit → core dependency plus a
  core → testkit test dependency is a reactor cycle, which Maven refuses. Whoever builds core
  would notice at the first `mvn verify`.
- **Severity:** minor — the document is imprecise about the direction; no mechanism changes.
- **Evidence:** `mvn -B -ntp verify` with testkit depending on core and core's test scope on
  testkit fails with "The projects in the reactor contain a cyclic reference" (observed while
  wiring P0-06 before D-031; the committed tree has testkit on api only).
- **Change made:** `flottila-testkit` depends on `flottila-api` only (D-031). The in-memory
  implementations of core's store interfaces live in core itself (§12 already says so for
  MessageStore/WorkQueue/MonitoringStore). The golden-test runner and anything else that needs
  core's `FlowBuilder` goes to `flottila-cli` (depends on api + testkit, may add core) or a later
  module, never into testkit. The ArchUnit rule keeps "testkit may use core" only as an upper
  bound.
- **ARCHITECTURE.md edit:** changelog line 2026-10-18 / F-1, §12 row for testkit annotated; no
  version bump (minor).
- **PROGRESS entry:** P0-06 marked `Deviation: F-1 (minor)`.
- **For the owner's review:** whether the golden-test runner should become its own module
  (`flottila-testkit-flow`, depends on core + testkit) rather than live in the CLI; either keeps
  the cycle away.
