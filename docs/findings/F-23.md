# F-23 — `payloads(hash PK)` carries no bytes and races retention through its foreign key

Date: 2026-11-03 · Task: P2-07c · ARCHITECTURE section: §5, §7 (version 3.4)

- **Assumption in the document:** §5 "identical bodies across steps are written once in Postgres (`payloads(hash PK)` with
  `ON CONFLICT DO NOTHING`) and dedup is visible in monitoring"; the table list names `payloads(hash PK, size, …)`.
- **How it fails in practice:** since V2 bytes live in `bodies` keyed by message id + step (D-061, CLAUDE.md), so `payloads`
  holds hash and size only. `messages.body_hash` has a foreign key to it; the writer's `on conflict (hash) do nothing` takes no
  lock on an existing row, so once retention covered the table (P2-07c's other option), a delete of that row committed between the insert and the
  messages insert's FK check would fail the whole snapshot batch or intake save with 23503. The hash-only primary key also makes a second algorithm with the same
  64-bit value read back as the first one's algorithm. No product code reads the table; retention never deletes it (rows outlive messages).
- **Severity:** major
- **Evidence:** designer's read of V1:22 / V2, PgMessageStore (INSERT_PAYLOADS, TIMELINE subquery), Retention phases; the P2-07c
  red tests (MigrationsIT v11…, PgMessageStoreIT theTimelineAnswersEachRowsOwnHashAlgorithm, RetentionIT aRunLeavesNothing…).
- **Change made:** V11 adds `messages.hash_algorithm` (not null, default 'sha256-64', data copied from payloads), drops the FK and
  the table; the snapshot write is messages + message_keys only. Bytes still exist once (bodies, by reference); dedup stays
  visible as equal (algorithm, hash) across rows. Retention needs no new phase: the hash goes with its messages rows.
- **ARCHITECTURE.md edit:** §5 sentence and the §7 table list; changelog row 2026-11-03 (P2-07c, D-097).
- **PROGRESS entry:** P2-07c marked `Deviation: F-23`
- **For the owner's review:** V11 is a one-way format change and assumes a stop-all upgrade (no pre-V11 node on the database);
  rejected: keeping the table without the FK (needs a body_hash index or a seq scan per batch, no reader), DO UPDATE last_seen
  (a row lock per hot hash serializes batches), keeping the FK with key share + skip locked (cost for a table nobody reads).
