# F-100 — F-98's remedy was wrong: the value form never runs at U_f ≤ 0

- **Assumption (F-98)**: `SpecialiseExplainTest.overInlineCapStillSpecialisesRecurse` passes once #116
  is merged into #117's branch, because the value form ends each ladder activation when its `eval`
  returns.
- **How it fails**: the over-INLINE_CAP pipe ladder inlines f15 into main, so `callFreeDepth` is
  about 131 000. With `Limits.cli()`'s 512 KiB stack, `U_f ≤ 0`, and the whole filter runs on the
  trampoline driver. Heap forms never call `eval` (ADR-0047 #116), and on the driver a PLAIN call
  stays live while its consumer runs (ADR-0046 #116 C2). Measured on impl/117 fede05d: the least
  passing depth is 95 522 for OPTIMISED and 125 522 for CONSERVATIVE. The code follows the accepted
  ADRs; the test premise contradicted them.
- **Severity**: minor. It is a test premise, not a behaviour defect. jq-ref's 29 999 is not reached
  in-suite at depth 40 000 for this one shape.
- **Evidence**: the #117 implementer's diagnosis and the grilling-adviser's scratch probe, both on
  impl/117 fede05d.
- **Change made** (grilling-adviser W1–W3, 2026-11-15):
  - The 40 000 pin moves to an over-cap comma ladder, with `callFreeDepth` 33. Reference jq gives
    29999.
  - The pipe ladder keeps its explain assertions, and its run is pinned in both modes at 110 000.
  - The withdrawn expectation is issue #198, which waits for grilling.
  - #117 merges only with the test at VERIFIED_PASS.
- **Also** (W4): UnitWeightsPropertyTest compared steps across modes. Specialised copies drop
  ParamCall ticks by design, so the comparison now covers three compiles: full equality at cap 0,
  and at `SPECIALISE_CAP` steps at most CONSERVATIVE's.
