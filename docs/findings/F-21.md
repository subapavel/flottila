# F-21 — the JVM cannot measure a virtual thread's CPU time, so no step records CPU

Date: 2026-10-30 · Task: FIX-106 (found by GATE run 1, check 6) · ARCHITECTURE sections: §4 threading (:146), §8 write path (:284), §7 (:350, :355)

- **Assumption in the document:** §4 "per-step wall and CPU time on the snapshot … replace" the blocked-thread checker; §8 the
  snapshot carries "wall and CPU time"; D-044 `Meter` = the thread's CPU time through ThreadMXBean; docs/GATE.md check 6 "wall and
  CPU time per step". Also §7 (sandboxed scripts' CPU budget, per-extension circuit breaker on CPU) leans on the same measurement — marked open in §7.
- **How it fails in practice:** every step runs on the message's virtual thread, and on JDK 25.0.5 ThreadMXBean answers -1 there:
  getCurrentThreadCpuTime, getCurrentThreadUserTime, getThreadCpuTime(threadId) and getCurrentThreadAllocatedBytes (a probe, platform
  thread 772 ms, virtual thread -1). The deployed stack shows cpuNanos null on steps 1..n; step 0 is a hard-coded 0 (Recorder.java:62).
  No test noticed: InvoiceSyncRecordingIT:122 asserts `>= CPU_UNKNOWN`.
- **Alternatives probed (architect, 2026-10-30, JDK 25.0.5, 4 vCPU):**
  - the carrier's CLOCK_THREAD_CPUTIME_ID through FFM: readable (50 ms busy loop → 48.6 ms; 26.9 ms in a second run on a loaded VM), but a virtual
    thread that sleeps returns to the same carrier 80/100 and 88/100 times with other threads' CPU counted in (up to 6.9 / 3.9 ms over a 5 ms sleep), and no public
    API says whether a step unmounted → silently wrong numbers; rejected.
  - JFR `jdk.CPUTimeSample` (JEP 509): samples name the virtual thread (75 of 77 and 75 of 76 for a 300 ms busy virtual thread), period 2–4 ms →
    statistical; a sub-millisecond step reads 0 or one period, and samples arrive after the trail row is written. Suits per-flow
    aggregates ("slowest steps"), not a per-message figure → FIX-108 after the gate.
  - an own virtual-thread scheduler (internal API, --add-opens), process CPU deltas, steps on platform threads: rejected (unsupported
    API / not per step / contradicts the threading rules).
- **Severity:** major (a documented per-step measurement and a gate condition cannot hold as written).
- **Change made (FIX-106):** CPU is recorded as unknown (null) on every step, step 0 included (no fake 0); `Snapshot.cpuNanos`,
  `messages.cpu_ns` and the admin `cpuNanos` field stay, so a JDK that measures virtual threads fills them without an API change;
  a tripwire test goes red the day `Meter.system()` reads a virtual thread. Rows recorded before FIX-106 keep step-0 `cpu_ns` 0 (no
  migration; retention ages them out). D-044 amended by reference. Probe sources and output: target/F-21-probes.log (not committed;
  the -1 claim is also pinned by MeterTest's tripwire and InvoiceSyncRecordingIT).
