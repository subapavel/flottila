# F-33 — Splitting 16 connections into 5 + 11 starves the workers under recording all

Date: 2026-11-11 · Task: CORE-17 · ARCHITECTURE section: §4 "Postgres pools by role" (version 3.9)

- **Assumption in the document:** the D-130 draft took the intake pool out of the old total:
  `FLOTTILA_PG_POOL_SIZE` (16) is both pools together, the intake share is max(1, min(5, total/2)),
  so a node's workers kept 11 of the 16 connections they had before.
- **How it fails in practice:** at r2000 with recording all, the work backlog grows through the
  window (+25 k and +45 k of ≈ 360 k), while one shared pool of 16 stays flat. Acknowledged
  messages are still completed after the window, but a node at this rate falls behind steadily.
- **Severity:** minor (the documented mechanism, two pools by role, stays; only the default size changes)
- **Evidence:** indicative A/B/A/B and diagnostic runs, same host, PG 16.15, raw in
  `agent/work/CORE-17-ab/` and `agent/work/CORE-17-diag/`:
  - Defaults 16/5 (work 11): backlog +40.8 k.
  - 21/5 (work 16): −138. 16/2 (work 14): +217, but ACK p99 144 ms and 2 259 refusals.
  - 24/8 (work 16): +1 000, ACK no better than intake 5.
  - Intake sessions were never saturated (0–3 of 5 active). Work sessions wait on WAL write/sync.
  - Confirmed at the 21 default (B3/B4): backlog 0 / +60, ACK p99 51–57 ms against one pool's 98–104 ms.
  - All runs in bench/RESULTS.md, entry "CORE-17 indicative"; activity samples agent/work/CORE-17-diag/D*-activity.txt.
  - So the work pool's size sets the backlog, and the intake pool's size sets ACK latency.
- **Change made:** the intake pool is added on top of what the workers had. The default total
  becomes 21 (5 intake + 16 work). The share formula and both keys are unchanged. A node now opens
  23 connections (two pools, membership, listen) instead of 18.
- **ARCHITECTURE.md edit:** changelog row 3.9 states the 21 default and refers here.
- **PROGRESS entry:** CORE-17 marked `Deviation: F-33`
- **For the owner's review:** whether 23 connections per node is acceptable against
  `max_connections`. The alternative, keeping 16 total with intake 2, gives a flat backlog but
  more than doubles ACK p99, so it was rejected.

- **Owner's answer (2026-11-13, D-142):** 23 per node accepted, with the sizing rule in the docs and a re-measure at CORE-GATE (FIX-189).
