# F-5 — a redeploy stops a flow's old consumer before starting the new one

Date: 2026-10-26 · Task: P1-09d2 · ARCHITECTURE section: §9 item 3 (version 3.3)

- **Assumption in the document:** §9 Deployment mechanics item 3: each node loads the new flow version beside the old one; new messages go to the new version while the old one drains; a failed load leaves the old version running. §9 also keeps deployed state in Postgres.
- **How it fails in practice:** an inbound endpoint owns a socket; two versions cannot both own it without relying on Vert.x's same-port round-robin, which would hand new messages to the old version too. Building the new version beside the old one is possible; serving it beside the old one is not, for a socket-owning consumer.
- **Severity:** major
- **Evidence:** D-057 (b) design draft 2026-10-26 (rejected: per-flow sequential swap, port sharing).
- **Change made:** the whole package is validated and every flow built before anything stops, so an invalid package leaves the old version running (422). The swap then runs per flow, all flows in parallel: old worker stop; old delivery stop with the stop deadline and old consumer stop; new consumer start; new worker start. During the swap the flow's endpoint briefly refuses (HTTP 503 / connection refused, retried by senders). A failed start rebuilds the old version from its kept directory (500); a failed rebuild lists the flow FAILED. Deployed state is in memory until P1-09c persists it (V7, D-058).
- **ARCHITECTURE.md edit:** §9 item 3 changelog line; version 3.4.
- **PROGRESS entry:** P1-09d2 marked `Deviation: F-5`
- **For the owner's review:** whether a brief per-flow refusal window on redeploy is acceptable for Phase 1; the alternative (two versions behind one listener with a version switch inside the consumer) was rejected as a component-SPI change.
