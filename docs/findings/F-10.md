# F-10 — step snapshot rows wait for their bodies (run trail)

Date: 2026-10-27 · Task: P1-09k2 · ARCHITECTURE section: §8 (version 3.4)

- **Assumption in the document:** §8 — "a snapshot after every stage", written through the bounded batch queue, and
  "processing never waits for monitoring".
- **How it fails in practice:** D-064 keeps every recorded step body durably. A row written at hand-on would point at a
  body that is not yet durable; a crash then leaves a row whose `body_key` names bytes that never become durable, and a
  replay or the admin route reads nothing (or, with FIX-35's per-key rule, other bytes). Persisting at hand-on instead
  releases the local copy (D-061) so later steps of the same run would read their input back from Postgres.
- **Severity:** major
- **Evidence:** designer draft for P1-09k (D-066, agent/packets/P1-09k.md); FIX-35 (D-061 amended) — a key's durable
  bytes never change; PgBodiesReleaseIT (local copy released after persist).
- **Change made:** rows of a run wait in a per-run trail; at run end each distinct kept body persists once, then its row is
  written, keeping `body_key` only if the persist succeeded (trail rows only: the at-least-once ingress row stays as D-058, saved beside its persist). No step waits except the one whose snapshot crosses 256 buffered rows (it waits for that flush, and a sync reply behind it too); the worker's item completion, the sync permit
  the at-most-once landing and a replay or retry wait for the run's last flush (persists, then row writes), so a slow Postgres shows up as admission refusals (as §4's
  writer overflow). The sync reply waits for no persist except that mid-run flush; the durable ACK is unchanged.
- **ARCHITECTURE.md edit:** §8 body (the write path, its waits and the durable-body exceptions) and the changelog line (3.4) at the P1-09k2 commit.
- **PROGRESS entry:** P1-09k2 marked `Deviation: F-10`
- **For the owner's review:** rows of a long-running message appear in the live timeline only at run end (or when more than 256
  snapshots are buffered); rows whose key is already durable could go at once — rejected for now to keep one write path.
