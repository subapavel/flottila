# F-6 — at-least-once bodies are made durable in Postgres until S3 lands

Date: 2026-10-26 · Task: P1-09h · ARCHITECTURE section: §5 (version 3.4)

- **Assumption in the document:** §5 sends at-least-once bodies "direct multipart to S3"; §3 names S3 as the object store.
- **How it fails in practice:** S3 moved to P2-05. An accepted at-least-once message's bytes lived only in the heap tier or in a spool sealed with a per-start key behind a heap index; a restart, or another node claiming the shared work item, could not read them, though the Postgres snapshot said "saved". `payloads.body` is never written (D-041).
- **Severity:** major
- **Evidence:** P1-09b review (Node clears the spool and draws a new key at start); designer draft 2026-10-26 (`Replay.rebuild` → `Body.open()` "no object stored under" after restart).
- **Change made:** api `BlobStore.persist(key)`; the at-least-once save awaits it beside the ingress snapshot under the save timeout. Bodies up to `FLOTTILA_BLOB_DURABLE_MAX` (1 MiB) move into Postgres `bodies(message_id, step, part, bytes)`, keyed by message id + step, read by key on an index miss. Above the bound S3 takes over in P2-05; until then a deploy refuses such a flow (422). D-058.
- **ARCHITECTURE.md edit:** §5 sentence; changelog 3.4.
- **PROGRESS entry:** P1-09h marked `Deviation: F-6`
- **For the owner's review:** whether 1 MiB is the right bound for Phase 1's at-least-once flows; S3 pulled forward was rejected (a new service on the gate path, a PUT per durable ACK against the 5 ms p99), as was persisting the spool key (bytes stay node-local while the queue is shared).
