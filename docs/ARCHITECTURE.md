# Rail8 Architecture v3.3 — Consolidated Summary & Implementation Plan

Oct 17, 2026 · @Pavel

## 1. Purpose

Rail8 is an open-source enterprise integration platform where monitoring is the product: every message, every step and every payload is captured and searchable, a failed message is retried or cancelled under its one id (D-156; cancel is FIX-267, pending), and the runtime also delivers messages reliably and fast. This document consolidates the v3.2 architecture (Sept 15, 2026), the 15 accepted findings of the §4 runtime review, and the October 2026 decisions (Java/Vert.x confirmed over Elixir and Rust; virtual-thread-per-message; byte budgets; structured concurrency; policing replaced by measurement). It is the base for v3.3 and for the implementation plan in section 13.

Three things it is not: it does not repeat the rationale behind rejected options (v3.2 §2 keeps that), it does not define the flow config JSON Schema (first deliverable of the plan), and it does not describe the control-plane UI screens in detail.

## 2. Decisions that are final

The language question is closed: Java 25 on Vert.x 5.1, one runtime, no second language in the core. Elixir/BEAM and Rust were examined in October 2026 and rejected because the Java mapping worker is unavoidable (migrated PO/CPI Java and Groovy mappings, JCo, Saxon), which made a two-language platform complexity without a matching gain.

## 4. Runtime core

One message = one plain JDK virtual thread, bounded per flow; verticles exist only to own sockets and timers. This replaces the v3.2 "VIRTUAL\_THREAD verticle per flow" model, which the §4 review showed interleaves only at `await()` and has no in-flight cap.

**Threading**

- Endpoint verticles (HTTP, XI) and pollers (a timer firing a round on a virtual thread, D-076) accept input and hand each message to `Executors.newVirtualThreadPerTaskExecutor()`; they never run a pipeline themselves. A poller starts a round only while its node holds the endpoint's lease (D-083); a stop at a lost or lapsed lease waits for the file in flight, so a takeover may overlap it by that file: a duplicate, never a loss; a consumer that names a dedupe key (`dedupeBy`, sftp `sftp.fileKey`) turns that duplicate into an `Accepted` naming the first message (D-084).
- Admission per flow = a semaphore that counts **requests and bytes** (the body's size is known before the run: `Body.size()`). Over the limit: HTTP 503 + Retry-After, SFTP poller pauses, a Kafka consumer (the optional add-on, CORE-REWORK O-1) stops polling. Memory, not thread count, is what backpressure protects. To be (OPS-2, pending; OPERATIONS-BRIEF §3): beside this per-flow admission the log records get one buffer for the whole platform; when it is full, intake stops for the whole platform — every door refusing as above, HTTP 503 + Retry-After and pollers paused — and the alert names the interface that writes most (OPS-8, pending); what the stop means for one node's journal, for work in flight and for a retry is OPS-2's (§8 Write path and loss contract).
- Concurrency per target system (D-099): every producer call to one target (`Component.target`, `scheme://host:port`) takes a node-wide permit (one `Targets` per node, shared by every package and flow version; `RAIL8_TARGET_*`, `GET /admin/targets`) that counts **requests only** (the body is already in its flow's admission) and is held only for the outbound send, inside the step's retry; a permit not granted within `maxWait` is a retryable `NackException` — sync 503 + Retry-After, at-least-once the step's retry, then a failed attempt of the flow's schedule (D-135), then park, at-most-once dropped and logged. Defaults 16 calls, 5 s, finite. A wait is bounded by the earlier of `maxWait` and the message's deadline (FIX-115, D-100).
- Two executors only for work: the virtual-thread executor (default for everything) and a small **platform-thread pool for JCo/JNI**, because JNI still pins carriers on JDK 25; a client library's own transport I/O threads (Vert.x event loops, the Kafka network thread of the add-on, MINA SSHD's NIO2 pool sized ≤ 2) are not executors and never run a pipeline (D-076). CPU-bound steps need no pool; the per-flow cap (default cores × 2 for CPU-heavy flows, higher for I/O flows) is the limit.
- `ScopedValue` carries message id, tenant, trace id and deadline through every step without threading them through signatures: FlowBuilder binds `MessageContext` at the head of every pipeline it builds, with the deadline = the run's start + the flow's `delivery.timeout` (default 30 s), fresh per run (D-100); the `tenant` field holds `default` (`MessageContext.DEFAULT_TENANT`) and the trace id is the message id. To be: there is no tenant level, and what becomes of the field goes with OPS-9 (pending; OPERATIONS-BRIEF §5; §9 Teams and permissions); the trace id is taken from the sender, stored on the message, passed to the receiver and searchable (OPS-8, pending; OPERATIONS-BRIEF §4); and the bound `MessageContext` is the brief's direction for attributing a line of standard Java logging to its message and step, the hook to be verified at design (OPS-4, pending; OPERATIONS-BRIEF §2.10; §8 Author voice and mapping trace, §14). A thin `RequestScope` (fork / join / cancel on virtual threads) is to wrap each message so a timeout or cancel stops all of its children — not yet on deployed paths: nothing cancels at the deadline (FIX-117) and steps do not see it (FIX-118). Producers do (D-113): a `to` hands the producer a live `Deadline` (`send(e, d)`), the time left until the message's deadline — on a worker run the earlier of that and the node's fence — and refuses a send with no time left (retryable Nack, nothing started); the producer cuts a send still open when the deadline, re-read, has passed (http resets the request); swap in `StructuredTaskScope` when it leaves preview.
- I/O goes through Vert.x clients with `Future.await()`; blocking SDKs run directly on the virtual thread (that is the point). The blocked-thread checker is not relied on: per-step wall time on the snapshot and a "slowest steps" view replace it; CPU time per step only where the JVM measures the thread, which it does not for a virtual thread on JDK 25, so `cpuNanos` is null on every step recorded since FIX-106 (F-21). CPU per flow and step comes from JFR CPU-time sampling instead: with `RAIL8_CPU_SAMPLING=<period>` the node wraps each step in a JFR event `dev.rail8.Step` (without it no step is wrapped: sampling off costs nothing, owner 2026-11-03) and matches every `jdk.CPUTimeSample` of a virtual thread to the innermost step event on that thread — statistical (±10 % from 1 000 samples of a step while at most 5 % of the samples are lost — the endpoint shows both), Linux only, per node, in memory, read from completed recordings every 5 s (so 5–10 s behind; a live JFR stream loses virtual-thread constants on JDK 25, F-22), never per message (FIX-108, D-094).
- One JVM per node. An out-of-process worker (same Step SPI, bodies by reference, HTTP/gRPC) is an installation option for untrusted mapping jars, not the default.

**Node lease and fence** (D-101 amended by D-112, F-28): every node holds one lease in the `nodes` table (V14), joined at start as a new incarnation (epoch + 1) — its previous incarnation's unheld items rerun only after that incarnation's `lease_until` — and renewed every `RAIL8_NODE_LEASE_RENEW` (PT5S, at most a quarter of `RAIL8_NODE_LEASE`, PT30S) on a connection of its own — one statement per renew, none per message, at most one in flight. Its fence is open until half a lease after the send of its last renew that answered renewed, measured on the node's monotonic clock; a worker checks it before every claim and every hand-off reservation (closed, it claims nothing and reserves no slot), and at-least-once runs check it before each producer send, before every park and every defer, and before every complete, same-key take and hold. A fenced node stops handing completions over; a completion handed over while the fence was open joins its node's batch (D-122) and may commit after the fence closes — behind the statements in flight (at most 2) and the gathered backlog ahead of it (at most 8192 members, sent 256 per statement); statements have no time bound, so nothing bounds that delay in time — but only while its row's attempts token is current, which a takeover's hand-out bumps (F-31, amending D-101 (2)). A fenced send fails with `FencedException`, which is never retried and never parked: the item stays unsettled for whoever runs it next. A send is bounded by the fence too (D-113): its deadline is the earlier of the message's and the fence's end, and a timer at the fence's end re-reads it — renewed, the run waits on; closed, the run stops waiting with `FencedException` (the send's target permit is held until its own future settles), and a producer failure that lands while the fence is closed is a `FencedException` carrying it; a superseded node ends its sends by fail-stop; an at-least-once failure met under a closed fence is neither deferred nor parked — no DLQ row, the row left unsettled to its lease (the worker's pipeline has no per-step Parking since D-135). A node releases a peer's expired row only while its own fence has been open for a whole lease; a released (or re-joined) node's next renew finds no row and the node exits (fail-stop). Sync and at-most-once runs are not fenced. In doubt is derived, not recorded: a hand-out of a row an earlier holder left unsettled counts a doubt (`work.doubts`) and an attempt (D-055); the rerun keeps the message id and is a failed attempt of the flow's schedule (`delivery.retries`, CORE-REWORK Q-7, O-9; D-135, CORE-14a): a failed attempt sets its row's `available_at` (database clock) to now plus the schedule's wait before that attempt (`interval` × `multiplier`^(k−1), at most `maxInterval`) and clears its holder, under its token and an open fence; the row keeps its seq, id and journal reference, so it heads its key and pins its segment; no thread waits; any node that may claim it runs it when due; a takeover hand-out counts as an attempt and runs at once; a JVM `Error` in a run, like a crash, is no failed attempt: the row is left to its lease and its rerun is in doubt, bounded by the same count. MALFORMED, INVALID and a final NACK park at once; after count + 1 attempts the ingress is parked at step 1 with its `attempt`. Each attempt reruns from the ingress, so earlier `to` steps are resent under the same id (O-9; CONSIDER-13). What that means for a flow's author and for a partner: *A message can arrive more than once*, below. `POST /admin/dlq/{id}/retry` re-enqueues a parked ingress under the same id for one more attempt, in one transaction (the DLQ row deleted, a step-1 work row inserted with `max_attempts` = k + 1, its body reference copied, its partition key kept by the DLQ row since V17); a keyed flow's row parked before V17 answers 422, a flow not deployed on the node or a body no longer kept 409 (D-135 [CORE-14b], D-136); the 422 texts say why and name no other route (FIX-263, pending) — a row `/retry` refuses has no operation until cancel exists (F-55; FIX-267, pending). A derived doubt over-reports: a dead node's in-flight items and items left unsettled by a fenced or leaving run count one whether or not they were sent. Until CORE-5 a node states at start and in the admin health that its at-least-once items wait for it while it is down (one journal copy), and when no other member is live.

**A message can arrive more than once** (D-160, D-161; ISSUE-11 items 2–4, stated here as their defaults; F-56; FIX-270; `draft — review at hand-over`: a public statement to partners). A partner can receive the same message again. Every repeat the platform sends carries the same `x-message-id` as the first send (§5, D-113) and nothing on the wire marks it as a repeat: no attempt number is sent (D-160 (d)), and the second request's headers equal the first's (`RerunWindowIT.theSecondRequestCarriesTheFirstRequestsHeadersAndNothingSaysAgain`; in the staged flow — one `to` that receives the ingress body — the rerun's envelope differs from the first run's only by its attempt prop, `FlowWorkerRerunWindowTest.theRerunsEnvelopeDiffersFromTheFirstRunsOnlyByTheAttemptProp`). The causes, the routine ones first. (1) The in-step retry (§6), in every delivery mode, under the flow's `retry`: a step marked `retryable` whose send failed after the partner had acted — it timed out (`timeoutMs`), or its answer was lost — is sent again inside the same attempt (`FlowBuilderTest.aRetryableStepIsRetriedWithTheFlowsPolicyAndANonRetryableOneIsNot`; in a sync flow the CLI's `sync-order` case "partner down", in an at-least-once one `async-order`'s). (2) A scheduled retry of an at-least-once flow after a failed attempt: each attempt reruns from the ingress (D-135), so every `to` step before the failure is sent again — a split's children too, each under its own id — and so is the failed `to` itself where the partner had acted before it failed — a send cut at its deadline among them: inside the attempt a `to` past its deadline is not started again (`FlowBuilderSendDeadlineTest.aSendPastTheMessageDeadlineIsNotStarted`), the next attempt has fresh time and sends it; resuming at the failed step is CONSIDER-13, pending. (3) An at-least-once run left to its lease after the partner received the message: the node died; its fence closed on the send or before the complete (D-113, F-28); its settle failed — the node lost its database, which is what `RerunWindowIT` stages (`FlowWorkerCompleteUnkeyedTest.aFailedCompleteUnkeyedFailsTheRoundAndLeavesTheItemToItsLease`); a JVM `Error` or an interrupt ended the run (`FlowWorkerRetryTest.anInterruptedRunIsNotDeferred`); or its stop ran past its deadline (read in `Deployments.drain`, not staged by a test). The message then runs again from the ingress as one more attempt — unless that hand-out is past its bound (count + 1 attempts; after an operator's retry, that one attempt): it is parked without running, so the message is listed as failed although the partner has it, and an operator's retry sends it again (`FlowWorkerFenceTest.aNodeKilledMidSendIsRerunInDoubtWithTheSameIdAndParkedPastMaxAttempts`, `FlowWorkerRetryTest.aRestartedRowTakenOverInDoubtIsParkedUnsent`; the same park after a death between the two writes named next, and what the history then shows, are not staged: ISSUE-11 item 5, FIX-271). A run ends in two writes, its rows and then the delete of its work row, and they stay two (D-160 (a), D-161). A death before the final row is committed leaves one finished run in the history (`FlowWorkerRerunWindowTest.aNodeDeadAfterThePartnerAnsweredAndBeforeItsRowsAreRecordedIsRunAgainAndTheHistoryShowsOnlyTheSecondRun`); a death between the two writes leaves two (`FlowWorkerRerunWindowTest.aNodeDeadBetweenItsFinalRowAndItsUnkeyedCompleteIsRunAgainAtTheLeaseEndAndThePartnerGetsTheIdTwice` and its fast-path twin; `RerunWindowIT.aNodeThatDiesBetweenTheTwoCommitsIsRunAgainByAnotherNodeAndThePartnerGetsTheIdTwice`); once the work row is gone nothing runs again (`FlowWorkerRerunWindowTest.aNodeDeadAfterItsCompleteIsNotRunAgainAndThePartnerGetsTheIdOnce`). Measured on one host under the kill ledger's load — a passthrough flow, 8 messages at a time, about 1 000 a second (`bench/RESULTS.md`, CONSIDER-24): 4.2–4.5 ms on average from the final step's end to the final row's commit, then 2.4–2.5 ms to the delete, the largest single values 40–53 ms; the completion statements have no time bound (the lease paragraph above), and the travel of the partner's answer comes on top of the first part. The platform cannot close the first part — the partner's system and the platform's database do not commit together — and nothing skips a run that had already finished: that would be the last-step case of CONSIDER-13, pending. Until CORE-5 a dead node's items wait for that node's restart, so this repeat can come long after the first send. Whether a second run can start beside a living, slow one is open (FIX-273). (4) An operator's retry of a parked message (`POST /admin/dlq/{id}/retry`): it has no limit in number or in time (D-156). So a partner's memory of ids has no safe expiry. For a partner: one that must not act twice recognises a repeat by `x-message-id`. For a flow's author: a partner that cannot do that will sometimes act twice, so the flow calls an operation that is safe to repeat — or delivers at-most-once with no step toward that partner marked `retryable`, which loses a message instead of repeating it. Limits. The id travels in a header: http carries it, and the mock; a transport without headers has no carrier yet — the sftp producer is Phase 4's and names its own. And a sender's own resend can arrive under another id, which the partner cannot recognise: an at-least-once sender's resend is saved once only where its endpoint's component names a dedupe key (D-084) — sftp's file key today; http names none — and for as long as retention keeps that key in `processed_ids`; without a key, a sender whose answer was lost and that sends again makes a second message — today every http sender's resend after a lost 202 (read in `Component.dedupeBy` and the two components, not staged by a test; CONSIDER-27); a sync caller's retry and an at-most-once sender's resend are always new messages (the lifecycle table: the client owns the retry). The platform never reruns a sync or an at-most-once message after its failure (D-156); only its `retryable` steps repeat, inside the one run.

The durable save is the consumer's responsibility, never a pipeline stage (on Postgres it also inserts the consumer's dedupe key into `processed_ids` first, in the same transaction; a key already seen writes nothing of the arrival and answers the first message's id, D-084; concurrent saves commit as a group in one transaction, a duplicate's neighbours unaffected, D-109): only the consumer knows what its ACK is and whether it is irreversible. Stage 0 "ingress" is a pure identity whose snapshot shows what arrived. For at-least-once the save *is* the ingress snapshot with its payload, written and awaited by the consumer's delivery handler before the ACK — its body forced into the node's body journal first, then on Postgres in one transaction with its row and its work item carrying the body's journal reference, no body bytes in Postgres (D-082, D-105; CORE-REWORK O-5, O-6) — whatever the flow's recording level says: the recording level governs the steps' snapshots, never the durable save (F-2). The worker then runs the pipeline without stage 0, which was recorded at the save.

**Body journal** (D-105, CORE-4; CORE-REWORK O-5, O-6, §3): message bodies live on the node's local disk in its body journal — append-only segments of encrypted journal records (per-tenant key, D-106: the tenant position holds `default`; it goes with OPS-9, and a key per team is open, §14), written with one `fdatasync` per group of journal records, sealed and never rewritten — and Postgres keeps only the reference (`body_refs`, the work item's `body_*` columns, V12); a body is keyed by message id + step. A node claims only the items whose body its journal holds; a crash between the force and the commit leaves unreferenced bytes that go with their segment, and the sweeper deletes a segment once nothing pins it (no row-level delete, CORE-4d): a work item's ref and a DLQ row's kept ref pin it, a kept step body's ref only while it is younger than `RAIL8_JOURNAL_KEEP_MAX_AGE` (PT1H, PT1M..P1D) — the interim rule (D-105, CORE-3 item 14); past that age its segment may be swept. A kept ref is to pin its segment until its body has moved to ClickHouse (CORE-REWORK Q-3, Q-4; CORE-10, pending). A full journal (its disk bound) refuses new at-least-once messages with 503 and an alert (D-105, CORE-4d); riding out a ClickHouse outage on the journal, with the same 503 when it fills, comes with the mover (CORE-REWORK Q-8; CORE-10, pending); the stop of intake for the whole platform when the log-record buffer is full is wider than this refusal and comes with OPS-2 (pending; OPERATIONS-BRIEF §3; §8 Write path and loss contract). Copies per environment are the operator's choice — e.g. dev 1, test 1, production HA 2 (local + a peer node, the ACK waiting for the peer's receipt, Q-5), re-replication after a lost node and the node-to-node read (CORE-REWORK O-7; CORE-5, D-138). Since CORE-5a (F-35, D-139 draft) nodes reach each other on the internal **peer link** (`dev.rail8.runtime.journal.peer`, TCP, `RAIL8_PEER_PORT` 8083): a HELLO and proof per direction under keys derived from a peer subkey of the environment master key (HKDF, D-106, D-141; the master key keys no HMAC on the link, its only use there being the input of the one HKDF that makes the subkey, under its own label), the HELLO naming its version (a link speaks the lower of the two; later fields are tolerated) and its channel (read; repl since CORE-5b1; bulk reserved for CORE-5b3), at most 64 handshakes at once and 8 per source address — the proof binds both nonces, both node ids, the epoch and the direction, the key named by fingerprint, from the current and the previous one the node holds (today only the current one is configured; FIX-178) — then frames of at most 4 MiB + 1 KiB of payload (HELLO and PROOF capped at their own size until the link is proven), each sequenced and tagged; bodies travel as the journal's AEAD ciphertext, journal-record metadata in clear under the tag. A node publishes its peer address in its `nodes` row (V18, written at join, read back by the one renew statement). A body a node's own journal does not hold is read from its live owner by (owner, journal id, segment): READ answered by BYTES chunks or MISS, at most `RAIL8_PEER_READS` (16, 1..64) reads in flight per peer, the socket paused while a reader is slow so the heap holds no whole body — one paused reader stalls every read on that link (head-of-line, FIX-177 before CORE-5c), and a link paused with no progress for `RAIL8_PEER_TIMEOUT` while a read is in flight is closed, failing its reads (a link left paused with no read in flight fails its next read after at most two timeouts); a miss or a dead owner fails the read. `RAIL8_JOURNAL_COPIES` (1..2; unset, 1 in dev and ci, 2 when deployed) is read, and a generated journal key is refused with more than one copy; since CORE-5b1 a node holds a peer's copies: on a link of channel repl (the dialer's HELLO channel, bound by both proofs) the owner sends OPEN (the segment header), DATA and SEAL (the file's end and its crc32c), never DATA before the holder's RECEIPT OPENED; the holder writes `replicas/<owner>/<journal>/<n>.part` (byte-identical to the owner's segment), answers RECEIPT OPENED after the header and both forces, WRITTEN once its write returned (the force runs off the receipt path) and SEALED after force, rename to `<n>.seg` and directory force, or REFUSE FULL, FAILED or MISMATCH; replicas count in the journal's bytes and an OPEN is refused FULL once the replicas with it would pass half the intake edge (bytes past an OPEN's length, the footer index, are counted unchecked), a failed replica keeps its file and is counted at its size, and a repl link is closed at its proof and at every OPEN when its epoch is below the highest the holder accepted from that owner or the owner's live epoch, while one at or above it supersedes the owner's link: the old link is reset (its unsent RECEIPT and REFUSE frames are dropped and DATA its writer had not taken is never written, so the owner treats every unreceipted byte of that link as not received) and the new link's frames are taken once the old writer stopped; until CORE-5b2b a replica is never swept; the owner's side — the ACK on the peer's receipt — and takeover from a copy and re-replication are CORE-5b2..5e (pending) — until then every body has one copy and a down node's items wait for it (D-101 (5), stated at start).

**Postgres durability profiles** (D-127 draft, D-114, D-115; D-061 amended): `RAIL8_PG_DURABILITY` says what an accepted message survives on the Postgres side. `local` — a single server's commit: it survives a Postgres crash, not a promotion or the loss of its host; the node states that promise among its notices (`/health`) at every start and, when the server streams to standbys, names them and `ha`. `ha` — a commit that waited for a synchronous (or quorum) standby: it survives the promotion of such a standby too. Unset, `local` in a non-deployed environment (`dev`, `ci`) and `ha` in every deployed one, whatever the host (a proxy on loopback does not make a production node local); any other value is refused naming the key. Under both, every session of the node (intake and work pools, membership, LISTEN, on every reconnect) carries the startup parameters `synchronous_commit=on` and `statement_timeout=0`, above a database's or a role's own setting (Flyway's migration is not pinned: the next pinned commit covers its WAL). Before it migrates, the node reads in one statement what an intake pool session runs with and what the server is, and refuses to start, under both profiles, when the session's `synchronous_commit` is not `on` (a pooler dropped the parameter) or the server is in recovery (the host names a standby); under `ha` also when `synchronous_standby_names` is empty, when its role cannot read every statistic (`GRANT pg_monitor TO <user>`: without it the standbys' state is hidden), when its role may not run the duplicate's barrier below (`GRANT EXECUTE ON FUNCTION pg_catalog.pg_logical_emit_message(boolean, text, text, boolean) TO <user>`, D-128) and when no sync or quorum standby is streaming; with a standby a commit does not wait for, an `ha` node names D-115 among its notices. The settings are checked at the start only (D-115): a standby lost later makes commits wait in Postgres, the save timeout bounds the caller's answer (503) and the node never cancels a commit. A duplicate (D-084) waits as a write does (D-128): under `ha` a save group with no row to write — every member's key taken — runs `select pg_current_xact_id(), pg_logical_emit_message(true, 'rail8', '')` and commits instead of rolling back; the transaction id and the transactional logical message (one WAL record, no row; Postgres makes a commit wait for its standby only when its transaction wrote WAL) make that commit wait for the synchronous standby, and the wait covers every earlier WAL record, so a retry whose key names a save committed only locally (its SyncRep wait ended by a backend termination or a fast primary restart, its sender answered 503) is answered 202 only once that save is on the standby. A failed barrier statement or a refused or lost barrier commit is no answer and retryable. EXECUTE on `pg_logical_emit_message` is an `ha` precondition checked at start (owner decision 2026-11-11; PUBLIC has it by default, works at `wal_level` `replica`): the start query looks the function up by its PostgreSQL 17 signature `(boolean, text, text, boolean)` and never errors, so `ha` needs PostgreSQL ≥ 17 and `local` starts on any version; an EXECUTE revoked after the start fails every `ha` duplicate, loudly and retryably. Under `local` such a group rolls back. Accepted residuals: an operator's `pg_cancel_backend` on a commit waiting for its standby makes Postgres return success for a commit that is only local (syncrep.c), so the message survives a crash but not a promotion; the start check is the only check (D-115): a reload that empties or renames `synchronous_standby_names` later — as a failover manager's non-strict synchronous mode does — stops commits from waiting and the node does not notice (CONSIDER-18); under `local` without `pg_read_all_stats` the standbys read as unnamed, so the streaming-standby notice cannot name them; managed cloud Postgres that replicates below Postgres (RDS Multi-AZ, Cloud SQL HA) shows no synchronous standby and is refused by `ha` — such a deployment sets `local` until ISSUE-5 is decided. PG 17 does not cut a SyncRep wait at `statement_timeout`; the pin stays as a defence against other servers and poolers. **Supported versions** (D-129): PostgreSQL 17 and 18. Tested main: `postgres:18.6`, the one pinned tag of `dev.rail8.testkit.PostgresImage` that every Testcontainers test and both compose stacks run; CI floor: the same `-Pit` suite on `postgres:17.11` through `-Drail8.it.postgres`; `ha` needs ≥ 17 (D-128), `local`'s start check refuses no version, yet below 17 nothing is tested; 19 joins the CI matrix after its GA (FIX-169b), never an RC image. A data volume of the 16/17 images is not reused by the 18 image (its PGDATA is `/var/lib/postgresql/18/docker`): a major upgrade is `pg_upgrade` or dump and restore.

**Postgres pools by role** (D-130 draft, F-27 I4; amends D-109's bound): a node's pooled Postgres connections are two pools. The **intake pool** (`RAIL8_PG_POOL_INTAKE`) carries the at-least-once saves — their groups and the in-doubt `XACT_STATUS` read — and every segment row the body journal writes — at its start, at each segment's pre-open and at each spill's persist, a step body's included (a save's persist may wait for any of them); the sweeper's deletes are on the work pool. The durability check at start runs on the intake pool. The **work pool** (the rest of `RAIL8_PG_POOL_SIZE`) carries everything else: the work queue's claims and completions, the message store's trail, the DLQ, the blob store's refs, the work events' NOTIFY sends, retention, the sweeper's segment rows, deployments, the journal keys, the `postgres` health check and every admin read. The membership and the LISTEN connection stay one dedicated connection each. The ACK path touches only the intake pool: the wake and the announce after a save's commit are fire-and-forget on the work pool, so a work pool saturated by parks or claims waiting on a lock does not delay a save. `RAIL8_PG_POOL_SIZE` is the total of both pools, 2..1024 (21 = 5 intake + 16 work: the intake pool is added on top of the 16 the workers had with one pool, F-33); `RAIL8_PG_POOL_INTAKE` is 1..1023 and below the total, so the work pool keeps at least one; unset, max(1, min(5, total / 2)) — 21 → 5 + 16, 16 → 5 + 11, 8 → 4 + 4, 4 → 2 + 2, 2 → 1 + 1. `RAIL8_INTAKE_GROUP_CONCURRENCY` (1..64) is bounded by the intake pool, at most max(1, `RAIL8_PG_POOL_INTAKE` − 1), unset min(4, that bound). A node holds `RAIL8_PG_POOL_SIZE` + 2 connections at most (23 at the defaults: two pools, membership, listen; 18 with one pool of 16). Every session names its role and its node in `application_name`, `rail8-<role>@<nodeId>` (`intake`, `work`, `membership`, `listen`), on the one source of the connect options (pins and TLS). Each key is refused at start naming it; `RAIL8_PG_POOL_INTAKE` not below the total names both keys, a concurrency above its bound names it and `RAIL8_PG_POOL_INTAKE`. Node.close closes the intake pool, then the work pool, each even when the other's close failed. Each pool waits at most `RAIL8_PG_POOL_WAIT` for a connection (ISO-8601, PT0.001S..PT1M, default PT5S, the save timeout) and queues at most `RAIL8_PG_POOL_QUEUE` callers (1..65536, default 1024); both are refused at start naming the key when not parseable or out of range (D-132, FIX-172). A caller the pool refuses — the wait elapsed or the queue full — is retryable backpressure (D-082): the intake answers 503 with nothing saved, an admin route answers 503 when the pool refuses it (the reads, the work queue's discard, a DLQ retry, a deploy's work-queue question and deployment-record write, an undeploy's work-queue question and deployment-record delete; FIX-172c) — a work-queue question the pool refused is 503 only when every failed question was the pool's: a real failure of another flow's question outranks it (500), on an undeploy so does a flow that holds items (409), and a deploy's package problems stay its 422 (D-133, FIX-173); whether a statement on the pool was refused (exactly `VertxException`, or `ConnectionPoolTooBusyException`) or a transaction's acquire (`PoolRefusedException`: every store's transaction takes its connection through one helper, `PgTx.inTransaction`, and a failed acquire — before any statement ran — is that type, whatever the pool failed with), the work queue's discard included; a deploy whose deployment-record write the pool refused answers 503 with the refusal's own `{error}` line (D-133, FIX-172b); a refused claim leaves the worker claiming on a later tick. The wait also covers opening a connection (TLS, authentication), so a wait below about 1 s can make a cold node refuse its own start; the default is far above it.

**Pickup** (D-121 (a), (b), F-30): a saved item reaches its node's worker by a local hand-off, not a claim. One `Workers` registry per node holds every started worker by flow; before its insert the intake reserves a slot of the flow's worker (`max − running − reserved` room, less what a claim in flight asked for, the fence open, no rows known to wait for a claim), and the item is written leased to its node — attempt 1, the flow's lease — in the same transaction when it heads its key; after the commit the slot runs it, with no claim statement. An item saved without a slot (no room, no worker here, a known backlog) is a plain row, and the save wakes its flow's worker after the commit; a reserved slot whose key already has a row is given back (the key's holder hands the row on); a rollback cancels the slot, an in-doubt commit cancels it and arms the wake below. A worker claims at its start, on a wake, at a chain's end only while it knows of a backlog (a claim that filled its room, a wake, a key's chain cut at its bound; cleared by a claim that answered less than it asked with no wake since it began), and on its reconciliation claim every `pollInterval` (PT30S; the first one interval plus `floorMod(flow.hashCode(), interval in ms)` ms after its start, so the flows of a node do not claim together); an item left to its lease (a fenced settle, a failed complete or hold, a lost lease, a leave verdict) arms one coalesced wake at its lease end. Between nodes, work events (D-121 (b), P2-16b): `WorkSignals.announce(targetNode | *, flow | *)` is called only after the commit that made rows claimable is acknowledged — a keyed completion, by the fast path or plainly (the chain bound, a stopped worker), that leaves the key's next row in another node's journal (the next-of-key statement, or a read after the plain delete, answers that row's `body_node`), an operator's release (it also wakes the flow locally; the row's `body_node`, or `*`), an intake item that copied a kept ref of another node's journal. The node's `PgWorkSignals` sends `w1 <sender> <target|*> <flow|*>` with `pg_notify('rail8_work', …)` on the work pool in autocommit, never inside a transaction: the first announce of a 50 ms window at once (leading edge), the window's later ones as one statement at its end (distinct payloads; more than 64 fold to `w1 <sender> * *`); a failed send is logged and dropped. It listens on one dedicated connection (never a pool's); a payload for this node or `*` wakes the flow's worker (`*`: every worker), its own sender's and other nodes' are ignored, another form is logged once per prefix. A lost listening connection reconnects on the node timer (100 ms doubling to 5 s, until the node closes) and every `LISTEN` acknowledged wakes every worker once: a missed event costs one claim, the reconciliation is the safety net. Node.close closes the signals after the flows and before the pools. Window, fold cap and interval are constants (no env keys until P2-16c measures NOTIFY inside the commit). An idle node sends only its membership renewals, one reconciliation claim per flow per 30 s and Retention's hourly run (`Retention.Config.interval`, PT1H by default, D-088).

**XI quality of service** is a layer on at-least-once: exactly-once at the intake = at-least-once + `processed_ids` dedupe table — where the endpoint's component names a dedupe key, a sender's repeat is saved once, for as long as retention keeps the key; toward the partner a message can still arrive again and is recognised by its id (*A message can arrive more than once*, above; F-56); in-order = XI queue name as partition key, serial per key, parallel across keys; a keyed (`partitionBy`) flow must state `onFailure`: `park` parks a message that failed past its attempts and lets its key's next message run; `block` (the key waits for the parked message, XI behaviour) is refused at load until a durable barrier with release and discard exists (FIX-141, F-32); a keyed flow without `onFailure` and an `onFailure` without `partitionBy` are refused. Three ack states are recorded per message: transport, system, application.

**Event bus** carries only admin commands. The customer's message never travels on it, and after the §4 review neither does monitoring: the writer path is worker → local bounded batch queue → Postgres (the last-N-hours copy, §8); ClickHouse is to be fed by the node's own mover from the sealed journal segments and the sync recording batches, never through Kafka (CORE-REWORK Q-3, O-1; CORE-10, pending). That built path is to be replaced by the log record in memory → writer → the node's journal → mover → ClickHouse (OPERATIONS-BRIEF §3; OPS-2, CORE-8, CORE-10, pending; §8 Write path and loss contract). Vert.x clustering is not used; nodes share state only through Postgres and Valkey (and Kafka only where the add-on is installed); the one direct node-to-node channel is the journal's peer link, which carries journal frames and nothing else (§4 Body journal, F-35).

**Writer (persistence batcher)**: hand-rolled, not a Mutiny operator chain (which emits on timer regardless of demand and dies on backpressure). Adaptive flush — write immediately when idle, accumulate to batchSize/batchMs under load; up to N commits in flight with per-batch completion; fixed-shape `unnest` inserts with prepared-statement cache; a small bounded admission buffer whose overflow surfaces as ingress rejection, never as a dead stream (trail rows wait FIFO for room up to `maxWait` instead, §8, D-071). The prototype measured batching at ≈ 80 % of no-persistence throughput; the serialized-commit ceiling is gone. This batcher writes today's snapshot rows; what writes the log records — where a full buffer waits and alerts and never drops — comes with OPS-2 and CORE-8 (pending; OPERATIONS-BRIEF §1, §3).

## 5. Message model

An Envelope is an immutable record; every step returns a new one, and bodies are handles to content, never streams. Immutability is what makes snapshots free, retries safe and parsed views shareable.

```java
record Envelope(String id, String flow, int step,
                Headers headers,               // transport metadata, String→String
                Props props,                   // typed flow state, Key<T>, never leaves the runtime
                Keys keys,                     // business correlation keys, indexed for search
                Body body,                     // main payload, by reference
                Map<String, Part> attachments, // Part(name, contentType, Body)
                Views views)                   // memoized parsed views, shared by reference
```

| Field | What goes there | Persisted | Indexed | Reaches producers |
| --- | --- | --- | --- | --- |
| `headers` | HTTP/JMS/mail headers from ingress, `http.status` from egress | jsonb; secrets in headers are to be replaced by a marker and never stored (OPS-5, pending; OPERATIONS-BRIEF §2.7) | no | only what the flow allow-lists (`forwardHeaders`); nothing propagates implicitly |
| `props` | split index, router decision, partner, validation result — anything a later stage decides on | jsonb, JSON-serialisable values only | no | never |
| `keys` | what operators search by (invoiceId, orderNo, meteringPoint); filled by `extractKey`, declared per flow | own table `message_keys(name, value, message_id, step)` / CH columns with skip index | yes | never |
| `attachments` | multipart parts (mail, SOAP/MTOM, AS2/AS4) | reference only; content kept per retention policy | no | yes, as parts |

Not carried over from Camel: `getIn()/getOut()`, `ExchangePattern` as a property (request/reply is a consumer trait), exception as a property (failure is a stream signal and a DLQ row). Keys are separate from props because "invoice 4711 — where is it" must answer in under 1 s over a year of data, and that needs an index on `(name, value)`, not a GIN index over a general-purpose bag.

**Body**: one final class, no visible variants.

```java
final class Body {
    Hash hash();            // content hash (xxh3), the identity; computed on arrival
    long size();
    ReadStream<Buffer> open();   // fresh cold stream, any number of times
    Buffer whole();         // only below the tree limit, else exception
}
```

Where the bytes live is a `BlobStore` concern, invisible to steps: memory tier (default 1 MB), then the node's body journal (§4 Body journal; D-105, CORE-4; CORE-REWORK O-6), which replaced the encrypted local spool, the S3 body tier and new inserts into Postgres `bodies` (CORE-REWORK O-4, O-5; the table dropped by CORE-11, pending, §7): a body that outgrows the memory tier spills into the journal, and an at-least-once body up to `RAIL8_BLOB_DURABLE_MAX` (1 MiB, at most 64 MiB) is forced into it before the ACK, a flow declaring a larger max body still refused at deploy (F-6, D-058; D-110 draft); a node-wide byte budget is the second spill trigger; every flow declares a finite max body size. Objects are keyed by **message id + step**, not by content hash (streaming multipart cannot know the hash up front, and content-keyed objects cannot be deleted per retention — §4 finding). The hash is still computed and stored on every step row (`messages.body_hash`, `hash_algorithm`), so dedup is visible in monitoring as equal (algorithm, hash) across rows; the bytes are written once, by reference (F-23, D-097).

Steps declare the body kind they need — `whole` (DOM-style, size-limited), `stream` (gzip, PGP, sign, copy; never materialised), `split-assemble` (StAX/CSV/JSON splitter at ingress producing child envelopes with `PARENT_ID / SPLIT_INDEX / SPLIT_TOTAL`, each child's id `<parent id>.<index>` so a rerun sends it under the same id (D-113), streaming aggregator writing header + fragments + footer). The deploy-time check rejects a `whole` step on a flow whose max body exceeds the tree limit unless a split precedes it. Producers pipe `open()`; they never buffer. Every producer whose transport carries headers — http and the mock today — sends the message id to its partner as `x-message-id` (`Envelope.withOutboundId()`, one value, a forwarded one replaced; D-113) so the partner can dedupe a rerun (§4, *A message can arrive more than once*); a transport without headers names its carrier with its producer (sftp, Phase 4; F-56). Stream-step outputs are materialised node-locally in the body journal by the same BlobStore rules (D-105, CORE-4), never uploaded to S3 (CORE-REWORK O-4). Rejected: auto-inserted splits.

## 6. Pipeline

A flow is a composition of stages built once from its config; at runtime a stage holds only the dependencies it was given at build time, and the `Runtime` record is never looked up again. That is what makes a flow unit-testable in milliseconds with a fake `Runtime`. "Interface" is the operator's word for a deployed flow; which unit it names behind a dispatcher flow is open (§14; OPS-3, OPS-9, OPS-11). This document keeps "flow" and writes "PO interface" for an interface of SAP PO.

```java
interface Step  { Envelope apply(Envelope e); }                     // runs on the message's virtual thread; may block
interface Stage { Envelope apply(Envelope e, Pipeline rest); }      // may emit 0..N, call rest for each
interface XmlStep  { XdmNode apply(XdmNode in, Headers h); }        // platform parses/serialises, view memoized
interface TextStep { String apply(String in, Headers h); }
```

With one virtual thread per message the reactive `Multi<Envelope>` stage contract from the prototype is no longer needed; a stage is plain code and cardinality is expressed by how often it calls `rest`. Patterns as built-in stages: `transform`, `filter`, `split`, `route` (first matching predicate wins; a branch is itself a pipeline, named `route:<branch>` in the timeline), `aggregate` (state in Postgres, deadlines as DB rows), `throttle` (per node, or global via Valkey), `circuitBreaker`, `idempotent` (processed\_ids), `resequencer` (Postgres).

State rule: state whose loss loses messages goes to Postgres (aggregator, resequencer, idempotent ids, DLQ, ordered queues); state whose loss only changes tempo may be in memory or Valkey (throttle, circuit breaker, caches).

Retry per step: policy from flow config, exponential backoff, only on steps marked retryable (I/O), for checked failures an awaited future rethrows as well (a refused connection, FIX-107); an interrupt is neither retried nor parked; final failure of an at-least-once flow → DLQ row by reference to the body, written only after that body is persisted (F-7); a sync flow returns the error to the caller and parks nothing (§4 table, D-045). At-most-once flows log and drop. A failed or in-doubt send of an at-least-once flow is retried as SAP PO does — `delivery.retries {count, interval, multiplier, maxInterval}`, node default RAIL8_RETRIES_COUNT / RAIL8_RETRIES_INTERVAL (3, PT5M), each attempt a work item with a not-before time and the same message id, never a sleeping thread — and then parked in an error state (CORE-REWORK Q-7; D-135, CORE-14a; §4 Node lease and fence); the manual retry under the same id is `POST /admin/dlq/{id}/retry` (D-136), as often as needed; cancel ends a parked message for good (FIX-267, pending); no operation sends a copy under a new id (D-156, F-55). `retry` stays the in-step retry inside one attempt.

**Inter-flow communication**, three mechanisms, all deploy-time checked for dependencies and cycles:

| Mechanism | Runs where | Message identity | Crosses nodes | Use |
| --- | --- | --- | --- | --- |
| `call: <subflow>` | nested stage, same thread, same message | same | no | shared, versioned library logic (what PO called a common mapping) |
| `flow://<name>` | caller's thread, direct call through the registry | child message with parent id | no | sync composition, lookups |
| `queue://<name>` | target flow's own virtual thread, via the Postgres work queue (Kafka only with the optional add-on, CORE-REWORK O-1) | child message with parent id, only configured props persisted | yes | async hand-over with the target's own retry/DLQ/ordering |

Headers always cross; the body is shared by reference. Never through the event bus.

**Dispatcher flows**: one endpoint (e.g. `/xi`) reads the routing key, looks up a versioned routing table in Postgres (cached per node), and forwards — a sync target is called directly on the same thread, an async target is enqueued with `target_flow`. Unknown route → error or DLQ "no route", never dropped. During a PO migration the dispatcher passes unmigrated PO interfaces through to the old PO, PO interface by PO interface.

**Recording** per flow, overridable per step: today the recording level `all | ends | errors | off`, payload `keep | metadata-only`. These are to be replaced as SAP PO does it (CORE-REWORK O-13, Q-9; CORE-13, pending): body levels `none`, `inputs` (the body as it arrived) and `changes` (every body a step changed), each combinable with the switches `errors` (also the body that entered a failing step) and `outputs` (also what was sent to the partner); the metadata of every step (time, duration, status, headers, props, keys) always; one global default for sync (`none` + `errors`) and one for async, overridable per flow; per step only `keep` or `skip` on its body (a skipped body is not shown for that step and the next step's mapping trace cannot be produced from it; the UI says so). At-least-once keeps its arrived body in the journal until processed whatever the body level; the body level decides whether it stays after that and moves to ClickHouse. Retention: a global period for sync and one for async, overridable per flow, and a separate period for error messages (a message that ever reached a state needing a person — parked, failed — whatever its end), applied as ClickHouse TTL by flow and age, older parts to S3 by age, then deleted (CORE-REWORK Q-9; CORE-13, pending). To be, by the operations brief (OPERATIONS-BRIEF §2.3, §2.8, §2.9, §3): body recording stays its own setting beside the log threshold, and a trace sets both to their maximum for a limited time (OPS-3, pending; §8 Levels and trace); the one fact a step shows at the log level info is composed at display time from the step metadata kept always (OPS-5, pending; §8 Log records); a message's log records (steps, log, errors) outlive its payload, both periods configurable (CORE-10, CORE-13, pending). How those two periods sit with Q-9's sync, async and error periods, and what "maximum" means for a `skip` step and for a body above the recording threshold of D-110, are open (§14). Recording serves monitoring — the timeline, each step's body, search by key, the diagnosis of an error, "save as test case" (§8) — with one exception: the at-least-once durable save at ingress, the ingress row and the arrived body, is written whatever the level, and every run and every retry starts from it (a run that finds no ingress row completes its item with a WARNING). No operation re-sends a message from a step's recorded output (D-156, F-55); a retry resumed at the failed step (CONSIDER-13, accepted in D-142, pending) will keep an envelope of the worker's own, never the recorder's. Storing only the input and what cannot be repeated, and reproducing the other steps' payloads on demand for display — never a re-send — is parked by the owner (CONSIDER-22; OPERATIONS-BRIEF §7). Every message pins the flow, partner-directory and routing-table versions it ran with, so monitoring tells the truth. Each attempt of a same-id rerun (a scheduled retry, a takeover, `POST /admin/dlq/{id}/retry`) keeps its own step rows, keyed (id, step, attempt) since V19: the timeline lists every attempt's steps in (attempt, step) order with their `attempt`, a step's body is the latest attempt's unless `?attempt=k` names one (FIX-175, D-140). A same-id DLQ retry (`/admin/dlq/{id}/retry`, D-136) runs the flow version deployed now (it exists to rerun a parked message after a fix) and pins the versions it ran with, so each run's configuration stays visible (F-11). A kept step body stays readable after a restart (`GET /admin/messages/{id}/steps/{n}/body`), because every kept step body is durable (D-064, D-066) — in the journal within `RAIL8_JOURNAL_KEEP_MAX_AGE`, beyond it once the mover lands (§4 Body journal; CORE-10, pending); a GET of a body retention removed is 404 (D-096). Retention never removes a parked message's rows, body or ref, so a DLQ retry is never refused for age; one whose ingress body is lost answers 409 (§4). **One id for the life of a message** (D-156, F-55): from ingress to its end a message has one id and one history; the operator's operations on a failed message are retry and cancel, both under that id; there is no cap on manual retries; a sync message and a cancelled one are never resent; a retry that succeeded shows in the message's history and nowhere else; a cancelled message counts as a failure of its flow (the default, unanswered — ISSUE-10). Neither operation leaves a record of who did it and when yet: there is no message log (§8), `/retry` takes no actor and writes no audit row, and cancel does not exist (FIX-267, pending).

## 7. Components, queues, persistence

All contact with the outside world goes through the Component SPI; nothing else in the platform opens a socket. That is the rule that makes mocking first-class. It binds contact with partners: the runtime's own sockets — the admin listener, the store clients and the journal's peer link between nodes (F-35) — are not components, and ArchUnit confines Vert.x `io.vertx.core.net.Net*` to `journal.peer` (`ONLY_THE_PEER_LINK_OPENS_RAW_TCP`; the JDK's `java.net` and NIO sockets are not covered yet, FIX-180). The rule binds the node; the `rail8` CLI is a tool outside the node, and its admin client (`rail8 deploy`, JDK `java.net.http`) talks to a node's admin API, not to a partner (F-16).

```java
interface Component {
    String scheme();                                   // "http", "sftp", "xi", "jms", "mock" …
    JsonSchema configSchema();                         // validated at deploy time
    Consumer consumer(EndpointConfig cfg, Function<Envelope, Future<Ack>> handler);
    Producer producer(EndpointConfig cfg);             // Future<Envelope> send(Envelope e); default send(e, Deadline d) (D-113)
    Future<Health> health();
    default Optional<InetSocketAddress> listensOn(EndpointConfig cfg) { return Optional.empty(); } // D-072
    default boolean polls(EndpointConfig cfg) { return false; }                                   // D-083
    default Optional<Key<String>> dedupeBy(EndpointConfig cfg) { return Optional.empty(); }        // D-084
    default Optional<String> target(EndpointConfig cfg) { return Optional.empty(); }               // D-099
}
```

A component whose consumer accepts connections answers `listensOn` with the local host:port it binds (from the config alone, no bind, no DNS; port 0 is never compared). A deploy refuses two `in` endpoints whose addresses overlap — same port and equal hosts or a wildcard host — within the package, against the node's admin listener, and against every running flow of every other package; Vert.x would share the port and round-robin it silently (D-072).

The consumer contract is `Function<Envelope, Future<Ack>>` (§4 finding), not a bare `ReadStream`: the handler returns the ack state the consumer needs to finish its own protocol (delete the file, commit the JMS session, send 202). Blocking SDKs run on virtual threads the component starts itself, as the http consumer does; no `BlockingConsumer` wrapper until a second blocking SDK needs one (D-076). One jar per component, wired explicitly by the node's `Main` (components need the node's `Vertx` and `BlobStore`, which `api` may not name — F-4); same classpath until a dependency conflict forces isolation. Steps (xslt, groovy, js, validate, map, ai) are wired the same way.

`WorkQueue` and `MessageStore` are interfaces. Rule (agreed Oct 17, 2026; amended by CORE-REWORK O-1, CORE-9): the core's queue is Postgres (`queue: postgres`, the default); Kafka is an optional event-broker add-on, with which a flow may move to `queue: kafka` when it needs high volume, cross-pool fan-out or replay from the log; XI EOIO ordered queues stay on Postgres always, and the /xi door's durability is the core's at-least-once save, not Kafka. A broker replaces save-before-hand-over, never the monitoring store. Per-key serial processing: a worker that finishes a message takes the next one of the same key without a new claim round-trip (hot-partition optimisation, measured at 60–200 msg/s per key in the prototype without it). The key is evaluated at the durable save from the flow's `partitionBy` (the name of its one `extractKey` step; no value = unordered; over 256 chars = final refusal); after the item it claimed, a worker takes at most `maxChain` further items of the key by the fast path (default 32; 0 = fast path off) before the key goes back to the seq-ordered claim; a key the extractKey cannot read (MALFORMED/INVALID) is saved unkeyed, any other key failure is a retryable refusal; `queue: kafka` is refused at deploy, naming Kafka as an optional add-on not in this build (D-075, CORE-9).

**Persistence tables (Postgres)**: `messages(id, step, attempt, flow, headers, props, keys, body_ref, versions…)`, `message_keys(name, value, message_id, step)`, `work`, `dlq(… body_ref, no FK to messages, so a park never waits on the step rows; its body's kept ref (`body_refs`, V12) and that ref's segment row must be committed first — D-062 persist → park, D-096, CORE-4c2)`, `processed_ids`, `aggregates`, `routing_table`, `partner_directory`, `flows`, `wallet`, `audit`; no message bytes — those live in the node's body journal, Postgres holds their references (CORE-REWORK O-2, O-5, O-6; D-105). `messages` holds today's snapshot rows (§8 Write path and loss contract); no Postgres `message_log` table — the table of the superseded draft `agent/packets/CONSIDER-13-design-draft.md` was not built and is not to be (OPERATIONS-BRIEF §1, D-147; OPS-2, pending). The V6 `bodies` table takes no insert since CORE-4c2; its remaining rows go by age, and the table and `PgBodies` are dropped, the rows moved to the journal or ClickHouse, by CORE-11 (pending). Rule: bytes exist in the system once; everything else is a reference. Never a synchronous delete on the hot path; retention is a background job in bounded keyset batches by age — not by partition, since a partitioned `messages` must carry the partition key in its primary key and that breaks the first-wins `ON CONFLICT (id, step, attempt)` (F-20, D-088, D-140). A message goes only whole, only when no work item or DLQ row names it; its body refs (`body_refs`, scanned in one keyset with the remaining `bodies` rows) and `processed_ids` rows go with or after it, the journal's bytes later with their segment (CORE-4d) (exception accepted in F-20: a message can stay partial until the next run after a work item held longer than the retention). A DLQ row never names a removed body: the park is one statement that holds its `body_refs` row and that ref's segment row `for key share` and writes no row when either is gone (a pre-V12 `bodies` row alone admits no park); retention locks its batch of `bodies` and `body_refs` rows `for update skip locked` and deletes it under a later snapshot that re-checks the guards (P2-07b2, D-096, CORE-4c2). So a DLQ row needs a durable body in the journal.

**Sizing**: one 8-core node is expected to carry tens of thousands of HTTP passthrough req/s, 5–20k msg/s with persistence, hundreds to low thousands/s with 100 KB XSLT. Targets to hold on native Linux: sync request/reply platform overhead < 2 ms p50 (met in the prototype), at-least-once durable ACK measured p99 8.80 ms at c=1 on a 4 vCPU cloud VM with Postgres 16 after the one-transaction save (10.58 ms before it on the same VM; F-14, F-18); a not-durable FLOOR run with pg_wal on tmpfs gave 8.04 ms, so faster storage alone cannot reach < 5 ms p99 on that machine; under load the one-transaction save is slower than the two-commit one (c=64 median 733 vs 833 msg/s, −12 %; c=8 p99 41.38 vs 31.83 ms) until FIX-95. FIX-95a/b were folded into the core rework (CORE-6a, CORE-6b, done); the new core is measured against CORE-REWORK Q-1's working targets on the 4 vCPU VM at CORE-GATE (pending; GATE.md §CORE-GATE), the 8-core figure above on a dedicated machine later (Q-1, Q-2).

## 8. Monitoring: log records, metrics, alerts

Monitoring is the product. Processing waits for monitoring only at the points named below, and monitoring is not best-effort either. This section is rewritten to `docs/OPERATIONS-BRIEF.md` (D-147; changelog 3.25, F-38): each sub-heading states under "Today (built)" what the code does now and under "To be" only what the brief decides, with the row that designs it; nothing under "To be" is built, and its design enters with that row. The one hard constraint the owner set for all of it: no loss of performance.

Three things in this document are called a record, and this section never uses the word alone. A **log record** is one entry of the log stream described below (to be; OPS-2). A **journal record** is one entry of a node's body journal (built; §4 Body journal). The **deployment record** is the Postgres row of a deployed package (built; §9 Deployment mechanics). An error record is a log record: the one of a failed step (to be; Log records below). What is built today where the log record is to be is the **snapshot**: one row per step and attempt in Postgres `messages` (§7).

**One log-record stream**

Today (built): a snapshot after every stage, searchable by business key — in under a second over a year of data is the target (§13 Phase 3) —, with the payload at each point the recording level keeps (§6 Recording, CORE-REWORK Q-9) and every attempt's steps under the message's one id (D-140, D-156). The snapshot is all that is kept per message: there is no message log, no interface log and no connection log, and what the platform itself reports — the write path's WARNING below, for one — goes to the node's process log.

To be (OPS-2, pending; OPERATIONS-BRIEF §1, §2.1, §2.2): one stream of log records. A step, an author line, an error, a send attempt, an operator or agent action and a channel event are log records of one shape — time, owner, log level, kind, text, fields. A message's log is its log records in order; there is no separate "snapshots" and "log". There are three logs by owner: the message; the interface (deploys and setting changes with their actor, channel events, refused contacts); the connection (TLS failures, unknown paths, malformed requests — whatever cannot be attributed to an interface, found by time and the peer's address). Code that runs outside a message logs to the narrowest owner known at that moment: the message, else the interface, else the code's own log. CORE-8, CORE-10 and CORE-13 are built to this: they carry log records, not only trail rows. The message-log draft `agent/packets/CONSIDER-13-design-draft.md` is superseded: no Postgres `message_log` table, no drop on overload, no lines-per-attempt bound, no new public logging type in `StepResources`. The ClickHouse table and its ordering key are OPS-2's to design.

**Log records**

Today (built): a snapshot carries the fields listed under Write path below; a failed step's snapshot adds its error text and nothing more about the failure. Of the client of a contact the platform keeps the request headers that reached the envelope (§5) and nothing else — no address, no certificate, no TLS fact; the one remote address stored anywhere is on the audit row of a lost-work discard (§9, D-126).

To be (OPS-5, pending, on the shape OPS-2 designs; OPERATIONS-BRIEF §2.3 to §2.7, §5):

- At the log level info, for a successful message, every step shows its start, its end and one fact — what it decided or whom it contacted (receivers chosen, mapping name and version, endpoint, attempt, status code). It is built from the step metadata that CORE-REWORK Q-9 stores always (§6 Recording; CORE-13, pending); the sentence is composed at display time.
- A running step is visible from its start. One rule for every step: each reports start and end, and the writer merges the two when they meet in one write batch. Log records leave the node continuously, not at run end (OPS-2, pending).
- The error record has a fixed core — step, attempt, time, the step's error text, the body that entered the failing step — plus optional fields only when the step knows them: code, place in the artefact, place in the data, the value, the contract. What a step does not know is absent; nothing is guessed. How the body in the fixed core sits with the `errors` switch of CORE-REWORK Q-9 is open (§14).
- Connection failures (TLS, certificates, WS-Security) are recorded in full the first time, so that no reproduction tool is needed: the handshake stage, which side refused what, the peer's chain and what our trust store lacks; when the peer refuses us, the certificate we presented (or that none matched its request), the authorities it asked for and the alert it returned. An outbound failure belongs to the message and step that made the call.
- On every contact all that is known about the client is recorded: address and port (directly, or through a trusted load balancer when one stands in front; R8 does not require one), the user name presented even when the login failed, the client certificate, TLS version, cipher and server name, method, path, headers, sizes, timings. Secrets in headers are replaced by a marker and never stored. A refused input (failed validation, failed login) is found by the same search as a message, with the reason.
- Payload values in log records are separate fields, so that they can be hidden: payload has its own permission (OPERATIONS-BRIEF §5; OPS-9, pending; §9 Teams and permissions).

**Levels and trace**

Today (built): there is no log level, no log threshold and no trace. The one setting is the flow's recording level `all | ends | errors | off` with payload `keep | metadata-only` (§6 Recording), written in the flow file and changed by a deploy.

To be (OPS-3, pending; OPERATIONS-BRIEF §2.8, §2.9): five log levels — error, warning, info, debug, trace. The author picks a line's log level in code. The log threshold is a per-interface setting, switched at run time without a deploy, and it applies to every writer: platform, components, engines, author code, libraries. Payload recording stays its own setting (the body levels of CORE-REWORK Q-9, §6 Recording; CORE-13, pending). A trace is not a separate mechanism: it is a time-limited override that sets the log threshold and the body recording to their maximum, always for the whole interface, expiring by itself; who switched it and when is recorded. Its main use is a message that passes but gives a wrong result; an error needs no trace, because the error record is complete the first time. The log levels info, debug and trace are to be measured against the CORE-REWORK Q-1 targets (OPS-7, pending; OPERATIONS-BRIEF §3). Open (§14): what "maximum" means for a step whose body is `skip` and for a body above the recording threshold of D-110, which stands; and which unit "interface" names behind a dispatcher flow.

**Author voice and mapping trace**

Today (built): a step cannot add a line to its message. `StepResources` (§6) has no logging type; code that logs through `System.Logger` writes to the node's process log, where a line belongs to a message only if its text names one. No mapping trace exists, and the PO facade `MappingTrace` of §10 — the migrated mappings' API, another thing — is not built.

To be (OPS-4 for the author voice, OPS-6 for the mapping trace, both pending; OPERATIONS-BRIEF §1, §2.10, §2.11):

- No new R8 logging API, and no new public logging type in `StepResources`. Custom code and its libraries use standard Java logging (`System.Logger`; SLF4J for libraries); the platform attributes each line to its message and step through the bound `MessageContext` (§4). Lines from threads the code starts itself lose the link. The brief marks this a direction, to verify at design: the hook with isolated extension classloaders (§14).
- Mapping UDF: standard logging with the five log levels; `run.log(text)` stays as shorthand for the log level info.
- jq: `debug` and `stderr` both map to the log level debug (`stderr` is a function an author calls, not an error).
- The three engines' errors become the same error record: code, place in the artefact, text.
- Mapping trace on demand: it is not stored at run time; it is produced later by re-running the mapping traced over the stored input (the mapping engine gives identical output traced and untraced). Conditions: the step's input is stored, the version that ran is used, and the results of lookups into changing tables are recorded at run time.

**Write path and loss contract**

Today (built; the core rework's pending parts are marked): step → `Snapshot` (id, flow, step, attempt, stage, timestamps, wall and CPU time (CPU null where the JVM cannot measure the thread, F-21), headers, props, keys, body reference, error, extension name + version (v3.3's, not built), trace id (v3.3's, not built)) → local bounded batch queue on the node (every snapshot but the at-least-once ingress row, which the intake's transaction writes, D-082) → the Postgres last-N-hours copy that the operator screens read for "now". ClickHouse is to be fed by the node's own mover, not by a Kafka `monitoring` topic: it reads the sealed journal segments with their Postgres references and the sync recording batches, writes batched idempotent ClickHouse inserts and marks what ClickHouse holds; whether Postgres keeps a short copy of the step metadata for the live view or the UI reads ClickHouse through pg_clickhouse is decided by measurement (CORE-REWORK Q-3, O-1; CORE-10, pending). Overload shows as a bounded queue filling: today that is the admission refusals (503), the WARNING and the `snapshotWriteFailures` count of the next sentence, and no alert is built on it (the alert is to be: OPS-8, pending); nothing is dropped silently (the event bus was removed from this path for exactly that reason). A run's trail rows that find the node writer's bounded backlog full wait for room in arrival order, holding the run's permit, so a writer that cannot keep up shows as admission refusals (503), not lost rows; a row still waiting after the writer's `maxWait` (10 s), or whose commit fails, is logged at WARNING with its message id, flow, step and cause and counted in `snapshotWriteFailures`; the at-least-once ingress row does not pass through the batch queue on Postgres: it is written in the intake's transaction with its work item and its body's journal reference (no backlog to wait on), and a failed intake is a retryable Nack, not counted in `snapshotWriteFailures` (D-082; it replaces the fail-fast row of F-13, D-071).

Today (built), what is kept and what waits: Each recorded step body is kept durably (D-064; in the journal within `RAIL8_JOURNAL_KEEP_MAX_AGE`, beyond it with CORE-10, pending — §4 Body journal) unless it is above `durableMax` or its persist fails — then its row is metadata-only, counted and logged at WARNING; a run's snapshot rows wait in a per-run trail and are written at run end, or when more than 256 are buffered, once their bodies persisted, so a trail row's `body_key` always names a durable body (the at-least-once ingress row is saved in one transaction with its work item and its body's journal reference, the body forced into the journal before, D-082, D-105). A step waits only when its snapshot is the one past 256 buffered rows (it waits for that flush, and a sync reply behind it waits too); a worker item, a sync permit and an at-most-once landing wait for the run's last flush (persists, then row writes); the sync reply waits for no persist except that mid-run flush, and the durable ACK waits for none of these (F-10, D-066). These waits are to go (CORE-REWORK O-8, Q-6; CORE-8, pending): at-least-once step bodies batched into the body journal, sync recordings into the mover's batches without any fsync, the pipeline and the sync answer waiting for neither, nothing dropped silently (a bounded queue that fills is an alert); a node crash may lose "the last few sync records" (Q-6's words). Which bodies are recorded then follows the Q-9 body levels (CORE-13, pending).

To be (OPS-2, pending, with CORE-8 and CORE-10 built to it; OPERATIONS-BRIEF §1, §3):

- Asynchronous, never on the message's path. The message thread puts the log record in memory and goes on; a writer takes batches to the node's journal; the mover carries them to ClickHouse — the path the rework builds for bodies. Whether a sync run's log records take the node's journal too, or the mover's batches without the durable journal path as CORE-REWORK Q-6 has it, is open (§14).
- Nothing is dropped and nothing is truncated. No per-message line bound. One buffer for the whole platform; when it is full, intake stops for the whole platform ("ClickHouse is down — the system is not working — act at once") and the alert names the interface that writes most (OPS-8, pending). "A bounded queue that fills is an alert" means wait and alert, never drop: the built rule above — a row not written within `maxWait` is logged at WARNING, counted in `snapshotWriteFailures` and stays unwritten — is today's behaviour and no longer the design; it goes with CORE-8. The stop is every door refusing as it does today at a full admission, HTTP 503 + Retry-After and pollers paused (§4 Threading); how one node's journal stands to one buffer for the whole platform, and what the stop means for work in flight and for a retry, is OPS-2's. Counted summaries for repeated identical refusals — a caller over its limit writes thousands of equal log records a second — are parked against this rule (CONSIDER-23; OPERATIONS-BRIEF §7).
- Accepted by the owner (brainstorm of 2026-11-14/15, D-147): "a node crash may lose the last moments of that node's detail records. The message and the proof of its receipt are not lost, and the takeover record says so." What the brief's "detail records" and its "takeover record" are in the log-record stream is OPS-2's to design. This widens CORE-REWORK Q-6, which accepted the loss for sync runs only, and the Phase 3 gate follows it (§13).
- Capacity is sizing plus reserve. The platform measures the numbers for it itself: lines, metadata bytes and compressed payload bytes per message of each interface (OPS-12, pending).
- Unusual inputs are the author's responsibility, tested with the mock tools and with the mapping tried on the expected payload. Not everything can be guarded and it will not be tried.
- Retention: a message's log records (steps, log, errors) outlive its payload; both periods are configurable (CORE-10, CORE-13, pending; §6 Recording). How the two periods are set is not decided (§14).

**Stores and query surface**

Today (built): of the table below, Postgres holds the snapshots, the in-flight state and the DLQ, and S3 holds the deployment archives; nothing feeds ClickHouse yet — its ingest is the mover (CORE-10, pending) — and no control plane reads any of it yet: the node's admin API reads Postgres. The cells state the design as the core rework left it, pending where marked.

| Store | Holds | Read by |
| --- | --- | --- |
| Postgres | in-flight state, last N hours of snapshots, DLQ, ack states | control plane directly |
| ClickHouse | full history, metrics, payloads as rows of at most 8 MiB with `CODEC(ZSTD(1))` (per-tenant key in v3.3: there is to be no tenant level, what replaces the key goes with OPS-9, pending, and a key per team is open, §14), a larger payload as several ordered rows, never an S3 reference (D-108, CORE-2 done; CORE-REWORK O-3; the ingest CORE-10, pending); hot NVMe → S3 by age, its cold tier (CORE-REWORK O-4, Q-9; CORE-13, pending); retention as TTL by flow and age with sync, async and error periods (CORE-REWORK Q-9; CORE-13, pending), never row-level delete | control plane through **pg\_clickhouse** (FDW, reads only); payload-search functions wrapped in Postgres functions; every search query EXPLAIN-tested for pushdown |

To be (OPS-2, OPS-8, CORE-10, CORE-13, pending; OPERATIONS-BRIEF §1, §3, §4): ClickHouse holds the log records and the platform's own metrics, both carried there by the node's mover. No Postgres `message_log` table (OPERATIONS-BRIEF §1); whether Postgres keeps a short copy of the step metadata for the live view stays the measurement of CORE-REWORK Q-3 (Write path above). A message's log records outlive its payload, both periods configurable.

**Screens**

Today (built): no screen. The control plane is the last part of the plan (Amendments item 6); until then the node's admin API is the operator surface: the search by business key, a message's timeline with every attempt's steps, a step's body, the DLQ, held and lost work, the targets and the CPU aggregate per flow. The three screens of v3.3 stand as the design: per message (timeline with per-step latency, payload at each point, props and keys, ack states transport/system/application, retry or cancel of a failed message (D-156), "save as test case"); per flow (throughput, error rate, p95, backlog, blocked ordered queues, slowest steps — by wall time from the snapshots, by CPU from the node's JFR sampling aggregate `GET /admin/flows/:flow/cpu`, FIX-108); per platform (virtual threads in flight per flow, byte budget, batcher queue depth, DB, disk and the body journal's fill (D-105), Kafka lag only with the add-on).

To be (OPS-2, OPS-5, pending; OPERATIONS-BRIEF §2.1, §2.3, §2.7): the per-message screen shows the message's log — its log records in order; at the log level info each step's one fact is a sentence composed at display time; a refused input is found by the same search as a message, with the reason.

**Metrics and OpenTelemetry**

Today (built): none of v3.3's tracing and metrics. v3.3 put OpenTelemetry in the node (`Vertx.builder().withTracer`, one span per step, the trace id on the message and propagated through HTTP headers to backends) and Micrometer → Prometheus for the platform's metrics; no module depends on OpenTelemetry, Micrometer or Prometheus, and no span exists. What a node measures today: the wall time per step on the snapshot, CPU per flow and step from its JFR sampling aggregate (§4), and the counters `/health` answers with (`snapshotWriteFailures` among them). The trace id is the message id (§4).

To be (OPS-8, pending; OPERATIONS-BRIEF §1, §4): R8 is self-sufficient — metrics and alerts live inside the platform, and metrics go to ClickHouse by the same path as the log records. Prometheus and Alertmanager are no longer required. OpenTelemetry is an optional export: a step's log record is a span, so nothing is measured twice; the trace id is taken from the sender, stored on the message, passed to the receiver and searchable. Vector as the collector of the platform's logs and metrics is rejected, and so is any other new dependency for this (§2).

**Alerts**

Today (built): no alert layer — no rule, no inbox, no channel; Prometheus and Alertmanager, which v3.3 named for the platform layer, were never added. What stands today where an alert is to be: a line in the node's process log beside a refusal — the body journal logs a WARNING when its bytes cross 80 % of its bound and an ERROR when the refusals of a bound start (§4 Body journal) — and the answers of `/health` and `/ready` (§9). v3.3 named the conditions in two layers, none of them alerted on yet: platform (event-loop blocking, pools, DB, disk, the body journal at its bound — new messages refused 503 (D-105, CORE-4d; with ClickHouse down, CORE-REWORK Q-8, CORE-10, pending) — and Kafka lag only with the add-on) and business (silence detection — "usually 50/h, last hour 0" from the flow's own baseline; error rate; SLA; DLQ growth; blocked queue; backlog) with email, webhook, Slack, Teams and PagerDuty channels; the brief regroups them below. Grafana is AGPL and may run alongside for the operator's own use; customer dashboards are the platform's own React + ECharts over Postgres/pg\_clickhouse.

To be (OPS-8, pending; OPERATIONS-BRIEF §4, §6):

- Alerts live inside the platform. An alert inbox per team: new, taken over (by whom), resolved. Channels only notify and link to the inbox: email, webhook, Slack, Teams, PagerDuty.
- One cause is one alert with a count, and the alert states the cause from the error record. An agent may attach an analysis and a proposal (configurable which alerts, what exactly; §9 Agents).
- An alert never closes by itself: a human closes it, or an agent at a human's prompt.
- Groups: messages (errors, silence, running or waiting too long, unusual volume); channels (cannot connect, refused inbound connections, certificate expiry including the peer's); platform (buffer filling, intake stopped, ClickHouse or the database down, node takeover, a proposal waiting too long); security (failed logins, signs of attack, unusual behaviour, sensitive changes).
- R8 also acts by itself, configurable — e.g. N failed logins, then a block — for technical users too (§9 Security, Identity).
- A minimal liveness check from outside is still needed: a platform that is down cannot alert (§9, the probes).

## 9. Configuration, partner directory, caching, security, permissions

Flows are code in git; partner details are data in Postgres; secrets are references. Keeping the three apart is what makes git-first deployment, per-environment mocking and audit possible.

**Flow configuration**: JSON/YAML with a published JSON Schema (the first deliverable of the plan). Identity `tenant / package / kind:id @ version`, where the tenant position holds `default`; it goes with OPS-9 (pending: there is to be no tenant level, OPERATIONS-BRIEF §5; Teams and permissions below); the package is the namespace and authorization unit (PO SWCV → package, ESR namespace → folder; artifact meta files carry the PO origin block) and is to belong to a team (OPS-9, pending). A folder is structure only: ids are unique per package and never contain the folder, an optional `folder.yaml` keeps the verbatim namespace, and a flow is addressed as `<package>/<flow>` (D-060). Artifacts are found by their `kind` anywhere in the package, at most four folders deep, every folder name a slug; a file reference in a flow or test file is a path from the package root, an include or import inside an XML file is relative to the including file, and both stay inside the package (D-052, D-078) — except that a flow names a declared dependency's file as `<dep>:<path>`, the one way out, and an include inside it stays in that dependency (D-087). `package.yaml` declares dependencies, `package.lock` pins them, so shared collections like `common` scripts are versioned per package. Deploy = CLI from CI (`rail8 validate`, `rail8 deploy`), the runtime pins the commit hash on every message, rollback is a revert. A pre-commit hook validates the schema, compiles XSLT and dry-builds the pipeline without a runtime.

**Partner directory**: keyed by partner and PO interface, resolved at processing time through `${partner.…}` placeholders, versioned and exportable; the PO interface registry keeps PO namespace + name verbatim as the routing key. Runtime consumer entitlements (PO sender agreements) are checked by the endpoint or dispatcher; how they stand beside a caller's assignments (Callers and the developer portal below) is open (§14; OPS-11, pending).

**Caching, two levels**

| Level | Holds | Invalidation |
| --- | --- | --- |
| Node-local (Caffeine) | partner, routing and flow config; compiled XSLT/XSD/scripts by content hash; decrypted secrets, short TTL, never shared; lookup tables; built pipelines | Valkey pub/sub hint → node reloads the row from Postgres; full reload after reconnect; row versions as backup |
| Valkey | warm copy for node start, partner OAuth tokens (primary, refresh-ahead), global throttles and rate limits, poller leases and distributed locks, shared lookup-cache step, UI sessions | TTL; persistence off; HA via Sentinel or cluster |

Never cached: idempotent ids, aggregator state, ordered-queue state, DLQ.

**Security**

- Wallet: secrets, keys and certificates encrypted in Postgres (AES-GCM; master key from env, file or KMS, never in the DB), pluggable backends (Vault, Kubernetes Secrets, cloud vaults), `secret://` references only in flow config, audit log per read, certificate rotation via `updateSSLOptions` without restart. To be (OPS-9, pending; OPERATIONS-BRIEF §5): secrets belong to a team; shared ones are created only by a user with a special permission.
- Until the wallet exists, `secret://<name>` resolves from the node's environment (`RAIL8_SECRET_<NAME>`); runtime resolves endpoint options before a component sees them, and listings, records, the flow hash and unpacked files carry only the reference (D-081); until FIX-92, text a component or transport builds from a resolved value (an overlap problem's address, a build/start exception, a parked send failure) may show it.
- Identity: OIDC relying party, local users fallback (argon2 + TOTP), API keys and mTLS for machines, client-credentials for service accounts; ZITADEL optional. To be (OPS-8, pending; OPERATIONS-BRIEF §6): R8 also acts by itself, configurable — e.g. N failed logins, then a block — for technical users too: the owner counts the user name as sensitive, and a lockout is a signal that it leaked.
- Authorization. Today (built): one shared token on the node's admin API (`RAIL8_ADMIN_TOKEN`); none of v3.3's three authorization planes — control-plane roles scoped tenant → package → flow with a separate view-payloads permission; runtime consumer entitlements; data-level payload visibility and masking — is built. To be: Teams and permissions, Agents, and Callers and the developer portal below (OPS-9, OPS-10, OPS-11, pending; OPERATIONS-BRIEF §5). `vertx-auth-abac` is no longer a candidate: no policy engine now (D-147; §14). Masking of sensitive fields is parked by the owner (CONSIDER-20).

**Deployment mechanics (git-first)**

The control plane watches a git branch (or tag) per environment and pushes to the nodes of the target pool; the CLI can deploy manually in non-production only. Deployed state lives in Postgres and the UI shows git revision versus running revision per node.

1. Commit → `rail8 validate` (schema, XSLT compile, dry build of the pipeline) → in-process tests → merge.
2. Control plane detects the new revision for the environment, records the package version in Postgres, notifies nodes through Valkey.
   The archive is stored once in S3 at `<prefix>/archives/<sha256>.zip` before the record is written; the record (package, version, git revision, archive sha256, deployed_at, and the resolved dependency closure as pins name/version/archive sha256; no bytes) is one row per package, shared by the pool, and its write is the deploy's commit point. In Phase 1 the node's admin PUT stores and records; the control plane must likewise upload before it records. Archives are never deleted in Phase 1 (superseded ones serve an emergency rollback). A package names its dependencies by exact version in `package.yaml`; `package.lock` pins each with a content digest; the node resolves them against the versions it holds (current or pinned by a record), refuses a missing version, a digest mismatch or a cycle (422), and never prunes a pinned archive; a flow reads a dependency's file as `<dep>:<path>` (D-087). Off-node, `rail8 lock` writes the lock from sibling package folders and `rail8 validate` / `rail8 test` resolve the same way, validate holding the closure for that one validation without deploying or starting anything, test deploying it into each case's node on mocks (D-089, FIX-110).
   In Phase 1 the node's admin DELETE undeploys, non-production only like PUT (D-095). It is refused 409 while a record this node lists pins the package, or while the work queue holds items of one of its at-least-once flows. Deleting the row is its commit point; its flows then stop and its unpacked directories are pruned. Archives stay. Other nodes of the pool keep running the package until they restart.
3. Each node loads the new flow version beside the old one; new messages go to the new version, the old one drains in-flight work and unloads. No node restart. A failed load leaves the old version running.
4. Every message pins the flow, partner-directory and routing-table versions it ran with.
5. Rollback = revert in git; emergency rollback = CLI pin to a previous recorded version, audited.

At start a node restores before its admin API opens: per recorded package it fetches the archive, checks its sha256 and starts it; a package it cannot fetch, verify, unpack or build is listed FAILED with its problems; a flow that does not start is listed FAILED and the others run; and the `deployments` health check is DOWN while any package or flow is FAILED. S3 is thereby a start dependency of a deployed node, never of the hot path (F-12). Next to `/health`, two open probes take no token (D-123): `GET /live` answers 200 `{"status":"UP"}` while the admin server runs and reads nothing (Kubernetes startup and liveness probes); `GET /ready` answers 200 or 503 with `checks` `lifecycle` (UP only once the start finished and before the close began — the close marks it first, so a draining node is not ready while its listeners still answer), `fence` (the node lease open), `journal` (UP only when neither failed nor in outage) and `deployments` (the `/health` rule), each an in-memory read on the request, nothing awaited, so it needs no deadline. A minimal liveness check from outside is still needed — a platform that is down cannot alert —, and what performs it is not designed (OPS-8, pending; OPERATIONS-BRIEF §4).

Secrets and partner data never travel through git; the flow carries only `secret://` and `${partner.…}` references resolved per environment.

## 10. Extensions, scripts, migrated SAP mappings, API management

Custom code runs in-process by default on the same Step and Component SPI as the built-ins, isolated by classloader and made survivable rather than impossible to crash. This is what replaces custom EJBs and Java mappings from SAP PO.

| Kind | Packaging | Isolation | Typical use |
| --- | --- | --- | --- |
| Sandboxed scripts (Groovy, GraalJS) | inline in flow config | platform API only, deadline, CPU budget (no per-thread CPU reading on a virtual thread, F-21: the mechanism is open) | small transforms, routing logic, CPI script migration (`Message` API facade) |
| Java extension jar | jar + `META-INF/rail8-extension.json`, built in CI, `rail8 deploy`, bytes in S3, metadata in Postgres | per extension-version classloader whose parent sees only the platform API jar; flows pin the version; platform API semver range checked at deploy | PO Java mappings (`AbstractTransformation` facade with `MappingTrace`, `DynamicConfiguration`), custom steps |
| Custom component | same packaging, implements Component SPI | same | vendor SDKs, JMS providers, partner APIs |
| Out-of-process service | any language, HTTP/gRPC, bodies by reference | process boundary | untrusted, JNI or non-Java code; also the home for a disposable mapping JVM when a customer's jars are hostile |

Bad-extension policy: messages are durable before any extension runs; `-XX:+ExitOnOutOfMemoryError` with fast restart; extension name and version on every log record and metric — v3.3 said "every span, snapshot and metric"; a step's log record is the span where OpenTelemetry is exported (OPS-2, OPS-8, pending; OPERATIONS-BRIEF §2.1, §4); per-extension circuit breaker on deadline, failure rate and CPU (CPU not measurable per virtual thread, F-21: open); deploy-time bytecode scan (System.exit, thread creation, Runtime.exec, Unsafe, JNI → warn or refuse per policy). Platform-managed named datasources (`Services.datasource("crm")`: wallet credentials, pooled, metered; reactive clients for PG/MySQL/MSSQL/DB2/Oracle, JDBC on the virtual thread when the step declares blocking). No XA; idempotent-key + outbox pattern with an SDK helper.

**SAP compatibility runtime** (part of the runtime, not a separate process): XSLT 3.0 (Saxon-HE; EE as plugin), XSD validation, WS-Security, JCo/IDoc on the platform-thread pool, PO and CPI mapping facades, XI/IDoc simulator for tests. Its own test harness runs a migrated mapping jar against golden payloads from PO monitoring with no flow around it. **PO migration** = assessment via Directory API/ESR export → automatic ICO/channel/XSLT conversion → AI-generated XSLT for graphical mappings validated by golden tests → Java mappings as extensions → cut-over per PO interface through the dispatcher. The errors of the three engines — mapping, jq, XSLT — are to become the same error record: code, place in the artefact, text (OPS-4, pending; OPERATIONS-BRIEF §2.10; §8 Author voice and mapping trace).

**API management** is ingress policies on the same runtime (authentication, quotas, rate limits via Valkey, transformation, logging with the same monitoring) plus API and product objects, an own developer portal and an MCP gateway — no second runtime. The application and subscription objects of v3.3 are to be the caller and its assignment: the one shared object to which interfaces are assigned is the API manager's application, the assignment is the subscription and may carry limits, and the developer portal is a separate door (OPS-11, pending; OPERATIONS-BRIEF §5; §9 Callers and the developer portal). Policies are transport-independent functions, so an Envoy data plane calling them through `ext_proc` is an installation option for line-rate requirements. Gateway target: JWT-validated, rate-limited, metadata-recorded passthrough ≥ 20k req/s per 8-core node, p99 < 5 ms.

**AI, three audiences**: agents building integrations (everything as text with published schemas, complete API and CLI, MCP server on the control-plane API, dry-run endpoint returning per-step snapshots, structured errors, schema registry, sample payloads from monitoring as mapping specs, XSLT 3 plus a small declarative JSON mapping format, `AGENTS.md` in the repo layout); an `ai:` step type (pluggable provider from the wallet — per tenant in v3.3; with no tenant level its scope is open, §14 —, schema-validated output with deterministic fallback, prompt/model/cost on the snapshot); and AI building the platform. Guardrails: no direct production deploy (PR + CI only); secrets never in prompts; and, in place of v3.3's "agent role with scoped permissions", an agent's key with the rights of the user who created it, whose changes to run-time state and settings are proposals that a human approves in R8 (OPS-10, pending; OPERATIONS-BRIEF §5; §9 Agents). v3.3's guardrail "PII masking before any payload reaches a model" is removed (F-38): an agent's key is not masked by default, masked payloads for agent keys are an option for customers that may not send sensitive data to a model provider (§9 Agents), and masking of sensitive fields is parked by the owner (CONSIDER-20).

**Service extensions** (what PO Java proxies + EJBs were for)

Parked by the owner (CONSIDER-19; OPERATIONS-BRIEF §7): custom code as a whole — Java code inside the platform with database, cache and third-party libraries, as an EJB on SAP NetWeaver Java; its work outside a message; the link from a message to the table load its values came from. The text below is the v3.3 design, kept until the owner's brainstorm; none of it is built.

A service is a hosted Java component that several flows call, with its own libraries, state and resources — e.g. an ISDOC generator.

```java
@Rail8Service(name = "isdoc", version = "2.1")
public class IsdocService implements Service {
    public void start(ServiceContext ctx) { /* load templates, open datasources */ }
    public Envelope handle(Envelope in) { /* return a new envelope */ }
    public void stop() {}
}
```

Flows call it as a target: `to: service://isdoc` (sync, same thread, body by reference) or `queue://isdoc` (async, durable). Monitoring records the call as a step with latency and service version.

| Host kind | Runs where | Use |
| --- | --- | --- |
| In-process (default) | same JVM, isolated classloader, one singleton per service version per node | what PO ran as EJBs |
| Service pool | a runtime pool that deploys only services; flows reach it via `queue://` or internal HTTP | heavy rendering, OCR, big lookups |
| Out-of-process | any language, HTTP/gRPC, registered with its schema | legacy, JNI, untrusted |

One registry declaration (name, version, request/response schema, host kind) — a flow does not change when a service moves between host kinds.

Packaging is a **bundle**: `isdoc-2.1.flx` = `manifest.json` + the extension jar + `lib/*.jar`. The classloader sees the platform API jar and everything bundled, so a service brings its own JAXB, POI or Jackson versions. Deploy path: CI build → bytecode scan → bytes to S3, metadata to Postgres → `rail8 deploy` → target pool loads the classloader, calls `start()`, advertises the service; versions load side by side and flows pin them in `package.lock`.

Resources only through the SDK, so every use is attributed to the service version: `Services.datasource("erp")` (wallet credentials, pooled, metered; a bundled driver allowed), `Services.cache(name, maxBytes)` (node-local Caffeine under the node budget), `Services.sharedCache(name)` (Valkey, cross-node), `Services.http()`, `Services.secret()`, `Services.blob()` (large output straight to the BlobStore), `Services.scheduler()` (leased periodic jobs), `Services.executor()`, `Services.clock()` — and no `Services.log()`, which v3.3 listed here: custom code uses standard Java logging, there is no new R8 logging API (§8 Author voice and mapping trace; OPERATIONS-BRIEF §2.10, D-147). Local transactions only; outbox helper for write-and-emit. Services are never exposed to external callers directly; external access is always a flow with an endpoint and policies in front.

## 11. Testing and AI-assisted development

Every flow is testable in milliseconds without infrastructure because outside access exists only behind the Component SPI, and Clock, timers and id generation are injected through the `Runtime` record — no static singletons.

| Level | What | Runs in |
| --- | --- | --- |
| Step / flow unit test | `new FlowBuilder(fakeRuntime).build(cfg)` with fake components and in-memory stores | ms, JUnit 5 |
| Component contract suite | one suite every real and fake component must pass: backpressure, re-open on retry, ACK only after durable write, spill behaviour, cancel | seconds, Testcontainers where needed |
| Flow tests in git | a `kind: test` YAML in the package (by convention next to the flow, D-078); `rail8 test` binds a mock for every shipped scheme and runs each case in-process on virtual time; same runner the CI uses (D-080) | seconds |
| Golden tests from monitoring | "save as test case" on a monitored message → input = step 1 payload, expected output = last step, partner reply = recorded response; rerun hundreds after an XSLT change | seconds |
| Integration / stack | Testcontainers for Postgres, ClickHouse, Valkey, S3 (Kafka only for the optional add-on, CORE-REWORK O-1); nightly Compose; kill -9 ledger tests (sent = final-step rows, DLQ 0, work 0) | minutes |
| Protocol doubles | embedded MINA SSHD, Artemis, GreenMail, WireMock, own XI/IDoc simulator | — |
| Deterministic simulation | `rail8-sim`: the real core over in-memory stores and SPI doubles, seeded workload, faults and schedule, an oracle per tick and after the drain; a failing seed prints its replay command and is pinned (P2-10, D-143) | seconds per push, minutes nightly |

Fake clock drives backoff, leases and deadlines; a blocked platform thread in tests is a failure. Benchmarks run natively on Linux (never through Docker Desktop on Windows, which the prototype showed is round-trip-bound) and are recorded in `bench/RESULTS.md` with machine, date and configuration.

AI-assisted development is a design constraint, not a tool choice: the repo carries `CLAUDE.md` / `AGENTS.md` with the architecture rules (immutable Envelope, Body by reference, no capture of `Runtime` in a stage, one commit per step, prefer `javap` on resolved jars over documentation for library APIs, stop and report after each step), and ArchUnit tests enforce module boundaries so an agent cannot quietly violate them.

**Mocking**

Every component ships as a pair — real implementation and mock — with the same scheme, config schema and SPI, and both must pass the same contract suite. No component is merged without its mock. Mocks exist for development and CI only: a deployed environment (test or production) refuses to load any mock binding at deploy time.

The flow file is byte-identical everywhere; mocks are bound in a `kind: test` document of the same package (by convention a `*.test.yaml` next to the flow, D-078):

```yaml
flow: invoice-to-partner
mocks:
  partner:    { reply: fixtures/partner-ack.xml, delay: 20ms }
  erp-lookup: { script: lookups/customer.groovy }
  sftp-in:    { files: fixtures/inbox/*.xml }
cases:
  - name: domestic invoice
    send: fixtures/invoice-4711.xml
    expect:
      sent: { partner: { xpath: "/PartnerInvoice/@number", equals: "4711" } }
      keys: { invoiceId: "4711" }
      steps: 6
  - name: partner down
    send: fixtures/invoice-4711.xml
    mocks: { partner: { fail: 503 } }
    expect: { dlq: 1, retries: 3 }
```

Behaviours, same vocabulary for every component: `reply` (fixture), `recorded` (response captured in monitoring), `script` (Groovy/JS request → response), `files` / `messages` (consumer side, feed fixtures), `fail` (503, timeout, reset, malformed; after N, every Nth), `delay`; capture is no behaviour key: every mock always records what it was sent, and a test's `expect.sent` reads that record (F-16).

Two execution layers run the same YAML: in-process mocks with in-memory stores (milliseconds, on save and as the CI merge gate) and protocol doubles with Testcontainers (embedded SSHD, GreenMail, Artemis, WireMock, XI/IDoc simulator, real Postgres/ClickHouse, Kafka only for the add-on) as the release gate. Fixtures come from hand-writing, from "save as test case" in monitoring (v3.3: "masked by the flow's PII policy"; masking of sensitive fields is parked by the owner, CONSIDER-20), or generated from the schema registry.

## 13. Implementation plan

The order is foundations first, features last, and no phase is called done until its gate is measured — not a V1/MVP staircase but the dependency order of the architecture itself. Durations are deliberately absent; the gates, not the calendar, decide.

&#91;embedded content: implementation roadmap · 6 phases, 6 gates\]

Phases 0–2 build the runtime that everything else sits on; 3 turns it into the product; 4 and 5 widen it. Nothing in 3–5 is designed to be rewritten later.

**Phase 0 — spikes and scaffolding.** Monorepo with the modules of section 12, ArchUnit boundary tests, CI (build, test, native bench job on a Linux runner), `CLAUDE.md`/`AGENTS.md`. Flow, package and endpoint JSON Schemas published. Two spikes with numbers: the prototype's batched persistence rerun on native Linux Postgres (closes the < 5 ms p99 question), and `RequestScope` + admission semaphore under 10k virtual threads. Gate: schemas merged, bench baseline recorded.

**Phase 1 — core runtime.** `rail8-api`, `-core`, `-runtime` with Envelope/Body/BlobStore (memory tier and the node's body journal, which replaced the spool and S3 tiers, D-105, CORE-4; byte budget), RequestScope, per-flow admission, the batcher, Postgres MessageStore/DLQ, recording levels, http and mock components, xslt/validate/extractKey/route steps, the three delivery modes.
