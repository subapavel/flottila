# F-58 — sftp's dedupe key recognises a file picked up twice, not a sender's resend

Date: 2026-11-16 · Task: ISSUE-12 · ARCHITECTURE sections: §4, §6 (version 3.31)

- **Assumption in the document:** §4, *A message can arrive more than once*: "an at-least-once
  sender's resend is saved once only where its endpoint's component names a dedupe key (D-084) —
  sftp's file key today". §4, *XI quality of service*: "where the endpoint's component names a
  dedupe key, a sender's repeat is saved once". §6 (3.31, D-162): "a sender's repeat under its
  dedupe key is answered with the cancelled message's id and nothing runs". Read together: a
  sender that sends a file again over sftp is recognised, and ISSUE-12 item 1 asked the owner what
  should then happen to a cancelled message's key.
- **How it fails in practice:** the key is `sftp://host:port/path@mtime#bodyHash` - one path at
  one server mtime with one content. A sender that uploads the file again gives it another mtime,
  so another key, so another message under another id. What the key recognises is the platform's
  own second pickup of one file - its removal refused after the save, another node polling it
  after a takeover - and a sender's upload only when path, mtime and content are all the same.
  The owner said so on reading ISSUE-12 item 1: "when the sender sends it again it is not the same
  message - it has another id. You are mixing two unrelated things." An operator reading the
  documents would have expected a sender's resend of a cancelled file to be swallowed; it runs.
- **Severity:** minor — the documents were imprecise; no mechanism changes.
- **Evidence:** `SftpComponent.java:399` builds the key; its Javadoc (`:95-96`, `:158-159`) names
  the two cases it is for; `SftpComponentTest.java:530` pins its shape
  ("sftp.fileKey: sftp://host:port/path@mtime#bodyHash"); `SftpIngressDedupeIT` runs the save's
  duplicate check on it. Read by the architect. No test was looked for that uploads a file again
  with a new mtime and counts two messages: the claim rests on the key's shape.
- **Change made:** the two sentences of §4 and the one of §6 say what the key recognises; ISSUE-12
  item 1 is withdrawn and D-163 records the owner's statement - a sender's resend is another
  message under another id; ISSUE-11 item 2 carries a dated correction; CONSIDER-27's row notes
  it. Nothing in the code changes. Whether a sender may name a key of its own (an http header, the
  XI message id) stays CONSIDER-27's question.
