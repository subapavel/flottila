# F-38 — ARCHITECTURE still described monitoring, metrics, alerts and permissions as v3.3 had them

Date: 2026-11-15 · Task: OPS-1 · ARCHITECTURE section: status note, amendments, §2–§11, §13, §14 (version 3.25)

- **Assumption in the document:** up to version 3.24 the document describes monitoring as
  snapshots only (§8), with a write path that leaves a row unwritten after `maxWait` and counts it
  (§8 Write path, D-071). It requires Micrometer and OpenTelemetry exporters in the node and
  Prometheus/Alertmanager for the platform's metrics and alerts (§3, §8, §13). It has a tenant
  level and three authorization planes with `vertx-auth-abac` as a candidate (§4, §9, §14), masks
  PII before any payload reaches an AI tool or a model (§9, §10, §11), gives custom code a
  `Services.log()` (§10), and closes Phase 3 on "a dropped node leaves no gap in the timeline"
  (§13).
- **How it fails in practice:** the owner's brief `docs/OPERATIONS-BRIEF.md` (brainstorm of
  2026-11-14/15, D-147) decides each of these otherwise. None of what the brief decides is built;
  what is built is the snapshot path of the core rework. A reader of ARCHITECTURE got a design the
  owner has replaced, and the designers of OPS-2 to OPS-11 would have been bound by it.
- **Severity:** major (documented mechanisms are replaced: the snapshot-only log, the drop-and-count
  rule as a design, Prometheus/Alertmanager and the exporters, the tenant level and the three
  planes, masking before a model, a gate clause. The intent is kept: monitoring is the product,
  nothing is lost silently, and no performance is given up for it)
- **Evidence:** the brief's sections; BACKLOG rows OPS-2 to OPS-11 and CONSIDER-19 to CONSIDER-23,
  all pending at b702b49. Code read at b702b49 for the lines stated as built:
  - `platform/core/.../scope/MessageContext.java:31` (`DEFAULT_TENANT = "default"`, the trace id is
    the message id) and `deploy/postgres/V12__journal.sql` (`journal_keys.tenant`, D-106)
  - `platform/core/.../record/Snapshot.java`, `Trail.java` (the trail, the WARNING for an unwritten
    row) and `platform/runtime/.../admin/AdminServer.java:228` (`snapshotWriteFailures` in
    `/health`; the shared admin token; the remote address on the discard's audit row only)
  - `platform/runtime/.../journal/Journal.java:71` (WARNING at 80 % of a bound, ERROR when its
    refusals start)
  - `platform/api/.../StepResources.java` (no logging type)
  - no `Services` and no `MappingTrace` class under `platform/`; no Micrometer, OpenTelemetry or
    Prometheus in any pom or source file; the http component authenticates no caller and reads no
    address, certificate or TLS fact of its client
- **Change made:** a thin rewrite (the architect's decisions of 2026-11-15, after the designer and
  the opponent). Every statement of what is built stays, but for two fields the `Snapshot` record
  never had (point 2). Each passage the brief touches opens with "Today (built)" and goes on with
  "To be (OPS-n, pending; OPERATIONS-BRIEF §x)", which states only what the brief states as
  decided, in the brief's words, with no mechanism beyond it. No section is inserted or
  renumbered. No D-, F-, FIX-, CORE-, CONSIDER- or ISSUE- id cited in the body was removed (137
  before, 146 after). The points, each cited by its changelog row:
  1. **Status note, Amendments item 1, §14 item 1.** The note names both briefs with the scope of
     each; there is no general rule between the two briefs. Its "unchanged" was false since the
     changelog's first change to the body (2026-10-18) and is corrected. Amendment 1 and §14 item 1
     keep the built path "worker → bounded batch queue → Postgres" and append its replacement,
     memory → writer → the node's journal → mover → ClickHouse (OPS-2, CORE-8, CORE-10, pending).
  2. **Snapshots only → one log-record stream.** §8 One log-record stream, Log records, Stores and
     query surface and Screens state the snapshot as built and, as to be, the brief's §1, §2.1 to
     §2.7: one shape, three logs by owner, the info fact, the error record, connection failures
     and client facts in full. "Log record", "journal record" and "deployment record" are defined
     at the head of §8, and §4 says which one it means where "record" stood alone in a passage on
     the journal or the deployment (journal record, deployment record, the ingress snapshot's row;
     the admission bullet names `Body.size()` and the duplicate's wait says "WAL record").
     The `Snapshot` field list of §8 Write path and loss contract marks v3.3's extension name +
     version and trace id as not built: the record has neither (`Snapshot.java:41`). Followed in §3
     (Postgres and ClickHouse rows; the node row: a load balancer may stand in front and is not
     required, brief §2.7), §5 (secrets in headers replaced by a marker), §6 Recording (the info
     fact), §7 (no Postgres `message_log` table: the table of the superseded draft is not to be
     built), §10 ("every span, snapshot and metric" becomes every log record and metric) and §13
     Phase 3 (the log-record stream in place of "OTel spans").
  3. **Levels, trace, author voice, mapping trace.** New in §8 Levels and trace and §8 Author voice
     and mapping trace (brief §2.8 to §2.11), with the built state before them: no log level, no
     threshold, no trace, no line a step can add to its message. §6 Recording says "recording
     level" for the built `all | ends | errors | off` and "body level" for Q-9's, and names the log
     threshold beside the body recording. §4 names the bound `MessageContext` as the brief's
     direction for attributing standard Java logging. Removed from §10: `Services.log()` — it was
     never built, and the brief wants no new R8 logging API. Added to §10: the three engines'
     errors as one error record. §13 Phase 3 names the log levels, the author voice and the
     mapping trace.
  4. **The write path's drop-and-count as a design — changed guardrail.** D-071's rule (a row not
     written within `maxWait` is logged at WARNING, counted in `snapshotWriteFailures` and stays
     unwritten) is stated in §8 Write path and loss contract as today's behaviour and no longer as
     the design: "a bounded queue that fills is an alert" means wait and alert, never drop (brief
     §1, §3). To be: one buffer for the whole platform; when it is full, intake stops for the whole
     platform. §4 (admission, Body journal, Event bus, Writer) points at it. The stop is described
     by the door behaviours built today (HTTP 503 + Retry-After, pollers paused); everything else
     about it is OPS-2's. One sentence is proposed for CLAUDE.md's limit rule for the same reason.
  5. **The loss contract and the Phase 3 gate clause — changed gate condition.** §8 Write path and
     loss contract quotes the owner (brief §3): "a node crash may lose the last moments of that
     node's detail records. The message and the proof of its receipt are not lost, and the takeover
     record says so." It widens CORE-REWORK Q-6, which accepted the loss for sync runs only. The
     §13 Phase 3 gate clause "a dropped node leaves no gap in the timeline" contradicts it and is
     replaced by the owner's sentence, with no word added, `draft — review at hand-over`.
  6. **Prometheus/Alertmanager and the exporters as required parts — removed.** §3 no longer puts
     "Micrometer + OTel exporters" in the node; §8 Metrics and OpenTelemetry states that none of
     v3.3's tracing and metrics is built and, as to be, that metrics and alerts live inside the
     platform, metrics go to ClickHouse by the log-record path, and OpenTelemetry is an optional
     export (brief §4). The trace id is to be taken from the sender, stored on the message, passed
     to the receiver and searchable (brief §4): §4's `ScopedValue` bullet and §8 Metrics and
     OpenTelemetry say so beside the built state, where the trace id is the message id. §2 records the owner's rejection of Vector (CONSIDER-11) and of any other
     new dependency for the platform's logs and metrics (brief §1). §13 Phase 3 follows, and the
     Phase 5 gate clause "shows on every span" becomes "shows on every step's log record, which is
     the span where OpenTelemetry — an optional export — is exported (OPS-8, pending)".
  7. **Alerts: two layers on Alertmanager → alerts inside the platform.** §8 Alerts keeps v3.3's
     conditions as named and not built, and states the brief's §6 as to be: an inbox per team,
     channels that only notify, one cause one alert with a count, an alert that never closes by
     itself, four groups. The lockout after failed logins, for technical users too, is in §9
     Security (Identity); the liveness check from outside (brief §4) is at §9's probes.
  8. **The tenant level — removed.** There is to be one installation per customer (brief §5). The
     places where a tenant is built are stated as built, each holding the one value `default` and
     going with OPS-9: `MessageContext.tenant` (§4), the journal's key (§4 Body journal, §9), the
     first position of the identity (§9 Flow configuration). §8's ClickHouse row and §10's `ai:`
     provider said "per tenant" as design; both now say what is open instead.
  9. **Three authorization planes and `vertx-auth-abac` → rights, roles, assignments.** §9 states
     that only the shared admin token is built and none of the three planes, and gains "Teams and
     permissions": teams with an enforced boundary, a role as a bundle of rights, an assignment in
     a scope and optionally for a limited time, one decision point, payload as its own permission,
     team secrets, payload views recorded (brief §5). §14's abac item is closed: no policy engine
     now (D-147).
  10. **Masking before a payload reaches a model — removed guardrail.** §9's "per-flow PII masking
      policy applied before any payload reaches an AI tool or an unprivileged viewer" and §10's
      "PII masking before any payload reaches a model" are removed: an agent's key is not masked by
      default, and masked payloads for agent keys are an option (brief §5). Masking of sensitive
      fields as such is parked by the owner (CONSIDER-20), which §9, §10 and §11 (fixtures saved
      from monitoring) now say.
  11. **Agents.** New "Agents" in §9: an agent's key has the rights of the user who created it, and
      anything it changes is a proposal that a human approves in R8, recorded in the message's log
      (brief §5). §10's guardrail "agent role with scoped permissions" gives way to it. "No direct
      production deploy (PR + CI only)" stays: the proposal rule is for run-time state and
      settings. §13 Phase 5 follows.
  12. **Callers and the developer portal.** New in §9: the caller as one shared object to which
      interfaces are assigned, the assignment as the subscription, the check in memory on the hot
      path, and the portal as a separate door with no monitoring and no account (brief §5). §3's
      control-plane row, §10 API management (application and subscription become caller and
      assignment; API and product objects stay) and §13 Phase 5 follow. How v3.3's PO sender
      agreements (§9 Partner directory) stand beside a caller's assignments is open (§14;
      ISSUE-8 C.6).
  13. **Parked by the owner.** CONSIDER-19 to CONSIDER-23 are listed in §14 and named where their
      subject stands: custom code at §10 Service extensions (the v3.3 text is kept and marked as
      not built), the operating modes at §3, the dry replay at §6 Recording, counted summaries at
      §8 Write path and loss contract.
  14. **What the brief does not decide.** Nothing the brief marks [inferred], "to verify" or "not
      thought through" is stated as design. §14 lists each such item with its row, the four places
      where the two briefs meet (D-110 stands), and the open questions of the rewrite. §6 defines
      "interface" without binding the dispatcher case: "the operator's word for a deployed flow;
      which unit it names behind a dispatcher flow is open". ISSUE-8 carries all of them to the
      owner with the default the documents now state.
