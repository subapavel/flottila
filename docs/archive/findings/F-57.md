# F-57 — an operator's retry before a park has settled runs the message twice

Date: 2026-11-16 · Task: FIX-267 · ARCHITECTURE sections: §4, §6, §7, §8, §9 (version 3.30)

- **Assumption in the document:** §4, *Node lease and fence*: "`POST /admin/dlq/{id}/retry`
  re-enqueues a parked ingress under the same id for one more attempt, in one transaction (the DLQ
  row deleted, a step-1 work row inserted …)". §7: "a same-id restart (CORE-14b) deletes the DLQ
  row … and inserts its step-1 row in one transaction". Read alone: a parked message has no work
  row, so the restart's row is the only one of its id. §6, *One id for the life of a message*,
  adds that neither operation leaves a record and that cancel does not exist (F-55).
- **How it fails in practice:** a park is two writes: the DLQ row commits, then the run's work row
  is removed (the settle). An interrupted park "may still land" and its item is left to its lease;
  a failed settle leaves it likewise. The DLQ row then stands beside a leased work row of the same
  id — for up to one work lease in a living system, with no node's death; for as long as the
  holding node is down when it died between the two writes. The restart statement locks the DLQ
  row and never looks at `work`, so a `/retry` in that window inserts a second work row of the id:
  - the old row's next hand-out is within its bound (a message parked on a final failure before
    its last attempt): the retry's row delivers the message and the old row delivers it again;
  - the old row's next hand-out is past its bound: the retry's row delivers, the old row parks the
    message again, unsent, against no DLQ row — a delivered message back in the failed list.

  An operator, or a tool that retries the whole failed list, would see a partner act twice, or a
  message that reappears after its retry delivered it. A cancel built as a plain delete of the DLQ
  row would be undone the same way: the old row reruns the message or parks it again.

  With no operator's act the same window has another outcome, which this finding names and does
  not close: the old row, alone and within its bound, reruns, can deliver, and leaves the DLQ row —
  a delivered message in the failed list, which a later retry sends again and a later cancel
  records as cancelled. The message's history shows that delivery.
- **Severity:** major — the documented restart gains a guard; the intent (one more attempt under
  the same id, one work row for the id) is kept.
- **Evidence:** read in the code by the designer and, independently, by the architecture advisor
  and the architect; then staged by FIX-275's red cases (2026-11-16), which failed on the code
  before the guard as the reading said (`agent/work/FIX-275-red-its.log`, `DlqRestartIT`, an
  unkeyed flow, the settle failed once by a decorator at the store boundary):
  - `aRetryBeforeTheParksSettleLandedIsRefused`: "the id has exactly one work row, W1 ==>
    expected: <[8]> but was: <[8, 9]>", and the DLQ row gone;
  - `aMessageRetriedBeforeItsParkSettledIsAcceptedByThePartnerOnce`: "the partner accepted the
    message exactly once; sent [m-1@1, m-1@2, m-1@2] ==> expected: <1> but was: <2>";
  - `aMessageRetriedBeforeItsParkSettledDoesNotComeBackAfterItsDelivery`: "the failed list has no
    row of the delivered message ==> expected: <Optional.empty> but was: <Optional[Parked[…]]>".

  A node's death between the two writes was not staged: the same rows, reached another way. The
  places: the park and what follows it
  (`FlowWorker.java:687-703`), the settle and its failure (`:745-749`), the bound check and the
  park past it (`:637`, `:648-654`), the restart statement (`PgWorkQueue.java:290-301`: `d` locks
  the DLQ row, nothing reads `work`), the park's `on conflict` (`PgDlq.java:61-62`). No existing
  test pins the behaviour: each restart test asserts that no work row of the id exists before the
  restart (`DlqRestartIT:176`, `FlowWorkerRetryTest:672`, `WorkQueueContract:260-305`,
  `PgWorkQueueRestartIT:91-189` — the designer's reading). `agent/work/FIX-267-designer-2.md`
  section A gives the scenario step by step; `agent/work/FIX-267-advisor-2.md` change 5 confirms it
  and names the other outcome.
- **Change made:** nothing is built in this row. Designed (D-162): both acts of an operator on a
  failed message — retry and the new cancel — answer 409 while a work row of the id exists. The
  guard on `/retry` is a row of its own and goes first (FIX-275); the rest of the design — the acts
  as one core type, their record in the `audit` table, a time bound on the act's statements, cancel
  and its routes — follows in FIX-276 to FIX-278. The other outcome stays as it is: it is one more
  way a message arrives more than once (§4, D-160); whether such a rerun should end unsent, or
  should remove the DLQ row when it delivers, is CONSIDER-28. Built since: the guard on `/retry`
  (FIX-275, 2026-11-16) - a restart beside a work row of its id is refused and writes nothing; the
  route answers 409 naming the id and the row's seq.
