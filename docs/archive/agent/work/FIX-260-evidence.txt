5. What a refused start leaves (read: Node.java:252-263, :351-382, :594-603; MasterKeySource.java:92-123)

   Before the durability check (Node.java:252-263) the components are built, not started; no port is bound; the
   master key is loaded. The class gives its key by value (`TestJournalKey.with`, NodePoolWaitIT.java:177), so the
   load writes nothing; a generated key (the dev opt-in) would create its file on the first load and the second
   start reads it back (MasterKeySource.java:92-123). No statement has reached Postgres. The failure path closes
   the deployments, the lease, the sampler, the work queue, the signals, the peers and both pools. A second start
   of the same configuration meets nothing of the first that changes what it does.

   Checked by the reviewer against the code: only `Node.start` hands the exception to the test thread; the durability
   check is the intake pool's first statement and nothing before it reaches Postgres; a start refused at a later
   pooled statement (the work pool's first connect is `JournalKeys.load`, Node.java:265, a second exposure under the

   Its remarks, not blocking:

     in CI logs; and the bound's path (mutant 5, and a dropped `refusals.add`) is unpinned - passing the bound as an
     argument would pin both. Both go to row FIX-261, which reworks this fixture's retry.

     awaited after it, so it does not matter here. A product observation: row FIX-261's notes.
