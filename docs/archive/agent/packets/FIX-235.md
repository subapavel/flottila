# Packet FIX-235 (class C) — nothing the writer was given throws through it

Row: `agent/BACKLOG.md` FIX-235. `BatchingWriter` (`platform/core/src/main/java/dev/rail8/core/batch/`) still lets out
what D-146 says it contains. Found by FIX-195's late review (`agent/work/FIX-195-evidence.txt:28-40`), listed in the
class Javadoc (:35-41) as not contained:

- a sink that answers null: the `NullPointerException` leaves `commit` (:388) through `dispatch` to whoever dispatched —
  `save`, `saveWaiting`, `flush`, the window's timer task, an earlier batch's completion listener. The batch stays
  counted in flight, its items never complete, the batches taken with it never reach the sink;
- a throw of the caller's weight function leaves `save`/`saveWaiting` (:181), nothing queued;
- a negative weight (:182) and a null item (:180) are thrown too.

Design: the designer's draft is `agent/work/FIX-235-designer.md`; the architecture advisor read it as its opponent
(verdict: sound with changes). The decisions below are the architect's, with both in hand.

## The decisions

1. **A sink that answers null fails its batch.** In `commit`, after the catch and before `onComplete`, a null answer
   becomes a failed future whose cause is a `NullPointerException` that names the fault: its message contains
   `answered null` and the batch's item count. One place serves every dispatch path (the advisor walked enqueue, the
   waiters, flush, the window task and the completion listener and found no path that needs more).
2. **A throw of the weight function fails that save.** `save`/`saveWaiting` return a future failed with the thrown
   object itself; nothing is queued, no deadline is scheduled, the sink is not called. The call stays outside the lock.
3. **A negative weight fails that save** with an `IllegalArgumentException` that names the weight — a failed future, no
   longer a throw. A weight is computed from the item by code the writer was given; it is no argument of `save`. In the
   one caller with a weight function the throw was not loud anyway: `PgIntake.java:360` sits inside a `compose` lambda
   (:354), which turned it into a failed save and skipped `fail(m, …)`.
4. **A null item stays thrown** (`NullPointerException`, nothing queued): the writer's own argument check, like the
   constructors'. There is no item whose future could carry it.
5. **Any `Throwable`, not only `RuntimeException | Error`.** A checked exception thrown without being declared (a
   generic rethrow, another JVM language) passes today's catches and reopens this row's defect at every site: the sink
   (:385), the timer's schedule for a waiter's deadline (:205) and for the window (:277), a handle's cancel (:346), and
   the new catch around the weight function. All five catch `Throwable`.
6. **A commit counts as succeeded only when its future says so.** `commit` hands `afterCommit` the result's
   `succeeded()`, and a failed result fails the batch whatever `cause()` answers. Today `failure == null` means success,
   so a failed result with no cause would complete its items as written — the one path in the class that could report a
   failed commit as a success. Measured (`javap` on vertx-core 5.1.10, end of the designer file): `FailedFuture` and
   `FutureImpl.tryFail` replace a null cause, and `PromiseImpl` extends `FutureImpl`, so Vert.x's own futures do not
   produce it and `tryFail(null)` on the item's promise fails it with a `NoStackTraceThrowable`. `Future` is an open
   interface; the guard is by construction and adds no branch.
7. **The writer does not log a fault that fails an item; the failed future is its report.** It logs, as today, the
   faults that fail no item (a refused window, a refused cancel), two lines per episode and site. D-146's words "logged
   with that cause, never swallowed" are read so: each fault takes one of the two ways, none takes neither. The branch's
   decision and code that the owner approved (`agent/work/FIX-201/e835f43-…diff`: D-104's row, and the Javadoc of
   `save` — "Never throws; every failure is the returned future's cause") logged the refusals only. The amendment of
   D-146 that says this is marked `draft — review at hand-over`.

### The advisor's points and their disposition

- W1: every inline answer (a throw, null, an already-completed future) nests one commit → afterCommit → dispatch cycle
  per queued batch while in-flight is saturated; with PgIntake's single mode (batch 1, backlog 16 384) a run of inline
  answers could overflow the stack, and that error is outside every try. It predates this row; the depth is not
  measured. **Not fixed here**: the Javadoc lists it as outside the guarantee; new row FIX-257 [C] (an iterative drain).
- W2: sneaky checked throws. **Taken**: decision 5.
- W3: the proposed amendment overclaims ("the only throw") and drops the owner's words. **Taken**: the advisor's
  sentence, see "The ledger" below.
- W4: test gaps — a waiter entering through a null-answer drain; which way a flush completes; a negative weight through
  `saveWaiting`; the property test never saturates in-flight. **The first three are in the acceptance below**; the
  fourth belongs to FIX-257.
- The null cause: guard by construction. **Taken**: decision 6.
- The weight sums overflow a `long` near `Long.MAX_VALUE` (:297, :315, :316). Not a containment fault: **one Javadoc
  clause now, new row FIX-258 [A]**.
- A caller that only counts a failed save loses the cause (`PgMessageStore.java:82,88`; `Trail.java:163` and
  `SequentialIntake.java:71` unchecked). **New row FIX-259 [A]**: check that each caller reports the cause.
- A timer that answers a null handle is contained but misreported (the designer's Q4c). **One Javadoc clause**, after
  the implementer has checked the two claims against the code (:276, :345).
- A null item as a failed future too. **Not taken**: decision 4.

## Review round 1 (FAIL, 2026-11-15) - the fix packet

The reviewer's two reasons are about what the documents claim, not about the code's behaviour; no behaviour changes.

The decision (the architect): a sink's `Future` whose `onComplete` throws, or calls its listener twice, stays outside
the guarantee and is written down as such. Containing it needs a once-guard per batch that is safe across threads -
an allocation on the path CORE-GATE measures - for a `Future` that breaks its own contract; every sink in the tree
answers a Vert.x future. The designer rejected the cheaper form (draft, section 3: `onComplete` inside the try settles
a completed batch twice). Row FIX-257 reworks the drain and can revisit it there.
