# Packet FIX-215 (class B) — the ledger asserts what a takeover may finish, not less

Row: `agent/BACKLOG.md` FIX-215, under MAIN-1 (and FIX-184, the same assertion). Facts:
`agent/work/FIX-215-scout.md` — read it whole; every claim below has its file:line there.

## The cause: a test fault

`bench/src/test/java/io/rail8/bench/LedgerIT.java:132` asserts `finishedByNode2 <= unfinished`:
"only what was unfinished at the kill is finished after it". `unfinished` counts the ACKed ids that
had no final row at the kill. But the runtime commits a run's final snapshot row first and deletes
its work row afterwards, in a separate transaction (FlowWorker: the trail closes, then COMPLETE). A
node killed between the two leaves a work row beside a final row, and the takeover runs that item
again — at-least-once, each attempt from the ingress, its rows kept beside the first attempt's
(ARCHITECTURE §4; D-101, D-135, D-140). Such a message is finished after the kill although it was
not unfinished at it. BASE-1 run 3: workAtKill 66, unfinished 60, finished after the kill 66 — the
six are re-runs; no message was lost (200 distinct final ids, missing empty, work 0).

Nothing in the design promises that a finished message is never run again, so the product is not at
fault; the assertion compares with the wrong population.

## Acceptance

1. Line 132 is replaced by what the design does promise, each with its own message that prints the
   numbers:
   (a) `unfinished <= finishedByNode2` — every ACKed id that was unfinished at the kill is finished
       after it;
   (b) `finishedByNode2 <= workAtKill` — the surviving node finishes only what still had a work row
       at the kill (`workAtKill` is in the record already);
   (c) `finishedByNode2 - unfinished <= rerun`, where `rerun` is the number of distinct ACKed ids
       that have a final row (`partner`, `ok`) created before killedAt AND one created after it —
       each message finished after the kill beyond the unfinished ones is a re-run that already had
       its final row.
   Inequalities, not equalities: a commit of the dead node that Postgres completes after the
   snapshot may put one id on both sides. Say so in a comment of at most four lines that names the
   order (final row committed, then the work row deleted) and D-135 / D-140.
2. On a failure of (a)-(c) the message lists the ids concerned (at most 20), so the next failure
   explains itself.
3. Nothing else changes: every other assertion of the test, the other test of the class, and
   `LedgerMain` (no production change, no new record field unless (c) cannot be computed by SQL in
   the test — then stop and say so).
4. Red and green, observed: before the change, run the IT alone up to 5 times and keep the log of
   the first run that fails at :132 (`agent/work/FIX-215-red-<n>.log`); if none of 5 fails, say so —

   the change, 5 runs alone, all green; report for each run workAtKill, unfinished, finishedByNode2
