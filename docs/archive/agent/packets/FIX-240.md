# FIX-240 - the polling self-test's broken variant is broken in every run (class B; tests only)

Row: `grep -n "^| FIX-240 " agent/BACKLOG.md`. The scout's map, read it first: `agent/work/FIX-280-scout.md`, Part 2.

## What is wrong

`PollingConsumerContractSelfTest.aRemovalBeforeTheAnswerIsAwaitedFailsEveryCaseThatKeepsAFile` (:365-369) runs the
polling contract against a consumer that removes a file before its answer is awaited, and expects eight cases to
fail. The variant removes the file on the round's thread AFTER it started the handler's thread
(`Variant.Poller.take`: `deliver` at :230, `dir.remove` at :232). Nothing orders that removal and the contract
case's read. The case `stopWaitsForTheDeliveryInFlightAndCompletesItsRemoval` reads the directory once the handler
recorded its call (`PollingConsumerContract.java`:465-468); when the round's thread is the slower one, the read
sees both files, the case passes against the broken consumer, and the self-test fails (seven cases, not eight).
The fault is the fixture's: its broken consumer is not broken at the moment the contract looks.

## The change (the test-author)

Allowed path: `platform/testkit/src/test/java/dev/rail8/testkit/PollingConsumerContractSelfTest.java`.

1. The variant removes the file BEFORE the handler can be called - before `deliver(in, promised)` - so the removal
   precedes the handler's record of its call and therefore every read a case makes after seeing that call. The
   flag's Javadoc (:98) says what it now does and why the order matters. No sleep, no latch held for a time, no
   retry of the case; `PollingConsumerContract.java` does not change.
2. The expected set of :365-369 is held against the new order case by case, not adjusted to whatever comes out:
   for each of the eight, and for each contract case NOT in the set, one line in the hand-back - why it fails or
   why it still passes when the file is gone before the handler runs. If a case joins or leaves the set, say which
   assertion of it decides, with its line. `theFileStaysWhileTheAnswerIsPending` (`PollingConsumerContract.java`
   :255) has the same kind of read: say that it is covered by the same order.
3. Look at the other broken flags of the variant for the same fault - a broken act placed after a thread was
   started, read by a case at an unordered moment (`removedOnAnyAnswer` :239 runs after `answer.await()`, so it is
   ordered by the answer; say so or say otherwise). Report what you find; fix another flag only if it has the same
   fault, and name it.
