## The reading (the scout's, from the code; unverified — the red confirms it or you hand back)

- The case starts its node with `RAIL8_PG_POOL_SIZE` 2 and `RAIL8_PG_POOL_QUEUE` 1 (`NodePoolWaitIT` :600).
  Size 2 is one intake connection and one work connection (`NodeConfig` :460-461, :469-470, :680); the queue
  bound goes to both pools (`Node` :233-234, :419-421). So the work pool has one connection and one place to
  wait; a third user is refused at once.
- The deploy record is written through the work pool: `PgDeploymentStore.save` (`PgDeploymentStore` :46),
  called at `Deployments` :888; a pool refusal becomes kind BUSY with the text "the deploy record was not
  written: …" (`Deployments` :891-893) and the admin server answers 503 (`AdminServer` :964-976). That is
  the designed answer (FIX-172b): a client retries.
- What else uses the work pool at that moment, unawaited by `Node.start`:
  `retention.start()` (`Node` :343) runs its first run at once on a virtual thread (`Retention` :317-320,
  :362-369), each batch a transaction on the work pool (:435-439);
  and, inside the deploy itself, `FlowWorker.start()` claims at once (`FlowWorker` :223, :236-243) and the
  deployment does not wait for that claim (`Deployments` :1629-1638).
  The sweeper's first pass comes after 10 s; the lease and the signals have connections of their own.
- Most likely: the retention's first batch held the one connection, the worker's first claim sat in the
  queue's one place, and the record's save was the third. Which held and which waited the code does not say.
- Nothing tells a test that the node's start-up work on that pool has ended: no future, no gauge, no
  endpoint (`Node` :349-350 sets `ready` before the retention's run ends; `Retention.totals()` is not
  exposed). With the default queue (1024, `NodeConfig` :316) no deploy is refused this way: not a product
  fault, the fixture's.
- The same fixture serves every case of the class; the cases that set the queue bound are :366 and :600.

## Acceptance

1. The cause shown by a staged order, no sleep: with what a test controls in Postgres (a lock taken by the
   test's own connection on what the retention's first batch needs, taken before the node starts — or
   another hold you find that keeps a start-up user of the work pool in flight), `startDeployed` as it
   stands gets the 503 with the text of the sighting. Name the statement that held the connection and the
   one that waited. If the staged order does not give that refusal, stop and hand back what you saw.
2. The fixture's deploy then follows the contract of the answer it got: a deploy refused 503 with the pool's
   refusal is sent again until it is accepted, bounded by the class's existing bound, by the helper the class
   already waits with. Only that refusal is retried — any other answer fails the fixture at once with its
   body, as today — and the fixture fails, naming the last answer, when the bound passes.
3. Show that sending the deploy again is sound: a refused first deploy leaves nothing behind (no deployment
   row, no running flow, no listener on the port) — assert it in the staged case between the refusal and the
   release, by what the admin API and the database show.
4. The staged case stays in the class: the order is held, the first deploy is refused, the hold is released,
   the fixture's deploy succeeds. Every existing case and assertion stays as it is.
5. No production change. If you find that a started node can refuse a deploy for its own start-up work with
   the DEFAULT queue, stop: that is a product fault and a different row.
