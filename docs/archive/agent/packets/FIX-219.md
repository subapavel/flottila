# Packet FIX-219 (class A) — the ClickHouse harness counts its timed reads in a log it can rely on

Row: `agent/BACKLOG.md` FIX-219, under MAIN-1.

## What is known

`bench/src/main/java/dev/rail8/bench/ClickHouseCompressionMain.java` :221-225: after the reads the
harness runs `SYSTEM FLUSH LOGS` once and counts the `QueryFinish` rows of its read query ids in
`system.query_log`; `ClickHouseCompressionMainIT:93` expects `readsLogged` 20. In the whole-reactor
run of BRAND-1 C one cell had 19 with 20 reads and no mismatch
(`agent/work/BRAND-1-C-verify.log` line 84171); three runs of the class alone passed
(`agent/work/BRAND-1-C-ch-rerun-{1,2,3}.log`). The cause is not established. The suspect: the
server adds a query's `QueryFinish` row after the client has its whole answer, so a flush sent
right after the last read can run before that row is queued.

## Step 1 — the cause, shown (before any fix)

Context7 first (ClickHouse: `system.query_log`, `SYSTEM FLUSH LOGS`, when `QueryFinish` is
written); if unreachable or ambiguous, say so. Then show it here: a throw-away run of the harness's
read loop (in the IT's container) that, when the count after the first flush is short, flushes and
counts again and prints both — repeated until a short first count is seen or 200 cells have gone by.
Write what was seen to `agent/work/FIX-219-cause.md`. **If no short count can be provoked and the
documentation does not state the order, stop and hand back**: the architect decides (the fix below
is then a guard against a cause that is not shown, and is said to be one).

## Step 2 — the fix, red first

1. The harness reads the count through one small seam it owns — a method that takes the expected
   number and a counting function and returns the count once it reaches the expected number, asking
   again after another `SYSTEM FLUSH LOGS` at most a fixed number of times (a named constant, with
   its reason; no sleep, no wall-clock deadline) and returning the last short count when the bound
   is spent.
2. Red tests (unit, bench module, no container): a count short on the first look and whole on the
   second is returned whole; a count that stays short is returned short after exactly the bound's
   looks; a count whole at once costs one look; a count above the expected number is returned as it
   is (it is the IT's to refuse). Observed red before the seam exists.
3. The other three counts read after the same flush (:226-231: inserts, errors, optimize) are
   looked at: one that has the same exposure is read through the seam with its own expected number,
   or the hand-back says why it has none.
4. The IT's expectation `readsLogged == 20` stays. The result's JSON gains nothing, or only the
   number of looks if that is one field — say which.
5. `bench/RESULTS.md` is not touched: no number changes meaning.

Test-author first (the red unit tests), then the implementer (the seam in the harness).
